Session Variables
in Blazor

State that survives a refresh, state that doesn't, and the one mistake that leaks data between users

There is no HttpContext.Session["key"] in interactive Blazor. Once the app is running, there are no more HTTP requests — everything happens over a persistent SignalR circuit. You replace session state with one of three tools, chosen by one question: must it survive a browser refresh?

  • No → a scoped state container (a class registered with AddScoped) — lives for the circuit, in memory.
  • Yes → ProtectedSessionStorage / ProtectedLocalStorage — encrypted browser storage.
  • Forever / across devices → the database. (It was never "session" state.)

Part 1: Why HttpContext.Session Vanishes

"In classic ASP.NET I just wrote Session["tenant"] = "acme";. Where did it go?"

Classic ASP.NET is like mailing letters back and forth. Every request is a fresh envelope. To remember who you are, each envelope carries a claim-ticket number (the session cookie), and the server keeps a numbered locker (HttpContext.Session) matching that ticket. Letter arrives → open the locker → reply → close it. The connection lives for one round-trip.

Interactive Blazor is like being on a phone call with the server. You dial once (the initial page load), and then you just talk — a live, open line called the circuit. There are no more envelopes, so there are no more claim-tickets, so there is no numbered locker to open. The whole mechanism that HttpContext.Session depended on isn't there anymore.

What actually happens on load

A Blazor Server app serves one real HTTP request: the initial page. After that, the browser opens a WebSocket and every click, keystroke, and render travels over that socket as SignalR messages. No HTTP request means no HttpContext — the object is gone, or stale, the moment your components go interactive.

CLASSIC ASP.NET (MVC / Razor Pages) Request 1 ──► [HttpContext + Session locker] ──► Response 1 Request 2 ──► [HttpContext + Session locker] ──► Response 2 Request 3 ──► [HttpContext + Session locker] ──► Response 3 ▲ a fresh HttpContext every time BLAZOR SERVER (interactive) Request 1 ──► [HttpContext] ──► Response (the page) ◄── last HttpContext you'll see │ └──► WebSocket opens ──► ░░░ THE CIRCUIT ░░░ ──► click, type, render... (no HttpContext here)

"Interactive" is the key word. During prerendering and static SSR (the very first render, before the circuit connects) you do have an HttpContext. That is exactly why beginners get burned: their code works for a split second during prerender, then breaks the instant the page becomes interactive. State management in Blazor is mostly about respecting that boundary.

Part 2: The Scoped State Container

Your everyday "session variable" replacement.

A scoped state container is the whiteboard in your office. It's yours for as long as you're in the room (the circuit). You and everyone you invite in (all your components) read and write the same board. Walk out and come back — refresh the page — and you get a fresh, blank board. Nothing is written to disk; it only lives while you're there.

In Blazor Server, a service registered as Scoped lives for the lifetime of the user's circuit. That is the closest thing to "per-user session state" the framework gives you for free. You make a plain class, register it, inject it, and — because it's a shared object — let it raise an event so components re-render when it changes.

Step 1: The state class (a plain C# class)

// Business state lives in a service, never in the component itself.
public class UserState
{
    public string? SelectedTenant { get; private set; }

    public event Action? OnChange;

    public void SetTenant(string tenant)
    {
        SelectedTenant = tenant;
        NotifyStateChanged();           // tell every listening component to re-render
    }

    private void NotifyStateChanged() => OnChange?.Invoke();
}

Step 2: Register it (Program.cs)

builder.Services.AddScoped<UserState>();   // Scoped = one instance per circuit

Step 3: Use it in a component

// In any .razor component:
@inject UserState UserState
@implements IDisposable

<MudText>Tenant: @UserState.SelectedTenant</MudText>
<MudButton OnClick="@(() => UserState.SetTenant("acme"))">Escolher Acme</MudButton>

@code {
    // Subscribe so this component re-renders whenever the shared state changes...
    protected override void OnInitialized() => UserState.OnChange += StateHasChanged;

    // ...and ALWAYS unsubscribe, or the component leaks and StateHasChanged fires on a dead component.
    public void Dispose() => UserState.OnChange -= StateHasChanged;
}

builder.Services.AddScoped<UserState>();

"Give each connected user their own UserState whiteboard, and keep it for as long as their tab stays connected."


UserState.OnChange += StateHasChanged;

"Whenever the shared state announces a change, re-render me."

If a component subscribes to a state container's event in OnInitialized, it must @implements IDisposable and unsubscribe in Dispose. Forgetting this is the #1 cause of "ghost" re-render exceptions and slow memory creep in Blazor Server.

The honest limitation

This whiteboard is wiped on a full page refresh, on a navigation that forces a reload, and whenever the circuit drops and reconnects (flaky Wi-Fi, server recycle, laptop sleep). It is in-memory only. That is perfectly fine for transient UI state — the selected tab, a wizard's current step, an in-progress filter — but the moment you think "this has to still be there after F5," you've outgrown it. That's Part 3.

Part 3: Protected Storage — Surviving a Refresh

Protected storage is a sealed lockbox you leave in the user's own browser. You write a note, lock it (the server encrypts it with ASP.NET Core Data Protection), and hand it to the browser to hold. On refresh, the browser hands the box back and the server unlocks it. The user can see they're holding a box, but they can't read or forge the note inside.

Built into Blazor Server via Microsoft.AspNetCore.Components.Server.ProtectedBrowserStorage, this comes in two flavours that differ only in how long the box survives:

ProtectedSessionStorage

Backed by the browser's sessionStorage.

  • Survives a refresh / reconnect.
  • Cleared when the tab closes.
  • Not shared between tabs.

Good for: the truly per-session stuff — a wizard you don't want to lose to an accidental F5.

ProtectedLocalStorage

Backed by the browser's localStorage.

  • Survives refresh, tab close, and browser restart.
  • Persists indefinitely until cleared.
  • Shared across tabs of the same site.

Good for: chosen theme, language, last-selected tenant.

Using it

@inject ProtectedSessionStorage SessionStorage

@code {
    private string? _tenant;

    // MUST be OnAfterRenderAsync, and MUST guard on firstRender — see the warning below.
    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        if (!firstRender) return;

        await SessionStorage.SetAsync("tenant", "acme");

        var result = await SessionStorage.GetAsync<string>("tenant");
        if (result.Success)
        {
            _tenant = result.Value;
            StateHasChanged();          // we changed state AFTER render, so ask for another
        }
    }
}

var result = await SessionStorage.GetAsync<string>("tenant");

"Go ask the browser for its 'tenant' box. You get back a little envelope with two things: did it exist (result.Success) and, if so, what was in it (result.Value)."

Protected storage works through JavaScript interop — it has to talk to the browser. During prerendering / static SSR there is no live browser connection yet, so calling it from OnInitializedAsync throws "JavaScript interop calls cannot be issued at this time". The rule: only touch browser storage in OnAfterRenderAsync(firstRender: true) (or later), never in OnInitialized/OnParametersSet. The side effect — the value is null on the very first paint and "pops in" a frame later — is normal; handle it with a loading state.

Prefer a richer API (typed wrappers, change events, expiry)? The community packages Blazored.LocalStorage and Blazored.SessionStorage are popular and have the same shape — same prerendering caveat applies.

Part 4: HttpContext.Session — Why You Still Can't Lean On It

"But IHttpContextAccessor exists — can't I just grab the HttpContext and use its session?" Technically the type is injectable. Practically, it betrays you:

  • It is only meaningful during the initial request (prerender / static SSR).
  • Once the circuit is interactive, IHttpContextAccessor.HttpContext is null or stale — it captured a request that finished long ago.
  • Microsoft explicitly discourages depending on HttpContext in interactive components.

Use IHttpContextAccessor for one job only: reading something that exists at the moment the page is first requested (e.g. the initial user identity), and copy it once into a scoped state container. Never treat it as a live, writable session store.

Part 5: The Trap — "Scoped" Doesn't Mean What You Think

In classic ASP.NET, Scoped = one per HTTP request. In Blazor the word is the same but the boundary is completely different, and the difference is a genuine security gotcha.

Lifetime Classic ASP.NET Blazor Server Blazor WebAssembly
Singleton Whole app, all users Whole app, ALL users — shared! Whole app (one user anyway)
Scoped One HTTP request One circuit (≈ one browser tab / user session) Effectively a singleton (one user)
Transient Every injection Every injection Every injection

On a Blazor Server, a Singleton is shared by every connected user at once. Put SelectedTenant in a singleton and User B suddenly sees User A's tenant — a real cross-user data leak, plus race conditions because multiple circuits hit the same object on different threads. This is the same family of bug as static fields and static events holding per-user state.

Per-user mutable state → Scoped (the circuit). Never Singleton. Reserve Singleton for genuinely shared, read-mostly things: configuration, caches, a connection multiplexer.

Part 7: Practice

Question 1

A user picks "Dark mode", you store it in an AddScoped service, and it works. They press F5 and the app is light again. Why, and what's the fix?

Show answer

A refresh tears down the old circuit and starts a new one, so the scoped container is reconstructed empty — it was only ever in server memory. The theme needs to survive a refresh, so it belongs in ProtectedLocalStorage (read it back in OnAfterRenderAsync). The scoped container is still useful as the in-memory cache that components bind to during the session.

Question 2

You inject ProtectedLocalStorage and read a value in OnInitializedAsync. It throws "JavaScript interop calls cannot be issued at this time." What happened?

Show answer

OnInitializedAsync runs during prerendering, before the browser connection is live. Browser storage rides on JS interop, which isn't available yet. Move the read into OnAfterRenderAsync(firstRender) guarded by if (firstRender), and call StateHasChanged() after you set the value.

Question 3

To "save a database lookup", a teammate registers UserState (holding the current user's tenant) as AddSingleton. QA reports that logging in as a second user sometimes shows the first user's tenant. Diagnose it.

Show answer

On Blazor Server a singleton is one shared instance across all circuits, so every user reads and writes the same SelectedTenant. That's a cross-user data leak plus a thread-safety hazard. Per-user mutable state must be AddScoped (one per circuit). Singletons are only for shared, read-mostly data.

Question 4

A component subscribes with UserState.OnChange += StateHasChanged; in OnInitialized but never unsubscribes. What goes wrong over time?

Show answer

The state container keeps a reference to every component that ever subscribed, so disposed components are never garbage-collected (a memory leak), and OnChange tries to StateHasChanged() on dead components, throwing ObjectDisposedException. Fix: @implements IDisposable and unsubscribe in Dispose.
