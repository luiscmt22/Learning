Git — Comprehensive Handbook

A reference you can come back to. What / Why / When / How / TL;DR per concept.

Companion docs in this folder:

1. Mental model

Git stores snapshots, not diffs. Branches are named pointers to commits. Most state lives locally; remotes are just other Git databases you sync with.

The three trees

Every Git repo has three places where a file can live:

TreeLives inWhat it represents
Working directoryYour folder on diskWhat you're editing right now
Index (staging area).git/indexWhat git commit will record next
Repository.git/objects/The committed history

Most commands move data between these:

working dir   ──[ git add ]──▶  index  ──[ git commit ]──▶  repository
working dir  ◀──[ git restore ]── index ◀──[ git restore --staged ]── repository

What a commit actually is

A commit is a snapshot + metadata:

  • A pointer to a tree (full state of every file at that moment)
  • The parent commit(s) — usually one, two for merge commits, zero for the very first
  • An author, committer, timestamp, message
  • A SHA-1 hash (40 hex chars, e.g. 019bcea0c9...) that uniquely identifies it

Git doesn't store diffs — it stores whole snapshots, then deduplicates content by hashing. Two files with identical content are stored once.

Refs and HEAD

A ref is just a pointer to a commit. Branches and tags are refs. HEAD is a special pointer that says "where am I right now" — usually it points at a branch ref ("I'm on master"), occasionally directly at a commit ("detached HEAD").

When you commit, the branch ref HEAD points at advances to the new commit. That's all. Branches are not folders, not copies of code — just sticky notes.

"Local" and "remote" are just other databases

There is no "the database in the cloud." Every clone is a complete, equal Git database. origin is a nickname for "the database I cloned from." git fetch copies new commits from there into your local database; git push copies the other way.

2. Setup & config

Set your identity once. Configure line endings on Windows. Pick a default branch. Optionally set up a global gitignore and pull strategy.

Identity (required)

git config --global user.name  "Luís Tavares"
git config --global user.email "luiscmt90@gmail.com"

Without this, commits show as unknown <unknown> and CI/PR systems get angry.

Line endings (Windows)

Windows uses CRLF, Unix LF. Mismatch = noisy diffs.

git config --global core.autocrlf true

For project-level enforcement, add a .gitattributes file at repo root:

* text=auto
*.cs text eol=lf
*.sh text eol=lf
*.png binary

Default branch name for new repos

git config --global init.defaultBranch master   # or main

Global gitignore

OS junk shouldn't sit in every project's .gitignore. Use a global one:

git config --global core.excludesFile ~/.gitignore_global

Then put .DS_Store, Thumbs.db, .idea/, .vs/, *.user, etc. in ~/.gitignore_global.

Default editor & merge tool

git config --global core.editor    "code --wait"
git config --global merge.tool     vscode
git config --global mergetool.vscode.cmd 'code --wait $MERGED'

Pull strategy

By default, git pull does fetch + merge. Pick an explicit policy so you're never surprised:

git config --global pull.ff only      # refuse pull if it would create a merge commit
# or
git config --global pull.rebase true  # always rebase your local on top of remote

pull.ff = only is the safest default for solo work — it forces you to think when histories have diverged.

View & edit config

git config --list                    # everything
git config --global --list           # only global
git config --global --edit           # open the file directly

Configs are layered: system → global → local (per-repo). More specific wins.

3. The daily flow

status → edit → add → commit → push. With pull somewhere before push.

Check where you are

git status                           # uncommitted changes + branch
git status -sb                       # short, with branch line

status is your most-used command. Run it often — Git's safety relies on you checking state before destructive operations.

See what changed

git diff                             # unstaged changes (working vs index)
git diff --staged                    # staged changes (index vs HEAD)
git diff HEAD                        # all changes (working vs HEAD)
git diff master..feature             # between two branches
git diff master...feature            # commits unique to feature since branched off master
git diff --stat                      # summary, not full content

.. vs ... is subtle but matters: A..B = "commits in B but not A." A...B in diff = "compare B to the merge-base of A and B" — i.e. only what B changed since branching off.

Stage changes

git add path/to/file.cs              # one file
git add Services/                    # whole folder
git add -p                           # interactive — pick chunks per file
git add -u                           # all tracked files (modifications + deletions, NOT new files)
git add -A                           # everything (modifications + deletions + new files)
git add .                            # everything in current dir + below

-p (patch mode) is the secret weapon — it lets you split one file's changes into multiple commits.

Commit

git commit -m "feat: add foo"        # short message
git commit                           # opens editor for full message
git commit -a -m "..."               # auto-stage tracked files (skip git add)
git commit --amend                   # rewrite the last commit (message or contents)
git commit --amend --no-edit         # add staged changes to last commit, keep message

Conventional Commits is the most common message style:

type(scope): short summary

Optional longer body explaining the why.

BREAKING CHANGE: ... (if applicable)

Common types: feat, fix, refactor, docs, test, chore, perf, style, build, ci.

Push & pull

git pull                             # fetch + merge/rebase from upstream
git pull --ff-only                   # refuse if it would need a merge commit
git push                             # send local commits to upstream
git push -u origin feature/x         # first push of a new branch + set tracking
git push origin --delete feature/x   # delete a remote branch

The -u flag tells Git "remember this local branch tracks this remote branch." After that, plain git push and git pull work without arguments.

.gitignore

Lives at repo root (or per-folder). Each line is a glob.

# build outputs
bin/
obj/
*.user

# secrets
appsettings.Development.json
.env

# IDE
.vs/
.idea/

Already-committed files are not ignored retroactively. To stop tracking but keep on disk: git rm --cached path/to/file then commit.

4. Inspecting history

git log --graph --oneline --all is the universal "show me what's going on" command. Everything else is filtering.

The base: git log

git log                              # full history, paged
git log --oneline                    # one line per commit
git log --graph --oneline --all      # ASCII graph of all branches
git log -10                          # last 10 commits
git log --since="2 weeks ago"
git log --author="Luís"
git log --grep="fix"                 # search commit messages
git log -- path/to/file              # commits touching a file
git log -p                           # show patches (full diffs) per commit
git log -S"someText" -p              # commits where "someText" was added or removed (pickaxe)
git log -G"regex" -p                 # commits whose diff matches the regex

Show a single commit

git show <sha>                       # message + full diff
git show <sha> --stat                # message + file summary
git show <sha>:path/to/file          # the file's contents at that commit

Who wrote each line

git blame path/to/file               # author + commit per line
git blame -L 50,80 path/to/file      # lines 50-80 only
git blame -w                         # ignore whitespace changes

git reflog — the time machine

reflog records every move HEAD makes — every commit, checkout, reset, merge. It's local-only and survives ~90 days. This is how you recover from "I think I lost a commit." Find the SHA in reflog, then git reset --hard <sha> or git checkout -b recovered <sha>.

git reflog                           # everything HEAD did
git reflog show feature/x            # for a specific ref

5. Branches

Branches are named pointers. Cheap to create, cheap to delete. Use the modern switch / restore instead of overloaded checkout where possible.

List

git branch                           # local
git branch -r                        # remote-tracking
git branch -a                        # both
git branch -vv                       # show upstream tracking + last commit

Create & switch

Modern (Git 2.23+):

git switch master                    # switch to existing branch
git switch -c feature/foo            # create + switch
git switch -c feature/foo origin/x   # create from a remote branch

Legacy (still works, you'll see it everywhere):

git checkout master
git checkout -b feature/foo

switch only handles branches — clearer mental model. checkout is overloaded with file-restore duties (use restore for files now).

Rename

git branch -m new-name               # rename current branch
git branch -m old-name new-name      # rename another

If the old name is on the remote, push the new and delete the old:

git push origin -u new-name
git push origin --delete old-name

Delete

git branch -d feature/x              # safe delete (refuses if unmerged)
git branch -D feature/x              # force delete (loses unmerged commits)
git push origin --delete feature/x   # delete remote branch

A "deleted" branch is just an unset pointer — the commits still exist for ~90 days and are recoverable via reflog.

Track an upstream

git branch --set-upstream-to=origin/master master
# or while pushing for the first time:
git push -u origin feature/x

After tracking is set, git status tells you "ahead/behind by N commits" and pull/push work without arguments.

6. Remotes

A remote is a named URL pointing at another Git database. origin is just convention.

Manage

git remote -v                        # list, with URLs
git remote add upstream <url>        # add another (e.g. for forks)
git remote remove upstream
git remote rename origin gh
git remote set-url origin <new-url>  # change where origin points

Sync

git fetch                            # download commits into refs (origin/master etc), don't touch working dir
git fetch --all                      # all remotes
git fetch --prune                    # also delete local refs for branches deleted on remote
git pull                             # fetch + merge (or rebase, depending on config)
git push                             # send local commits to upstream
git push --tags                      # also push annotated tags
git push --force-with-lease          # safer --force; refuses if remote moved unexpectedly

Never git push --force to shared branches. Use --force-with-lease if you must — it bails if someone else pushed since your last fetch.

Inspect a remote

git remote show origin               # branches, tracking info, default branch
git ls-remote origin                 # raw list of all refs (branches + tags) on the remote
git ls-remote --tags origin          # only tags
git ls-remote --heads origin         # only branches
git ls-remote origin v1.2.0          # check if a specific ref exists on origin

Quick verification after pushing a tag: git ls-remote --tags origin shows whether the tag actually landed. Unlike git fetch + git tag -l, this queries the remote live and doesn't touch your local refs.

7. Merging

git merge feature brings feature's commits into your current branch. Three flavours: fast-forward, merge commit, squash. See merge-walkthrough.html for a full step-by-step tutorial.

Fast-forward (default when possible)

If your branch hasn't moved since feature branched off, Git just slides the pointer:

Before:                  After git merge feature:
  A─B─C ← master           A─B─C─D─E ← master, feature
       \
        D─E ← feature

No new commit. History is flat.

git merge feature                    # ff if possible, otherwise three-way merge
git merge --ff-only feature          # only merge if ff is possible; fail otherwise

Merge commit (forced, with --no-ff)

Creates a visible "bubble" in history showing the feature landed:

A─B─C─────────M ← master
     \       /
      D─E───' ← feature
git merge --no-ff feature

Use this for feature branches when you want the bubble for clarity / easy revert.

Squash merge

Collapses the feature into a single new commit on master, with no merge bubble:

git merge --squash feature
git commit -m "feat: add foo"

Good for small features with messy intermediate commits. Loses individual commit history.

Conflicts

When both branches edited the same lines, Git stops:

CONFLICT (content): Merge conflict in Services/Foo.cs

The file gets marker lines:

<<<<<<< HEAD
your version
=======
their version
>>>>>>> feature/x

To resolve:

  1. Edit the file, choose what's correct, delete all marker lines
  2. git add path/to/file
  3. Repeat for every conflicted file (find them with git status)
  4. git commit — Git pre-fills the merge message

Bail out: git merge --abort. Restores everything to pre-merge state. Nothing lost.

Three-way merge — what's actually happening

When ff isn't possible, Git finds the merge base (most recent common ancestor) and does a three-way merge: it compares "their changes since base" vs "your changes since base" and combines them. Conflicts arise only when both modified the same region.

8. Rebasing

Rebase replays your commits on top of a different base, rewriting history. Cleaner than merge for keeping branches up-to-date. Never rebase commits already pushed to a shared branch.

Basic: rebase your branch onto latest master

git switch feature/x
git fetch origin
git rebase origin/master

What happens conceptually:

Before:                  After:
  A─B─C ← master           A─B─C ← master
       \                        \
        D─E ← feature            D'─E' ← feature (new commits, same content)

D' and E' have new SHAs — Git replayed them on top of C. The original D and E are dangling and reachable only via reflog.

Interactive rebase — rewriting history

The most powerful Git command. Squash, reorder, edit, drop commits:

git rebase -i HEAD~5                 # last 5 commits
git rebase -i origin/master          # everything since branched off

Editor opens with:

pick a1b2c3d feat: add login
pick e4f5g6h fix: typo
pick h7i8j9k fix: another typo
pick l0m1n2o feat: add password reset

Change pick to:

ActionEffect
rewordKeep commit, change message
editPause to amend it
squash / sFold into previous commit, combine messages
fixup / fFold into previous commit, drop this message
drop / dRemove the commit
(reorder lines)Reorder commits

Save and close. Git replays. If conflicts arise, fix them, git add, then git rebase --continue. To bail: git rebase --abort.

--autosquash workflow

You spotted a bug in commit a1b2c3d. Make the fix, then:

git commit --fixup=a1b2c3d
git rebase -i --autosquash HEAD~10

Git pre-orders the editor with your fixup correctly placed. Saves typing.

The golden rule

Never rebase commits that have been pushed to a branch other people use. Rebasing rewrites SHAs. If feature/x is shared and you rebase, your colleagues' clones diverge from yours and they'll have a bad time.

Exception: rebasing your own PR branch to incorporate latest main is fine even if pushed — but you must git push --force-with-lease and warn anyone else who happens to have it checked out.

Rebase vs merge — which to use

SituationUse
Updating a feature branch with latest master, before sharingrebase
Merging a finished feature into mastermerge (--no-ff)
Cleaning up your own messy commits before pushinginteractive rebase
Pulling shared updates on a branch where others also commitmerge (or pull.rebase=true carefully)

9. Stashing

Temporarily shelve uncommitted changes so you can switch contexts. Like a clipboard for working-tree state.

You need to switch branches but have uncommitted work. You started edits on the wrong branch. A git pull is blocked by your unstaged changes.

Commands

git stash                            # stash tracked, modified files
git stash -u                         # ALSO stash untracked files
git stash -a                         # stash everything including ignored
git stash push -m "WIP: refactor X"  # named stash
git stash push -p                    # interactive — pick chunks to stash
git stash push -m "msg" -- file1 file2  # pathspec: stash ONLY these files, leave others in working tree

git stash list                       # show all stashes
git stash show stash@{0}             # summary of one
git stash show -p stash@{0}          # full diff

git stash pop                        # apply newest + remove from stash list
git stash apply                      # apply newest, keep in stash list
git stash apply stash@{2}            # specific stash
git stash drop stash@{0}             # delete one
git stash clear                      # delete ALL stashes (be careful)

git stash branch new-branch stash@{0} # apply stash on a new branch from where it was created

Stashes are local-only — they aren't pushed. Don't rely on stash for "remember to come back to this in a week." For long-lived work, commit to a WIP branch.

Pop applies the stash to your current branch, not back to the branch where it was created.

Conflict during pop means the stash isn't auto-deleted. Resolve, git add, then git stash drop manually.

10. Tags

Tags are immutable named pointers to commits. Use them for releases (v1.2.0) or as backup markers before risky operations.

Two kinds

  • Lightweight — just a name pointing at a commit. No metadata.
  • Annotated — full Git object with author, date, message, optional GPG signature. Use for releases.

Create

git tag v1.2.0                       # lightweight at HEAD
git tag -a v1.2.0 -m "Release 1.2.0" # annotated at HEAD
git tag -a v1.2.0 abc1234            # annotated at a specific commit

List, inspect, push

git tag                              # list all
git tag -l "v1.*"                    # filter
git show v1.2.0                      # info about the tag

git push origin v1.2.0               # push one
git push origin --tags               # push all annotated tags
git push --follow-tags               # push branch + tags reachable from it

Delete

git tag -d v1.2.0                    # local
git push origin --delete v1.2.0      # remote

Use case: backup before risky operation

This is the trick used in merge-walkthrough.html step 3 — plant a tag before a merge / rebase / reset, so any mistake is one command to undo.

git tag pre-rebase-backup
git rebase -i HEAD~10
# if it goes wrong:
git reset --hard pre-rebase-backup
git tag -d pre-rebase-backup

Pre-merge safety recipe (solo-dev workflow)

The full sequence for merging a feature branch into master with a rollback anchor — convention used across HRModule:

# 1. Anchor BEFORE the merge — the rollback point
git tag pre-merge/2026-05-19-prj-0006-t-0016
git tag --list "pre-merge/2026-05-19-prj-0006-t-0016"   # verify tag was created

# 2. The merge itself, with --no-ff so the bubble stays visible in history
git merge --no-ff feature/prj-0006-t-0016-myinfo \
          -m "Merge: PRJ-0006-T-0016 - MyInfo personal section"

git log --oneline --graph -10                            # verify graph shape

# 3. Publish: master and tags need separate pushes (lightweight tags don't auto-follow)
git push origin master
git push origin pre-merge/2026-05-19-prj-0006-t-0016

If the merge causes a problem you only notice later, git reset --hard pre-merge/<date>-<slug> rewinds master to its pre-merge state in one move. The tag is your rollback anchor.

Lightweight tags (the form above) require explicit push by name. For one-shot git push --follow-tags origin master to also publish the tag, create it as annotated instead: git tag -a pre-merge/<date>-<slug> -m "Anchor before merging <slug>". --follow-tags only follows annotated tags.

Tag naming convention: pre-merge/<YYYY-MM-DD>-<slug>. The pre-merge/ namespace groups all safety anchors when listing tags; the date sorts naturally; the slug is a short URL-friendly identifier (ticket code like prj-0006-t-0016 or a descriptive label like role-service-cleanup).

11. Undoing things — the survival guide

Almost everything is recoverable for ~90 days via reflog. Pick the right tool: restore for files, reset for branch pointer, revert for shared history, reflog for "I lost a commit."

"I edited a file and want to throw away changes"

git restore path/to/file             # discard unstaged changes
git restore .                        # discard ALL unstaged changes (be careful)
git checkout -- path/to/file         # legacy equivalent

"I staged a file and want to unstage"

git restore --staged path/to/file    # unstage but keep edits
git reset HEAD path/to/file          # legacy equivalent

"I want to fix the last commit"

git add forgotten-file.cs
git commit --amend                   # opens editor
git commit --amend --no-edit         # keep message, just add the staged changes

Don't amend a pushed commit on a shared branch — same rule as rebase. Amend rewrites the SHA.

"I committed to the wrong branch"

git switch correct-branch
git cherry-pick wrong-branch          # bring the commit over
git switch wrong-branch
git reset --hard HEAD~1               # remove from wrong branch

"I want to undo the last commit but keep changes"

git reset --soft HEAD~1              # keep changes staged
git reset HEAD~1                     # keep changes, unstaged (default --mixed)
git reset --hard HEAD~1              # discard everything (dangerous)
ModeWorking dirIndexHEAD
--softunchangedunchangedmoves
--mixed (default)unchangedreset to HEADmoves
--hardreset to HEADreset to HEADmoves

"I want to undo a commit that's already pushed"

Don't reset --hard and force-push to a shared branch — it breaks others' history.

git revert <sha>                     # creates a NEW commit that undoes <sha>
git revert -m 1 <merge-sha>          # revert a merge commit (1 = mainline parent)
git push                             # safe

"I think I lost commits"

git reflog
# find the SHA you want
git reset --hard <sha>
# OR start a new branch at that point
git switch -c recovered <sha>

The reflog is your backup tape. As long as Git's garbage collector hasn't run (default: 90 days), commits are recoverable.

"I want to bail on an in-progress operation"

git merge --abort                    # cancel an in-progress merge
git rebase --abort                   # cancel an in-progress rebase
git cherry-pick --abort              # cancel cherry-pick with conflicts
git revert --abort                   # cancel revert with conflicts

"I deleted a branch — can I recover it?"

git reflog                           # find the last commit on that branch
git switch -c recovered-feature <sha>

12. Cherry-picking

Apply a single commit from one branch onto another. Useful for backporting fixes.

git cherry-pick <sha>                # apply that commit on current branch
git cherry-pick <sha1> <sha2>        # multiple, in order
git cherry-pick A..B                 # range, exclusive of A
git cherry-pick A^..B                # range, inclusive of A
git cherry-pick -n <sha>             # apply but don't commit (stage only)

If conflicts arise: resolve, git add, git cherry-pick --continue (or --abort).

Cherry-picking creates a new commit with a new SHA but the same content/message. If you later merge the original branch in, Git is usually smart enough not to reapply (because the patch already matches), but you can occasionally get confused histories. Prefer rebase or merge for whole-branch operations.

13. Worktrees

One clone, multiple branches checked out into different folders simultaneously. Useful when you need to work on two branches without constantly switching.

Create

git worktree add ../sibling-folder feature/x
git worktree add ../hotfix -b hotfix/urgent master   # new branch from master

This creates ../sibling-folder containing feature/x's files. The .git/ data is shared with your main folder.

List & remove

git worktree list
git worktree remove ../sibling-folder
git worktree prune                   # clean up after manually deleted folders

The rule

Within one clone, the same branch can't be checked out in two worktrees. If master is in worktree A, trying git switch master in worktree B fails.

This is per-clone, not per-machine — two separate clones can both have master checked out independently. See merge-walkthrough.html § 4 for the full mental model.

14. Submodules vs subtrees

Both let you embed one repo inside another. Submodules link by reference, subtrees copy in. Both are awkward; consider monorepos or package managers first.

Submodules

A submodule is a pointer (commit SHA) into another repo. The parent records "this folder is a checkout of repo X at commit Y."

git submodule add <url> path/to/sub
git submodule update --init --recursive   # after cloning a repo with submodules
git submodule foreach 'git pull origin master'
Pros

Small parent repo, sub-repo stays independent.

Cons

Complex workflows, easy to forget --recursive, two-step commits.

Subtrees

A subtree merges another repo's history into a subdirectory of yours.

git subtree add --prefix=path/to/sub <url> master --squash
git subtree pull --prefix=path/to/sub <url> master --squash
git subtree push --prefix=path/to/sub <url> master
Pros

Consumers don't need to know it's a subtree, no --init step.

Cons

Parent repo gets bigger, history can be confusing.

When to use each

  • Need to update the sub independently and pin specific versions in parent → submodule.
  • Want a copy that lives in your repo with no extra setup for cloners → subtree.
  • Have an actual problem package managers (npm, NuGet) can solve → use those instead.

15. Repo separation

See separating-repos.md. Key trick: git push <remote> <sha>:<branch> --force rewrites a remote branch to a specific commit without touching your working tree.

For more advanced history surgery (extracting a subdirectory's history into its own repo), use git filter-repo:

git filter-repo --subdirectory-filter path/to/keep

git filter-repo is the modern replacement for the deprecated git filter-branch. Install separately (pip install git-filter-repo).

16. Hooks

Scripts in .git/hooks/ that Git runs at lifecycle points. Local-only by default unless you set up tooling.

Common hooks

HookWhen it runsCommon use
pre-commitBefore commit message editorRun linter, formatter, fast tests
commit-msgAfter message is writtenValidate Conventional Commits format
pre-pushBefore push to remoteRun full test suite
post-mergeAfter merge completesReinstall deps if package.json changed
prepare-commit-msgBefore message editor opensPre-fill template (e.g. issue number from branch name)

Anatomy

Hooks are executable scripts. Example .git/hooks/pre-commit:

#!/usr/bin/env bash
dotnet format --verify-no-changes || {
    echo "Formatting issues — run 'dotnet format' and re-commit."
    exit 1
}

Make executable: chmod +x .git/hooks/pre-commit.

Sharing hooks across the team

.git/hooks/ isn't committed (it's inside .git/). Share via:

  1. Commit a hooks/ folder, then git config core.hooksPath hooks per clone.
  2. Use a tool: Husky (Node), pre-commit (Python), lefthook, CaptainHook (PHP).

Skip a hook

git commit --no-verify               # skip pre-commit + commit-msg
git push --no-verify                 # skip pre-push

Don't make this a habit. Hooks are there for a reason. Skipping with --no-verify is for genuine emergencies, not "tests are slow today."

17. Searching the repo

git grep for current code. git log -S / -G for "when was this string added or removed?"

git grep "pattern"                   # search tracked files in working tree
git grep "pattern" master            # at a specific ref
git grep -n "pattern"                # with line numbers
git grep -i "pattern"                # case insensitive
git grep -l "pattern"                # files only

git log -S"InitializeForCompany"     # commits where this exact string was added/removed
git log -G"async\s+Task"             # regex pickaxe — diff matches regex
git log -p -S"foo" -- path/to/file   # full diffs, scoped to a file

git grep is significantly faster than regular grep -r because it skips ignored files and uses Git's index.

18. Bisect — finding the bug commit

Binary search through history to find which commit introduced a bug. With ~1000 commits, you find the culprit in ~10 steps.

git bisect start
git bisect bad                       # current commit is broken
git bisect good v1.0.0               # this old commit was working
# Git checks out the midpoint commit
# Test it; mark good or bad:
git bisect good                      # or 'bad'
# Git checks out next midpoint
# Repeat until Git names the culprit
git bisect reset                     # exit bisect mode

Automated bisect

If you have a script that exits 0 for "good" and non-zero for "bad":

git bisect start HEAD v1.0.0
git bisect run ./test-script.sh

Git runs the script automatically at each midpoint. You walk away, come back to the answer.

19. Git LFS

Large File Storage. Git's a poor fit for binary files >50MB; LFS replaces them with text pointers and stores blobs separately.

git lfs install                      # one-time per user
git lfs track "*.psd"                # tell LFS to manage these
git add .gitattributes               # LFS rules live here
git add design.psd
git commit -m "Add design"
git push                             # LFS uploads to LFS server

When to use

  • Photoshop / Illustrator files
  • Video / audio
  • Large datasets
  • Compiled binaries you must version (try to avoid this)

When NOT to use

  • Code / text — Git handles these efficiently natively.
  • Anything you can regenerate (build outputs, generated docs).

LFS storage is usually billed separately by GitHub/GitLab. git clone of an LFS repo without LFS installed gets pointer files, not real data. Some platforms (BitBucket Cloud) have surprising LFS quotas.

22. Shell environment notes (Windows)

Git commands look identical across shells, but anything you pipe through or continue across lines turns shell-specific fast. Know which shell your prompt belongs to.

Which shell am I in?

Prompt looks likeShell
PS C:\path>PowerShell (Windows-native)
C:\path>cmd.exe (legacy)
user@host:/path$Bash (WSL or Git Bash)
user@host MINGW64 /path$Git Bash specifically

Line continuation across shells

Same git command, three different line-continuation characters:

ShellContinuation char
Bash, Git Bash, WSLBackslash \ at end of line
PowerShellBacktick ` at end of line
cmd.exeCaret ^ at end of line

Bash form:

git merge --no-ff feature/x \
          -m "Merge feature/x"

PowerShell form:

git merge --no-ff feature/x `
          -m "Merge feature/x"

Two strict rules for any line-continuation: (1) a space before the continuation char, and (2) nothing after it on that line — not even trailing whitespace. Either is silent: the command appears to run but doesn't do what you wrote.

Filtering output — grep equivalents

grep is a Unix tool. Not present in PowerShell or cmd. Same operation, four ways depending on where you're running:

ShellCommand
Bash / Git Bash / WSLgit ls-remote --tags origin | grep pre-merge
PowerShellgit ls-remote --tags origin | Select-String pre-merge
cmd.exegit ls-remote --tags origin | findstr pre-merge
From PowerShell, calling WSLgit ls-remote --tags origin | wsl grep pre-merge

WSL — installed vs active

Having WSL installed doesn't mean your current shell uses it. Linux tools (grep, sed, awk, jq, etc.) only work either when you're inside a WSL session (prompt switched to Bash) or when you pipe through | wsl <tool> explicitly from PowerShell/cmd.

To drop into WSL from PowerShell:

wsl                                  # opens a WSL Bash session
# ... do Bash-y things ...
exit                                 # back to your original shell

The two-shell strategy

For Windows + Git workflows: use PowerShell for everyday Git (it handles paths, tab completion, and Windows-native tooling fine) and drop into WSL or Git Bash only when you need Unix tools (grep, complex pipes, shell scripts). Don't try to bend PowerShell into Bash syntax — pick the right shell per task.

23. Common errors & what they mean

fatal: refusing to merge unrelated histories

You're trying to merge two histories with no common ancestor. Usually means you cloned wrong, or you initialized a repo locally and then git pull'd a remote that already had commits. Fix:

git pull origin master --allow-unrelated-histories

Then resolve any conflicts. Verify the result is what you wanted before pushing.

error: failed to push some refs

The remote has commits you don't have locally. Don't --force. Pull, integrate, then push:

git pull --rebase origin master
git push

Your branch is ahead of 'origin/master' by N commits

Just informational. You have local commits not pushed yet. git push to send them.

Your branch is behind 'origin/master' by N commits, and can be fast-forwarded

The remote has commits you don't have. git pull (or git merge --ff-only origin/master).

Your branch and 'origin/master' have diverged

Both you and the remote have new commits. You need to merge or rebase. Check the picture: git log --graph --oneline HEAD origin/master.

fatal: '<branch>' is already checked out at '<path>'

Worktree rule: that branch is already in another worktree off the same clone. Either switch the other worktree to a different branch, or do your work in that other folder.

error: Your local changes to the following files would be overwritten by checkout

You have uncommitted edits to files that differ between branches. Commit, stash, or discard:

git stash
git switch other-branch
git stash pop

CONFLICT (content): Merge conflict in <file>

See § 7 — edit the file, remove markers, git add, git commit.

detached HEAD

You checked out a commit directly instead of a branch. Anything you commit here is reachable only by SHA — easy to lose. Either:

git switch -c new-branch    # save your work to a real branch
# or
git switch master            # commits made on detached HEAD are now reachable only via reflog

fatal: Authentication failed

Credentials wrong. On Windows, Git uses Credential Manager — open it from Control Panel and remove stale entries, then retry. For HTTPS GitHub, your password isn't your password — it's a Personal Access Token from Settings → Developer settings → Tokens.

error: cannot lock ref ...

Another git process is running, or .git/index.lock is stale. If no other git is running:

rm .git/index.lock
