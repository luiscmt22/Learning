1. The big confusion: clones vs worktrees

"You said a branch can only be checked out in one worktree at a time — but everyone on my team works on master. That can't be right."

You're right that it can't be right — because the rule applies to worktrees, not to clones. These are two different things that look superficially similar. Let's separate them.

A clone is one developer's independent copy of the repo

When Alice does git clone <url> on her laptop, she gets a complete, self-contained copy of the repo — the whole history, every branch, every commit. It has its own .git/ folder. It is independent. When Bob does the same on his laptop, he gets a separate independent copy. They are unrelated copies that happen to have started from the same source.

Alice's laptop                Bob's laptop                  Server (origin)
─────────────                 ─────────────                 ──────────────
C:/repo/                      D:/work/repo/                 git.example.com/repo.git
 ├ .git/  ← her own            ├ .git/  ← his own            ├ .git/  ← bare
 └ files/                      └ files/                      └ files/
   master ✓                      master ✓                      master ✓

           Each is a SEPARATE clone with its OWN .git/ folder.
           They each have master checked out — totally fine.
           They sync with the server via git pull / git push.

This is what your team does. Each developer has their own clone. Each clone has master checked out. No rule violated.

A worktree is a SECOND folder linked to the SAME clone

A "worktree" is a specific Git feature you opt into by running git worktree add <path> <branch>. It creates a new folder that shows the files for a chosen branch, but it shares the same .git/ database as the original folder.

YOUR machine right now
──────────────────────

C:/repos/aginternal/AgileInCloud/         ← worktree 1: feature/prj-0001-...
                  \
                   shares ONE .git/
                  /
C:/repos/aginternal/aginternal-notif/     ← worktree 2: perf/prj-0006-...

These two folders are ONE clone presenting TWO branches simultaneously.
They share the SAME .git/ between them.

The rule: WITHIN this single clone, the same branch can't be
checked out in both folders at the same time.

If master is showing in folder 1, and you try git checkout master in folder 2,
Git refuses with:
  fatal: 'master' is already checked out at 'C:/repos/aginternal/AgileInCloud/'

Why? Because if both folders showed master, you'd commit in folder 1
and folder 2 would be out of sync with itself — which file is "really" master?

Your team's setup uses clones — one per developer, no rule applies. The rule only kicks in when one developer (you, right now) has multiple worktrees off the same clone. The other Claude that worked on the notifications branch was in a worktree off your clone.

2. What a branch actually is

A branch is not a copy of your code. It's a sticky note with a name, stuck to a specific commit. When you commit, the sticky note moves forward to the new commit. When you switch branches, the files on your disk swap to match wherever that sticky note is currently pointing.

   A ── B ── C           ← master sticky note is here
              \
               D ── E      ← feature/prj-0001 sticky note is here

Each letter is a commit (a snapshot of all files at one point in time). The lines show which commit comes from which. The branch names are tiny pointers — they cost almost nothing.

When you run git checkout feature/prj-0001, Git moves the special pointer called HEAD to that branch and rewrites the files on your disk to match commit E. Your code looks different, not because Git copied anything, but because your "current view" pointer moved.

3. Clones — the everyday case

A clone is a complete independent copy of a Git repo. git clone <url> creates one. Everyone on your team has at least one. They are how distributed development works.

PropertyMeaning
Has its own .git/Yes — full history database, independent of every other clone
Knows about other clonesOnly via git remote URLs (e.g. origin)
Can have any branch checked outYes, including the same branch as another clone
Syncs howgit fetch, git pull, git push

4. Worktrees — the special case

A worktree is a feature for power users. You opt in with git worktree add <path> <branch>. It creates a new folder where the chosen branch is checked out, but the underlying database is shared with your original folder.

PropertyMeaning
Has its own .git/No — it shares the parent's .git/
Why use themRun two branches in parallel without constantly switching
The ruleEach branch can be checked out in at most one worktree at a time
List themgit worktree list
Remove onegit worktree remove <path>

The "one branch per worktree" rule applies only inside a single clone. Two different clones can both have master checked out. Two worktrees off the same clone cannot both have master checked out.

5. Local vs remote

Think of Git as a distributed network of independent diaries. Each diary is complete on its own. There is no "the database" living in the cloud — there are just lots of diaries, and you sync them with each other on demand.

YOUR LAPTOP                          SERVER (origin)
─────────────────────────            ─────────────────────────
.git/                                .git/  (bare repo)

master          A ─ B ─ C          master          A ─ B ─ C ─ D
                                                              ↑
                                                              someone pushed
                                                              this yesterday

origin/master   A ─ B ─ C          (this is your laptop's
                                      cached idea of where the
                                      server's master pointer was
                                      last time you fetched —
                                      currently stale)

The three sync commands

CommandWhat it doesRead-only?
git fetchPhone the server. "Show me your branches." Updates your local cache (origin/master). Does NOT touch your local master.Yes
git pullgit fetch, then merge origin/master into your local master. Two operations in one.No — modifies local master
git pushUpload your local commits to the server.No — modifies the server

So when I say "bring local master up to remote master", I mean: take the new commits the server has, copy them onto your laptop, and slide your local master pointer forward.

6. Fast-forward vs merge-commit

When you ask Git to merge feature into master, Git looks at the history and asks: "Did anything new happen on master since feature branched off?"

Case A — Master hasn't moved (fast-forward is possible)

Before:          ↓ master
   A ─ B ─ C
            \
             D ─ E
                  ↑ feature

After git merge feature (fast-forward — Git's default when possible):

   A ─ B ─ C ─ D ─ E
                    ↑ master AND feature both point here

The master sticky note just slides forward to where feature is. No new commit is created. History is a flat line.

Case B — You forced a real merge (with --no-ff)

Before: same as above

After git merge --no-ff feature:

   A ─ B ─ C ─────────── M     ← master
            \              /
             D ─ E ────'         ← feature still points at E

Git creates a brand new commit M whose two parents are C (old master) and E (feature tip). It's called a merge commit. Visually, history shows the bubble where the feature joined.

Why does this distinction matter?

Fast-forwardMerge commit (--no-ff)
Creates new commit?NoYes
History shapeFlat lineBubble — clear "feature landed here" mark
Easy to revert the whole featureNo — feature commits are now indistinguishable from regular commitsYes — git revert -m 1 M undoes the bubble
Best forTrivial updates, syncing local with remoteFeature branches

What the flags actually mean

FlagMeaning
--ff-only"Only allow this merge if it's a fast-forward. If a real merge would be needed, refuse and stop." Used as a safety belt on git pull — catches surprise divergence between local and server.
--no-ff"Even if a fast-forward is possible, force a merge commit anyway." Used on feature merges so the branch is clearly visible in history.
(neither)Git picks. Defaults to fast-forward if possible, otherwise three-way merge. Fine for most cases but less explicit.

7. Merge conflicts

A merge conflict happens when both branches modified the same lines of the same file. Git can't pick automatically because both edits are reasonable. It pauses and asks you.

What you'll see in the terminal

Auto-merging Services/Foo.cs
CONFLICT (content): Merge conflict in Services/Foo.cs
Automatic merge failed; fix conflicts and then commit the result.

What you'll see in the file

Open the conflicted file. Git wrote both options into it with marker lines:

public void DoStuff()
{
<<<<<<< HEAD
    var timeout = 30;        // ← what's on master right now
=======
    var timeout = 60;        // ← what feature branch wants
>>>>>>> feature/prj-0001
}

How to resolve it

  1. Edit the file. Pick one version, pick a hybrid, write something new — whatever's correct for the code.
  2. Remove ALL the marker lines (<<<<<<<, =======, >>>>>>>). The file should look like normal code again.
  3. git add Services/Foo.cs — this tells Git "this file is resolved".
  4. Repeat for any other conflicted files. Use git status to see what's still in conflict — they show as both modified.
  5. When all conflicts are resolved, run git commit. Git pre-fills a merge commit message; save and close the editor.

If you panic mid-conflict and want to bail entirely: git merge --abort. It restores your repo to the exact state it was in before you started the merge. Nothing lost.

8. The walkthrough — step by step

You're going to merge two feature branches into master. After each step you'll see what to expect. If your output differs, stop and check before continuing. We plant a backup tag in step 3 so any mistake is one command to undo.

Step 0 — Check where you are

git status

Expected output:

On branch feature/prj-0001-t-0010-phase-1a
nothing to commit, working tree clean

The two things to verify:

  • Branch line confirms which branch you're on (any feature branch is fine for now).
  • "working tree clean" — no uncommitted edits hanging around.

If you see Changes not staged for commit: instead, stop. We need to commit, stash, or discard those changes first.

Step 1 — Switch to master

git checkout master

Expected output:

Switched to branch 'master'
Your branch is up to date with 'origin/master'.

or possibly:

Switched to branch 'master'
Your branch is behind 'origin/master' by 3 commits, and can be fast-forwarded.

The first line is what matters. If you see error: 'master' is already checked out at '<path>', that's the worktree rule biting — master is currently in the sibling worktree folder. We'd need to switch that worktree off master first. Tell me if it happens.

What changed on disk: the files in your working folder are now master's version, not your feature branch's. Your IDE might refresh.

Step 2 — Pull the latest from the server

git pull --ff-only origin master

Expected output (one of):

Already up to date.

or:

Updating abc1234..def5678
Fast-forward
 SomeFile.cs | 5 +++++
 1 file changed, 5 insertions(+)

If you see fatal: Not possible to fast-forward, aborting. — that means the server has commits that conflict with your local master. Stop and ask. We'd need to investigate before continuing.

Step 3 — Plant a safety tag

git tag pre-merge-backup

Expected output: nothing. (Git is silent on success.)

You just stuck a label called pre-merge-backup on the current commit. If anything goes sideways in the next steps, git reset --hard pre-merge-backup jumps you back here.

Verify the tag exists:

git tag --list

You should see pre-merge-backup somewhere in the output.

Step 4 — Merge the notifications branch

git merge --no-ff perf/prj-0006-t-0008-notifications

Git opens an editor (Notepad, VS Code, or possibly Vim) with a pre-filled commit message:

Merge branch 'perf/prj-0006-t-0008-notifications'

You can edit the message or leave it. To finish:

  • Notepad — Ctrl+S, close window.
  • VS Code — Ctrl+S, close the tab.
  • Vim (if it opened) — type :wq and press Enter.

Expected output after editor closes:

Merge made by the 'ort' strategy.
 25 files changed, NNN insertions(+), MM deletions(-)
 ...list of files...

Step 5 — Merge the CRM branch

git merge --no-ff feature/prj-0001-t-0010-phase-1a

Same dance as step 4. Editor opens, save and close.

Expected output: similar to step 4 but with the larger CRM file list (~140 files).

Step 6 — Visualize what happened

git log --graph --oneline -20

Expected output (yours will have different hashes):

*   abc1234 (HEAD -> master) Merge branch 'feature/prj-0001-t-0010-phase-1a'
|\
| * 0292374 fix(crm): UI review for deferred-routing...
| * 38d7f9f docs(crm): forensic audit script...
| * ...
*   def5678 Merge branch 'perf/prj-0006-t-0008-notifications'
|\
| * 375c732 feat: Replace per-check-in validator pings...
| * ...
* old123 (origin/master) ...previous master commit...

Two Merge branch commits with |\ below them — those are the bubbles forced by --no-ff. Press q to quit the log view.

Step 7 — Sanity check (build + test)

dotnet build

Should end with Build succeeded and 0 Error(s).

dotnet test --nologo -v quiet --no-build

Should end with Passed! and a green count.

If either fails, stop. We can git reset --hard pre-merge-backup to undo the entire merge — that's exactly why we planted the tag.

Step 8 — Push to the server (only when you're satisfied)

git push origin master

Expected output:

Enumerating objects: ..., done.
...
To https://...
   def5678..abc1234  master -> master

Until this command succeeds, everything is local — only your laptop knows. Once pushed, it's on the server and your colleagues will see it on their next pull.

Don't push until you've actually run the app and tested the new features end-to-end. The build + test pass is necessary but not sufficient — there's UI behaviour that automated tests can't verify.

9. Recovery — the safety net

SituationCommandWhat it does
Merge in progress, conflicts you don't want to deal withgit merge --abortRestores everything to pre-merge state. Like Ctrl-Z for the in-progress merge.
Merge committed but you want to undogit reset --hard pre-merge-backupJumps back to the tag we planted in Step 3. Local only — safe before push.
You can't remember what happenedgit reflogShows every position your HEAD has been at, in order. Find the line you want, then git reset --hard HEAD@{N} where N is the index.
Pushed something bad and want to undo on the servergit revert <commit>Creates a NEW commit that undoes the bad one. Safe to push. Use this instead of reset --hard after pushing.

git reflog is your real superpower. Git remembers every move HEAD made for ~90 days, even branches you "deleted" or commits you thought were lost. As long as you haven't run git gc manually, you can almost always recover.
