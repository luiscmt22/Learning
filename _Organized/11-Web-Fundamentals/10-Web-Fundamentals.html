Static vs Dynamic Content

Static Files

Files served exactly as they are on disk. No code runs, no database queries, no user-specific changes.

File Type Examples Characteristics
JavaScript .js Browser executes client-side
Stylesheets .css Browser applies styles
Images .png, .jpg, .svg Browser displays
Fonts .woff2, .ttf Browser renders text
Documents .pdf, .html Browser displays/downloads

Dynamic Content

Content generated by code at request time. Can vary by user, time, database state, etc.

Source Examples Characteristics
Razor Components .razor C# code generates HTML
API Controllers /api/* C# returns JSON/data
Razor Pages .cshtml C# + HTML templating

Key Insight

Static:  Browser asks for /js/app.js → Server sends file bytes → Done
Dynamic: Browser asks for /dashboard → Server runs C# → Queries DB → Renders HTML → Sends result

The wwwroot Folder

The wwwroot folder is special in ASP.NET Core. It's the only folder that's publicly accessible by default.

Structure

YourProject/
├── wwwroot/                 ← PUBLIC (accessible via HTTP)
│   ├── js/
│   │   └── script.js        → GET /js/script.js
│   ├── css/
│   │   └── app.css          → GET /css/app.css
│   ├── images/
│   │   └── logo.png         → GET /images/logo.png
│   └── favicon.ico          → GET /favicon.ico
│
├── Pages/                   ← PRIVATE (not directly accessible)
├── Services/                ← PRIVATE
├── Models/                  ← PRIVATE
└── appsettings.json         ← PRIVATE (never expose!)

URL Mapping

The wwwroot folder itself is not part of the URL:

File Path URL
wwwroot/js/app.js /js/app.js
wwwroot/css/site.css /css/site.css
wwwroot/images/photo.png /images/photo.png

Security Note

Never put sensitive files in wwwroot:

  • ❌ appsettings.json
  • ❌ .env files
  • ❌ Connection strings
  • ❌ API keys
  • ❌ Source code (.cs, .razor)

Kestrel Web Server

What is Kestrel?

Kestrel is the built-in web server that comes with .NET. It's not a physical machine—it's software that runs inside your application.

Architecture Layers

┌─────────────────────────────────────────────────────────────┐
│  Physical Machine (your PC, cloud VM, container)            │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  Operating System (Windows, Linux, macOS)              │ │
│  │  ┌──────────────────────────────────────────────────┐  │ │
│  │  │  Your Application (dotnet run / HRModule.exe)    │  │ │
│  │  │  ┌────────────────────────────────────────────┐  │  │ │
│  │  │  │  Kestrel Web Server                        │  │  │ │
│  │  │  │  • Listens on ports (5000, 5001, 80, 443)  │  │  │ │
│  │  │  │  • Receives HTTP/HTTPS requests            │  │  │ │
│  │  │  │  • Routes to middleware pipeline           │  │  │ │
│  │  │  └────────────────────────────────────────────┘  │  │ │
│  │  └──────────────────────────────────────────────────┘  │ │
│  └────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘

When You Run dotnet run

  1. Your application starts
  2. Kestrel initializes inside your app
  3. Kestrel binds to configured ports (e.g., https://localhost:5001)
  4. Kestrel waits for incoming HTTP requests
  5. Each request flows through the middleware pipeline

Production Considerations

In production, Kestrel often sits behind a reverse proxy:

Internet → Nginx/IIS/Azure → Kestrel → Your App
           (reverse proxy)    (app server)

The reverse proxy handles:

  • SSL termination
  • Load balancing
  • Request buffering
  • Static file caching

Browser Caching

Why Browsers Cache

Downloading files is slow and uses bandwidth. Browsers store copies locally to:

  • Speed up page loads
  • Reduce server load
  • Save user bandwidth

How Caching Works

First Visit:
  Browser: GET /js/script.js
  Server:  200 OK + file contents + Cache-Control: max-age=3600
  Browser: Saves file with URL as key

Second Visit (within 1 hour):
  Browser: Checks cache for /js/script.js
  Browser: Found! Uses cached version (no network request)

Cache Headers

Servers control caching via HTTP headers:

Header Example Meaning
Cache-Control max-age=31536000 Cache for 1 year
Cache-Control no-cache Always revalidate with server
Cache-Control no-store Never cache
ETag "abc123" File fingerprint for validation
Last-Modified Wed, 01 Jan 2025 When file last changed

The Problem

When you update script.js on the server:

  • Server has: New version
  • Browser has: Old cached version
  • Browser doesn't know to fetch new version!

Cache Busting

The Solution

Trick the browser into thinking it's a different file.

Method 1: Query String (Simple)

<!-- Before update -->
<script src="/js/script.js?v=1"></script>

<!-- After update -->
<script src="/js/script.js?v=2"></script>

How it works:

  • Browser sees /js/script.js?v=1 and /js/script.js?v=2 as different URLs
  • Server ignores ?v=2 and serves the same file
  • Browser downloads fresh copy and caches under new URL

Pros: Simple, no build tools needed Cons: Manual version incrementing

Method 2: File Hash (Production)

Build tools generate unique filenames based on file content:

<!-- Before update -->
<script src="/js/script.a1b2c3.js"></script>

<!-- After update (content changed, hash changed) -->
<script src="/js/script.d4e5f6.js"></script>

Pros: Automatic, optimal caching (cache forever, new content = new URL) Cons: Requires build tooling (webpack, esbuild, etc.)

Method 3: ASP.NET Core Tag Helper

<script src="~/js/script.js" asp-append-version="true"></script>

Renders as:

<script src="/js/script.js?v=SHA256HashOfFile"></script>

Pros: Automatic, built into ASP.NET Core Cons: Only works in Razor views/pages

The Request Pipeline

Middleware Concept

ASP.NET Core processes requests through a pipeline of middleware. Each middleware can:

  1. Handle the request and return a response
  2. Pass the request to the next middleware
  3. Do something before AND after the next middleware

Visual Pipeline

Request                                                    Response
   │                                                          ▲
   ▼                                                          │
┌──────────────────────────────────────────────────────────────┐
│  UseHttpsRedirection()                                       │
│  Redirects HTTP → HTTPS                                      │
└──────────────────────────────────────────────────────────────┘
   │                                                          ▲
   ▼                                                          │
┌──────────────────────────────────────────────────────────────┐
│  UseStaticFiles()                                            │
│  If URL matches wwwroot file → serve it → STOP               │
│  Otherwise → pass to next middleware                         │
└──────────────────────────────────────────────────────────────┘
   │                                                          ▲
   ▼                                                          │
┌──────────────────────────────────────────────────────────────┐
│  UseRouting()                                                │
│  Determines which endpoint matches the URL                   │
└──────────────────────────────────────────────────────────────┘
   │                                                          ▲
   ▼                                                          │
┌──────────────────────────────────────────────────────────────┐
│  UseAuthentication() / UseAuthorization()                    │
│  Validates user identity and permissions                     │
└──────────────────────────────────────────────────────────────┘
   │                                                          ▲
   ▼                                                          │
┌──────────────────────────────────────────────────────────────┐
│  MapBlazorHub() / MapControllers() / MapRazorPages()         │
│  Your application code runs here                             │
└──────────────────────────────────────────────────────────────┘

Static Files Example

GET /js/face/script.js

1. UseHttpsRedirection: "Already HTTPS, pass through"
2. UseStaticFiles: "Checking wwwroot/js/face/script.js..."
   Found! Read file, send to browser, DONE.
   (Later middleware never runs)

GET /dashboard

1. UseHttpsRedirection: "Already HTTPS, pass through"
2. UseStaticFiles: "Checking wwwroot/dashboard..."
   Not found. Pass to next middleware.
3. UseRouting: "Matches Blazor route /dashboard"
4. UseAuthentication: "User is logged in"
5. UseAuthorization: "User has permission"
6. MapBlazorHub: Render Dashboard.razor component

Order Matters!

// Program.cs - ORDER IS CRITICAL

app.UseHttpsRedirection();     // 1. Redirect HTTP to HTTPS first
app.UseStaticFiles();          // 2. Serve static files (fast path)
app.UseRouting();              // 3. Match routes
app.UseAuthentication();       // 4. Who is the user?
app.UseAuthorization();        // 5. Can they access this?
app.MapBlazorHub();            // 6. Handle Blazor
app.MapFallbackToPage("/_Host"); // 7. Fallback for SPA routing

If you put UseAuthentication() before UseStaticFiles(), you'd require login to see CSS/JS files!

Quick Reference

Common Paths

What Path
Static files root wwwroot/

CSS wwwroot/css/
Images wwwroot/images/

Common Issues

Problem: CSS/JS changes not appearing Solution: Cache busting (?v=2) or hard refresh (Ctrl+F5)

Problem: 404 for static files Solution: Check file exists in wwwroot/, check app.UseStaticFiles() is called

Problem: Static files require authentication Solution: Ensure UseStaticFiles() comes before UseAuthentication()
