Equality in C#: Equals, GetHashCode, IEquatable, IEqualityComparer

A practical guide to value vs reference equality, the equality contract, and custom comparers (with StringComparer).

1. The default behavior: reference vs value

By default, C# compares two things differently depending on whether they're a reference type (class) or a value type (struct, primitive).

Classes — reference equality

For a class, == and Equals ask “are these the same object in memory?” — not “do they have the same values?”

public class Point
{
    public int X { get; }
    public int Y { get; }
    public Point(int x, int y) { X = x; Y = y; }
}

var a = new Point(1, 2);
var b = new Point(1, 2);

Console.WriteLine(a == b);        // False
Console.WriteLine(a.Equals(b));   // False

Both return False because a and b are two distinct objects, even though their fields are identical.

Structs and primitives — value equality (sort of)

Value types compare field-by-field by default, but via reflection — slow and box-prone. You almost always want to override Equals on structs too.

2. The Equals / GetHashCode contract

When you want value equality on a class, you must do two things together:

  1. Override Equals(object?) to compare by content.
  2. Override GetHashCode() so equal objects produce equal hashes.
The rule: if a.Equals(b) is true, then a.GetHashCode() == b.GetHashCode() must be true. Violating this breaks Dictionary, HashSet, LINQ Distinct, and many other things in subtle ways. 
public class Point
{
    public int X { get; }
    public int Y { get; }
    public Point(int x, int y) { X = x; Y = y; }

    public override bool Equals(object? obj)
    {
        if (obj is not Point other) return false;
        return X == other.X && Y == other.Y;
    }

    public override int GetHashCode() => HashCode.Combine(X, Y);
}

HashCode.Combine does the bit-mixing for you — just pass the fields that participate in equality.

Reading obj is not Point other

That single line does three things:

  • Type test — is obj actually a Point?
  • Declaration pattern — if so, give me a variable other already cast to Point.
  • Negation — not inverts the test.

The pre-C# 7 equivalent was uglier:

if (obj == null || obj.GetType() != typeof(Point)) return false;
var other = (Point)obj;   // redundant cast

3. IEquatable<T> — the strongly-typed overload

The inherited Equals takes an object. That means every call must:

  • Box value types (allocation on the heap).
  • Cast reference types (runtime type check).

IEquatable<T> adds a second Equals with the real type as parameter, sidestepping both:

public class Point : IEquatable<Point>
{
    public int X { get; }
    public int Y { get; }
    public Point(int x, int y) { X = x; Y = y; }

    // A — strongly typed, the real logic
    public bool Equals(Point? other)
    {
        if (other is null) return false;
        return X == other.X && Y == other.Y;
    }

    // B — overrides object.Equals, delegates to A
    public override bool Equals(object? obj) => Equals(obj as Point);

    public override int GetHashCode() => HashCode.Combine(X, Y);
}

B → A: the delegation pattern

External callers
      │
      ├─ knows it's a Point  ———►  A  (direct, no cast, no box)
      │
      └─ only sees object    ———►  B  —delegates►  A

A and B are two separate methods that both exist. They don't replace each other; B is a thin adapter that funnels object-typed callers into A. obj as Point is a safe cast — returns null on mismatch instead of throwing, which A handles with its other is null check.

Operators == and !=

For classes, == still uses reference equality even after you override Equals. To make a == b mean value equality, overload the operators:

public static bool operator ==(Point? a, Point? b) =>
    a?.Equals(b) ?? b is null;

public static bool operator !=(Point? a, Point? b) => !(a == b);

The line a?.Equals(b) ?? b is null reads as:

  • If a is not null → call a.Equals(b).
  • If a is null → result is b is null (both null counts as equal).

4. IEqualityComparer<T> — equality from the outside

Sometimes the type itself shouldn't define equality — or you need different equality rules in different contexts. IEqualityComparer<T> lets you supply equality logic as a separate object.

Concrete example from your own Chapter2:

internal class CaseInsensitiveCharComparer : IEqualityComparer<char>
{
    public bool Equals(char x, char y)
        => char.ToUpper(x) == char.ToUpper(y);

    public int GetHashCode(char input)
        => char.ToUpper(input).GetHashCode();
}

IEquatable<T>The type itselfLINQ, collections (when no comparer is given)
IEqualityComparer<T>A separate objectDictionaries, sets, LINQ — when you pass one in

5. StringComparer — the built-in flavors

StringComparer is a set of ready-made IEqualityComparer<string> implementations exposed as static properties. You almost never need to write one yourself for strings.

FlavorComparesUse for
OrdinalByte-exact, case-sensitiveDefault for IDs, keys, filenames
OrdinalIgnoreCaseByte-exact, case-insensitiveIDs/keys where casing shouldn't matter
InvariantCultureCulture-neutral linguistic rulesCross-machine sorting/comparison
InvariantCultureIgnoreCaseSame, case-insensitiveSame, case-insensitive
CurrentCultureUser locale rulesUser-facing text comparison (rare)
CurrentCultureIgnoreCaseSame, case-insensitiveSame, case-insensitive
Rule of thumb: for anything that's not user-facing prose — IDs, keys, file paths, config names — use Ordinal or OrdinalIgnoreCase. They're the fastest and free of locale surprises.

6. How Dictionary uses a comparer

A Dictionary<TKey, TValue> does two things with each key on every lookup:

  1. comparer.GetHashCode(key) — to find the bucket.
  2. comparer.Equals(key, storedKey) — to confirm the match.

When you build it, you can install a comparer that changes those two operations forever:

var dict = new Dictionary<string, StoryNode>(StringComparer.OrdinalIgnoreCase);
dict["Start"] = node;
dict["start"];   // works — case-insensitive lookup
dict["START"];   // also works
Important: the key is stored as-is — nothing is “normalized.” If you add "Start", the dictionary literally stores the string "Start". The comparer only changes how future lookups are matched against stored keys.

With ToDictionary

var comparison = StringComparer.OrdinalIgnoreCase;

_nodes = nodes.ToDictionary(n => n.Id, comparison);

That uses the overload:

Dictionary<TKey, TSource> ToDictionary<TSource, TKey>(
    this IEnumerable<TSource> source,
    Func<TSource, TKey> keySelector,
    IEqualityComparer<TKey>? comparer)
  • source — the collection (supplied by the extension-method dot).
  • keySelector — how to extract the key from each item.
  • comparer — installed in the resulting dictionary; runs on every later lookup.

7. The shortcut: record

If you want value equality for free, declare a record — the compiler writes Equals, GetHashCode, IEquatable<T>, and the operators for you:

public record Point(int X, int Y);   // equality by X and Y, automatically
Gotcha: the auto-generated equality still uses reference equality for array and collection properties. string[] doesn't compare structurally even in records — you'd still need SequenceEqual or a custom equality method.

8. Checklist for adding equality to a class

  1. Decide: does equality belong on the type (IEquatable<T>) or outside it (IEqualityComparer<T>)?
  2. If on the type:
    • Implement IEquatable<T> and write Equals(T?) — the real logic.
    • Override Equals(object?) — delegate to the typed one.
    • Override GetHashCode() using HashCode.Combine(...) over the same fields you compared.
    • Optional: overload == and != if you want operator-level value equality.
  3. If outside the type: implement IEqualityComparer<T> — pass it into the collection/LINQ call.
  4. For strings as keys, reach for StringComparer.Ordinal[IgnoreCase] first — don't roll your own.
  5. If you don't need a class identity, consider a record instead.
