Chapter 1: Introduction to Unit Testing {#introduction}

What is Unit Testing?

Unit testing is the practice of testing individual units or components of your software in isolation. In .NET, a "unit" typically refers to a single method or function. The goal is to verify that each unit of code performs as designed.

Why Unit Testing Matters

Imagine building a car. You wouldn't wait until the entire vehicle is assembled to test if the engine works. Similarly, unit testing allows you to verify that each piece of your code works correctly before integrating it into the larger system.

Key Benefits:

Early Bug Detection: Catch issues before they become expensive problems

Documentation: Tests serve as living documentation of how your code should behave

Refactoring Confidence: Make changes knowing your tests will catch any breaks

Design Improvement: Writing testable code leads to better architecture

The Testing Pyramid

/\

/ \

/ UI \

/Tests \

/--------\

/Integration\

/ Tests \

/--------------\

/ Unit Tests \

\________________/

Unit tests form the foundation of the testing pyramid. They should be:

Fast: Run in milliseconds

Isolated: No external dependencies

Repeatable: Same result every time

Self-Validating: Pass or fail with no manual interpretation

Chapter 2: Understanding the Fundamentals {#fundamentals}

The AAA Pattern

Every unit test follows the Arrange-Act-Assert (AAA) pattern:

[Test]

public void Calculator_Add_ReturnsSumOfTwoNumbers()

{

// Arrange - Set up the test data and environment

var calculator = new Calculator();

int a = 5;

int b = 3;

// Act - Execute the code being tested

int result = calculator.Add(a, b);

// Assert - Verify the outcome

Assert.AreEqual(8, result);

}

Key Concepts

Test Fixture: A class containing related tests

[TestFixture]

public class CalculatorTests

{

// Test methods go here

}

Test Method: An individual test

[Test]

public void TestMethodName()

{

// Test code

}

Assertions: Statements that verify expected outcomes

Assert.AreEqual(expected, actual);

Assert.IsTrue(condition);

Assert.Throws<ExceptionType>(() => { / code / });

Testing Frameworks in .NET

The .NET ecosystem offers several testing frameworks:

NUnit: Popular, feature-rich, extensive assertion library

xUnit: Modern, used by .NET Core team, parallel execution by default

MSTest: Microsoft's framework, excellent Visual Studio integration

For this guide, we'll primarily use NUnit, but the concepts apply to all frameworks.

Chapter 3: Setting Up Your Testing Environment {#setup}

Step-by-Step Setup Guide

Step 1: Create Your Solution Structure

A well-organized solution structure is crucial. Here's the recommended layout:

MySolution/

├── src/

│ └── MyProject/

│ ├── MyProject.csproj

│ └── Calculator.cs

└── tests/

└── MyProject.Tests/

├── MyProject.Tests.csproj

└── CalculatorTests.cs

💡 Pro Tip: Always separate your test projects from your main code. Use the naming convention [ProjectName].Tests for clarity.

Step 2: Create the Test Project

Using Visual Studio:

Right-click on your solution

Select "Add" → "New Project"

Choose "NUnit Test Project" (or "Unit Test Project" for MSTest)

Name it YourProject.Tests

Using .NET CLI:

Navigate to your solution folder

cd MySolution

Create the test project

dotnet new nunit -n MyProject.Tests -o tests/MyProject.Tests

Add to solution

dotnet sln add tests/MyProject.Tests/MyProject.Tests.csproj

Step 3: Add Project Reference

Your test project needs to reference the project being tested:

Using Visual Studio:

Right-click on the test project

Select "Add" → "Project Reference"

Check the box next to your main project

Using .NET CLI:

cd tests/MyProject.Tests

dotnet add reference ../../src/MyProject/MyProject.csproj

Chapter 4: Writing Your First Unit Test {#first-test}

Creating the Code to Test

Let's start with a simple Calculator class:

// src/MyProject/Calculator.cs

namespace MyProject

{

public class Calculator

{

public int Add(int a, int b)

{

return a + b;

}

public int Subtract(int a, int b)

{

return a - b;

}

public int Divide(int a, int b)

{

if (b == 0)

throw new ArgumentException("Cannot divide by zero");

return a / b;

}

}

}

Writing Your First Test Class

// tests/MyProject.Tests/CalculatorTests.cs

using NUnit.Framework;

using MyProject;

namespace MyProject.Tests

{

[TestFixture]

public class CalculatorTests

{

private Calculator _calculator;

[SetUp]

public void Setup()

{

_calculator = new Calculator();

}

[Test]

public void Add_WhenGivenTwoPositiveNumbers_ReturnsCorrectSum()

{

// Arrange

int a = 5;

int b = 3;

int expected = 8;

// Act

int result = _calculator.Add(a, b);

// Assert

Assert.AreEqual(expected, result);

}

}

}

Understanding Test Attributes

[TestFixture]: Marks a class as containing tests

[TestFixture]

public class MyTests { }

[SetUp]: Runs before each test

[SetUp]

public void Initialize()

{

// Prepare test environment

}

[TearDown]: Runs after each test

[TearDown]

public void Cleanup()

{

// Clean up resources

}

[Test]: Marks a method as a test

[Test]

public void MyTestMethod() { }

Writing Multiple Test Cases

Use [TestCase] for parameterized tests:

[TestCase(5, 3, 8)]

[TestCase(-5, 3, -2)]

[TestCase(0, 0, 0)]

[TestCase(100, -50, 50)]

public void Add_VariousInputs_ReturnsCorrectSum(int a, int b, int expected)

{

// Act

int result = _calculator.Add(a, b);

// Assert

Assert.AreEqual(expected, result);

}

Testing Exceptions

[Test]

public void Divide_WhenDividingByZero_ThrowsArgumentException()

{

// Arrange

int a = 10;

int b = 0;

// Act & Assert

Assert.Throws<ArgumentException>(() => _calculator.Divide(a, b));

}

[Test]

public void Divide_WhenDividingByZero_ThrowsWithCorrectMessage()

{

// Arrange

int a = 10;

int b = 0;

// Act & Assert

var ex = Assert.Throws<ArgumentException>(() => _calculator.Divide(a, b));

Assert.That(ex.Message, Is.EqualTo("Cannot divide by zero"));

}

Chapter 5: Test Organization and Best Practices {#organization}

Naming Conventions

Good test names are crucial for understanding what went wrong when a test fails.

Pattern: MethodName_StateUnderTest_ExpectedBehavior

Examples:

Add_WhenGivenTwoPositiveNumbers_ReturnsCorrectSum()

Divide_WhenDividingByZero_ThrowsArgumentException()

GetUser_WhenUserDoesNotExist_ReturnsNull()

Test Organization Structure

MyProject.Tests/

├── Unit/

│ ├── Services/

│ │ ├── UserServiceTests.cs

│ │ └── OrderServiceTests.cs

│ └── Utilities/

│ └── StringHelperTests.cs

├── Integration/

│ └── DatabaseTests.cs

└── Helpers/

└── TestDataBuilder.cs

The F.I.R.S.T. Principles

Fast: Tests should run quickly (milliseconds) Independent: Tests shouldn't depend on each other Repeatable: Same result every time Self-Validating: Clear pass/fail result Timely: Written just before or after the code

Common Assertions

// Equality

Assert.AreEqual(expected, actual);

Assert.AreNotEqual(notExpected, actual);

// Boolean

Assert.IsTrue(condition);

Assert.IsFalse(condition);

// Null

Assert.IsNull(obj);

Assert.IsNotNull(obj);

// Collections

Assert.Contains(item, collection);

Assert.IsEmpty(collection);

CollectionAssert.AreEqual(expectedList, actualList);

// Strings

StringAssert.Contains(substring, fullString);

StringAssert.StartsWith(prefix, fullString);

// Exceptions

Assert.Throws<ExceptionType>(() => { / code / });

Assert.DoesNotThrow(() => { / code / });

// Fluent Assertions (NUnit 3.x)

Assert.That(actual, Is.EqualTo(expected));

Assert.That(list, Has.Count.EqualTo(3));

Assert.That(text, Does.Contain("substring"));

Fluent Assertions Library

Fluent Assertions is a set of .NET extension methods that allow you to more naturally specify the expected outcome of a TDD or BDD-style unit test. It works with all major testing frameworks (xUnit, NUnit, MSTest).

Installation

dotnet add package FluentAssertions

Basic Usage

using FluentAssertions;

using Xunit;

public class CalculatorTests

{

[Fact]

public void Add_WhenGivenTwoNumbers_ReturnsSum()

{

// Arrange

var calculator = new Calculator();

// Act

var result = calculator.Add(5, 3);

// Assert - Fluent style

result.Should().Be(8);

}

}

Comparison: Traditional vs Fluent Assertions

// Traditional xUnit

Assert.Equal(8, result);

Assert.True(result > 0);

Assert.Contains("Hello", message);

Assert.Throws<ArgumentException>(() => calculator.Divide(5, 0));

// Fluent Assertions

result.Should().Be(8);

result.Should().BePositive();

message.Should().Contain("Hello");

calculator.Invoking(c => c.Divide(5, 0))

.Should().Throw<ArgumentException>();

Common Fluent Assertions

// Numbers

result.Should().Be(8);

result.Should().BeGreaterThan(5);

result.Should().BeInRange(5, 10);

result.Should().BeApproximately(8.0, 0.1);

// Strings

name.Should().Be("John");

name.Should().StartWith("J");

name.Should().EndWith("hn");

name.Should().Contain("oh");

name.Should().HaveLength(4);

name.Should().BeNullOrWhiteSpace();

// Booleans

isValid.Should().BeTrue();

isValid.Should().BeFalse();

// Collections

list.Should().HaveCount(3);

list.Should().Contain(item);

list.Should().ContainSingle();

list.Should().BeInAscendingOrder();

list.Should().BeEquivalentTo(new[] { 1, 2, 3 });

// Objects

person.Should().BeEquivalentTo(expectedPerson);

person.Should().BeOfType<Employee>();

person.Name.Should().NotBeNull();

// Exceptions

action.Should().Throw<InvalidOperationException>()

.WithMessage("Operation not allowed");

// Async

await asyncFunc.Should().CompleteWithinAsync(TimeSpan.FromSeconds(2));

// Multiple assertions on same object

result.Should()

.BePositive()

.And.BeLessThan(100)

.And.Be(42);

Why Use Fluent Assertions?

Readability: Tests read like natural language

Better Error Messages:

// Traditional: Expected 8 but was 7// Fluent: Expected result to be 8, but found 7

Discoverable API: IntelliSense guides you to available assertions

Chainable: Multiple assertions can be chained together

Framework Agnostic: Works with xUnit, NUnit, MSTest

Advanced Fluent Assertions

// Custom messages

result.Should().Be(8, "because we added 5 and 3");

// Collection comparisons

var actual = new[] { 1, 2, 3 };

var expected = new[] { 3, 2, 1 };

actual.Should().BeEquivalentTo(expected); // Order doesn't matter

// Object graph comparison

var actualPerson = new Person { Name = "John", Age = 30 };

var expectedPerson = new Person { Name = "John", Age = 30 };

actualPerson.Should().BeEquivalentTo(expectedPerson);

// Execution time assertions

Action someAction = () => Thread.Sleep(100);

someAction.ExecutionTime().Should().BeLessThan(TimeSpan.FromMilliseconds(200));

// Event monitoring

var subject = new Subject();

using var monitor = subject.Monitor();

subject.RaiseEvent();

monitor.Should().Raise("SomeEvent");

Chapter 6: Advanced Testing Techniques {#advanced}

Data-Driven Tests

Using TestCase:

[TestCase(1, 1, 2)]

[TestCase(2, 3, 5)]

[TestCase(-1, 1, 0)]

public void Add_MultipleScenarios_ReturnsCorrectSum(int a, int b, int expected)

{

var result = _calculator.Add(a, b);

Assert.AreEqual(expected, result);

}

Using TestCaseSource:

public class CalculatorTests

{

private static IEnumerable<TestCaseData> AddTestCases()

{

yield return new TestCaseData(1, 1, 2).SetName("PositiveNumbers");

yield return new TestCaseData(-1, -1, -2).SetName("NegativeNumbers");

yield return new TestCaseData(0, 0, 0).SetName("Zeros");

}

[TestCaseSource(nameof(AddTestCases))]

public void Add_VariousInputs_ReturnsCorrectSum(int a, int b, int expected)

{

var result = _calculator.Add(a, b);

Assert.AreEqual(expected, result);

}

}

Testing Async Methods

public class AsyncService

{

public async Task<string> GetDataAsync()

{

await Task.Delay(100);

return "Data";

}

}

[Test]

public async Task GetDataAsync_WhenCalled_ReturnsData()

{

// Arrange

var service = new AsyncService();

// Act

var result = await service.GetDataAsync();

// Assert

Assert.AreEqual("Data", result);

}

Theory Tests (xUnit style in NUnit)

[Theory]

[TestCase(2, true)]

[TestCase(3, false)]

[TestCase(4, true)]

public void IsEven_VariousNumbers_ReturnsCorrectResult(int number, bool expected)

{

var result = MathHelper.IsEven(number);

Assert.AreEqual(expected, result);

}

Chapter 7: Mocking and Dependencies {#mocking}

Introduction to Mocking

When testing units in isolation, you need to replace dependencies with test doubles. The most popular mocking framework for .NET is Moq.

Installing Moq

<PackageReference Include="Moq" Version="4.18.4" />

Basic Mocking Example

Consider a service with a dependency:

public interface IEmailService

{

bool SendEmail(string to, string subject, string body);

}

public class UserService

{

private readonly IEmailService _emailService;

public UserService(IEmailService emailService)

{

_emailService = emailService;

}

public bool RegisterUser(string email, string name)

{

// Registration logic...

return _emailService.SendEmail(

email,

"Welcome!",

$"Hello {name}, welcome to our service!");

}

}

Testing with a mock:

[Test]

public void RegisterUser_WhenCalled_SendsWelcomeEmail()

{

// Arrange

var mockEmailService = new Mock<IEmailService>();

mockEmailService

.Setup(x => x.SendEmail(It.IsAny<string>(), It.IsAny<string>(), It.IsAny<string>()))

.Returns(true);

var userService = new UserService(mockEmailService.Object);

// Act

var result = userService.RegisterUser("test@email.com", "John");

// Assert

Assert.IsTrue(result);

mockEmailService.Verify(x => x.SendEmail(

"test@email.com",

"Welcome!",

It.Is<string>(body => body.Contains("John"))),

Times.Once);

}

Mock Setup Patterns

// Return specific value

mock.Setup(x => x.Method()).Returns(value);

// Return different values on successive calls

mock.SetupSequence(x => x.Method())

.Returns(value1)

.Returns(value2);

// Throw exception

mock.Setup(x => x.Method()).Throws<InvalidOperationException>();

// Match specific arguments

mock.Setup(x => x.Method(It.Is<int>(i => i > 0))).Returns(true);

// Callback

mock.Setup(x => x.Method(It.IsAny<string>()))

.Callback<string>(s => Console.WriteLine($"Called with: {s}"));

// Async methods

mock.Setup(x => x.AsyncMethod()).ReturnsAsync(value);

Verification Patterns

// Verify method was called

mock.Verify(x => x.Method(), Times.Once);

mock.Verify(x => x.Method(), Times.Never);

mock.Verify(x => x.Method(), Times.AtLeastOnce);

mock.Verify(x => x.Method(), Times.Exactly(3));

// Verify with specific arguments

mock.Verify(x => x.Method("specific value"));

// Verify property was set

mock.VerifySet(x => x.Property = It.IsAny<string>());

Chapter 9: Test Coverage and Metrics {#coverage}

Understanding Code Coverage

Code coverage measures how much of your code is executed during tests. It's a useful metric but shouldn't be the only goal.

Generating Coverage Reports

Using dotnet CLI with Coverlet:

Install coverlet tool

dotnet tool install --global coverlet.console

Run tests with coverage

dotnet test --collect:"XPlat Code Coverage"

Generate HTML report with ReportGenerator

dotnet tool install --global dotnet-reportgenerator-globaltool

reportgenerator -reports:coverage.cobertura.xml -targetdir:coveragereport -reporttypes:Html

Coverage Metrics

Line Coverage: Percentage of lines executed

Branch Coverage: Percentage of decision points tested

Method Coverage: Percentage of methods called

Best Practices for Coverage

Good Coverage Targets:

Unit tests: 80-90%

Critical business logic: 95%+

UI/Controllers: 60-70%

Coverage Anti-patterns to Avoid:

// Bad: Testing just for coverage

[Test]

public void Constructor_CreatesInstance()

{

var obj = new MyClass();

Assert.IsNotNull(obj); // Not meaningful

}

// Good: Testing behavior

[Test]

public void Constructor_WithNullDependency_ThrowsArgumentNullException()

{

Assert.Throws<ArgumentNullException>(() => new MyClass(null));

}

Chapter 10: Common Issues and Troubleshooting {#troubleshooting}

Issue 1: Tests Not Discovered

Symptoms: Tests don't appear in Test Explorer

Solutions:

Ensure test project references Microsoft.NET.Test.Sdk

Clean and rebuild solution

Check test method has [Test] attribute

Verify test class has [TestFixture] attribute (NUnit)

Ensure test methods are public and not static

Issue 2: "Could not load file or assembly"

Symptoms: Tests fail with assembly loading errors

Solutions:

<!-- Add to test project .csproj -->

<PropertyGroup>

<CopyLocalLockFileAssemblies>true</CopyLocalLockFileAssemblies>

</PropertyGroup>

Issue 3: Tests Pass Individually but Fail Together

Symptoms: Tests pass when run alone but fail in groups

Common Causes:

Shared state between tests

Static variables not reset

Database/file system modifications

Solution:

[SetUp]

public void Setup()

{

// Reset all state

StaticClass.Reset();

_database.Clear();

}

[TearDown]

public void Teardown()

{

// Clean up resources

_connection?.Dispose();

}

Issue 4: Flaky Tests

Symptoms: Tests randomly pass or fail

Common Causes:

Time-dependent logic

Random values

External dependencies

Race conditions

Solutions:

// Bad: Time-dependent

public bool IsExpired()

{

return ExpiryDate < DateTime.Now;

}

// Good: Inject time provider

public bool IsExpired(IDateTimeProvider dateTimeProvider)

{

return ExpiryDate < dateTimeProvider.Now;

}

Issue 5: Slow Tests

Symptoms: Test suite takes too long to run

Solutions:

Mock external dependencies

Use in-memory databases for integration tests

Parallelize test execution

Identify and optimize slow tests

// Enable parallel execution in NUnit

[assembly: Parallelizable(ParallelScope.Fixtures)]

// Or per fixture

[TestFixture]

[Parallelizable(ParallelScope.All)]

public class FastTests { }

Final Thoughts

Unit testing is a skill that improves with practice. Start small, test the critical paths first, and gradually expand your test coverage. Remember that the goal isn't 100% coverage, but rather confident, maintainable code.

Key Takeaways:

Write tests as you code, not after

Keep tests simple and focused

Use descriptive names

Mock external dependencies

Maintain your tests like production code

Measure coverage but don't obsess over it
