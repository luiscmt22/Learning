Stampede protection — one Task, many waiters

A practical pattern for de-duplicating expensive async work when many threads hit the same cold cache key at once. Companion to 22-ConcurrentDictionary, 30-SemaphoreSlim, and 20-IMemoryCache. Born from the BioBraga “Primavera stock” refactor.

1 — Why this exists: the cache stampede

A “cache stampede” (sometimes called a thundering herd) is what happens when many threads hit the same cold cache key at the same time. Each one finds nothing in the cache, each one starts the expensive fetch, each one writes the same result back. The cache exists to spare the expensive resource — but at the worst possible moment (cold start, traffic burst, after eviction), it briefly stops doing its job.

Concrete scenario from BioBraga. Five users open the same article details page within 10 ms. Each call goes through a decorator that asks Primavera for the article’s stock breakdown. Without protection: five SOAP calls in flight at once, ~10 seconds of Primavera CPU wasted on identical work, five cache writes overwriting the same key. With protection: one SOAP call, four waiters, identical result delivered to all five.

The fix is not more caching. It’s asking the question once and sharing the answer with everyone who wanted it.

2 — The mental model: a whiteboard and a slip of paper

Picture a small office with one whiteboard. The whiteboard has a column called “currently fetching”. When you need data, you check the whiteboard first.

                  WHITEBOARD (the dictionary)
   +-------------------+---------------------------+
   |   article code    |   slip of paper (Lazy)    |
   +-------------------+---------------------------+
   |     ABC123        |    [answer arrives here]  |
   +-------------------+---------------------------+

       ^
       |
   You arrive looking for ABC123.

   Case A:  Nothing on the board for ABC123.
            You pin a fresh slip, you go fetch the answer yourself.

   Case B:  Somebody else already pinned a slip.
            You DON'T go fetch. You stare at THEIR slip until it fills in.

Three properties make this work:

  • The act of checking and pinning happens in one atomic step — otherwise two people could both think the board was empty.
  • The slip is the same object for everyone — when the runner fills it in, every waiter sees the same answer.
  • Once the answer is filled in, the slip is removed from the whiteboard — otherwise the board fills with stale slips.

That’s the whole pattern. The rest of this document is just C# names for these three properties.

3 — Building it from scratch

Round 1 — no protection

public async Task<StockRows> GetAsync(string code)
{
    if (_cache.TryGet(code, out var hit))
        return hit;

    var fresh = await _primavera.FetchAsync(code);
    _cache.Set(code, fresh);
    return fresh;
}

Correct in single-threaded land. Catastrophic under load. Every concurrent caller that hits the same cold key fires its own FetchAsync.

Round 2 — obvious-but-wrong lock

private readonly object _lock = new();

public async Task<StockRows> GetAsync(string code)
{
    lock (_lock) // ← won't compile across await anyway
    {
        if (_cache.TryGet(code, out var hit)) return hit;
        var fresh = await _primavera.FetchAsync(code); // ❌ illegal
        ...
    }
}

A C# lock block cannot contain await. Even if it could, this would serialise every caller for every code — user A asking for ABC blocks user B asking for XYZ, which is absurd.

Round 3 — per-key gate with SemaphoreSlim

private readonly ConcurrentDictionary<string, SemaphoreSlim> _gates = new();

public async Task<StockRows> GetAsync(string code)
{
    if (_cache.TryGet(code, out var hit)) return hit;

    var gate = _gates.GetOrAdd(code, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync();
    try
    {
        if (_cache.TryGet(code, out var cached)) return cached;
        var fresh = await _primavera.FetchAsync(code);
        _cache.Set(code, fresh);
        return fresh;
    }
    finally { gate.Release(); }
}

This works. It’s the textbook double-checked-locking pattern, adapted for async. But read it carefully: every waiter ends up running the inner logic — they re-check the cache, find it populated, and return. The result is shared through the cache. That’s fine, but a bit indirect.

Round 4 — share the Task itself

private readonly ConcurrentDictionary<string, Lazy<Task<StockRows>>> _inFlight = new();

public async Task<StockRows> GetAsync(string code)
{
    if (_cache.TryGet(code, out var hit)) return hit;

    var lazy = _inFlight.GetOrAdd(code, c =>
        new Lazy<Task<StockRows>>(async () =>
        {
            try
            {
                var fresh = await _primavera.FetchAsync(c);
                _cache.Set(c, fresh);
                return fresh;
            }
            finally { _inFlight.TryRemove(c, out _); }
        }));

    return await lazy.Value;
}

This is the final shape. Three small lines of clever do the work of fifteen lines of lock-juggling. The rest of this page explains why.

4 — Why Lazy<Task<T>> works

Lazy<T> is the standard library’s answer to “compute this once, the first time someone asks”. You hand it a factory. The first thread that reads .Value runs the factory. Every subsequent thread reads the already-computed value. The first-time-only behaviour is thread-safe by default (LazyThreadSafetyMode.ExecutionAndPublication) — you don’t need to wrap it in anything.

Now substitute T = Task<StockRows>. The “value” the Lazy holds is no longer a finished computation — it’s a promise of one, in the form of a Task. The first thread runs the factory; the factory returns a Task; everybody else reads .Value and gets the same Task. They each await it and each wake up with the same result when it completes.

The two-jobs trick. Lazy<Task<T>> is doing two jobs at once: gating who runs the factory (only one), and sharing the result (everyone awaits the same Task). Most other concurrency primitives do one of these — not both.

Failure semantics

If the factory’s Task faults, every waiter sees the same exception. That’s usually what you want — if Primavera was offline for the runner, it was offline for everyone. It is NOT what you want if you expected each waiter to retry. We’ll come back to that under pitfalls.

5 — The ConcurrentDictionary guarantee

The other half of the pattern is GetOrAdd(key, factory). The contract:

  • If the key is absent, the factory runs and the result is stored.
  • If the key is present, the factory does not run; the existing value is returned.
  • If two threads call GetOrAdd with the same absent key at the exact same instant, both factories may run but only one return value wins. Each caller receives the winning value.
Wait — both factories may run? Yes. GetOrAdd is “atomic in the answer”, not “atomic in the factory’s side-effects”. This is why we wrap the heavy work in Lazy<Task<T>>. Constructing a Lazy is cheap and side-effect-free. The expensive bit (calling Primavera) lives inside the Lazy’s factory, which the Lazy itself guarantees runs only once.

So the layered guarantee is: ConcurrentDictionary may run two Lazy constructors, but Lazy guarantees only one Primavera call. Belt and suspenders, each cheap.

6 — The cleanup imperative

The finally { _inFlight.TryRemove(c, out _); } in the factory is not optional. Without it, the in-flight dictionary becomes a permanent cache of completed Tasks — a memory leak that grows with every distinct article code ever requested.

With the cleanup, the dictionary is just a transient — entries exist only while a fetch is in flight. The cache is the long-term store. The dictionary is the short-term coordination layer.

Mental shortcut. Think of _inFlight as a list of work currently happening, not a list of work that has happened. The finally is what keeps that mental model true.

7 — When to reach for SemaphoreSlim instead

PropertyLazy<Task<T>> mapSemaphoreSlim map
Lines of code~8~14 (double-check needed)
How waiters get the resultAwait the same TaskRe-read the cache after acquiring the gate
If first call failsAll waiters see the same exceptionEach waiter re-tries the fetch independently
FamiliarityLess common idiomTextbook double-checked locking
Memory cleanupTryRemove in finallyManual; or accept leaked semaphores
Reuse for other goalsPurpose-builtSame primitive can rate-limit, gate, throttle

Use Lazy when you want “fetch once, share result, all waiters see the same outcome”. This is the right default for cache-on-miss patterns.

Use SemaphoreSlim when (a) you need each waiter to make its own independent attempt if the first fails, (b) the gate has a wider purpose like rate limiting, or (c) the team is more comfortable with a familiar idiom and the extra lines aren’t a cost.

8 — Three places this fits in our apps

  1. Caching decorator around an expensive read. The BioBraga Primavera stock decorator is the textbook fit. Any time you have a singleton/long-lived component caching the result of an async call, this pattern earns its keep.
  2. One-shot loaders triggered by many UI elements. Imagine ten dashboard widgets each loading “current user” on initial render. Wrap the loader in Lazy<Task<User>> at the service level — one HTTP call, ten widgets satisfied.
  3. Per-id resolution work. Resolving a customer name from a customer id, fetching geofence polygons for a site id, loading a tenant config for a tenant id. Any idempotent per-key async work can be wrapped this way.
Where it does NOT fit. Per-request state. Per-user UI state. Anything where the “same key, same answer” assumption is wrong. If two callers asking the same question would legitimately get different answers (because the answer depends on who is asking), the pattern is the wrong shape.

9 — Pitfalls & gotchas

Pitfall 1 — forgetting TryRemove

The dictionary grows forever. Process memory climbs. You’ll find it because the GC starts gnawing at the working set, not because anything crashes. Add the finally.

Pitfall 2 — faulted Task poisons the cache?

If _primavera.FetchAsync throws, the Task becomes faulted. With cleanup in place, the entry is removed and the next call after the exception starts fresh. Without cleanup, every future caller sees the same exception forever. Make sure your finally runs even on exception — standard try/finally does this, but if you ever refactor to ContinueWith be careful.

Pitfall 3 — double work in batched calls

If your API has both single-key and multi-key entry points, you have to think about how a batch reads the in-flight map. The BioBraga decorator partitions a batch into three buckets: cached / in-flight / cold, and only sends the cold ones to Primavera. Two simultaneous batches with overlapping cold keys can still double-fetch — an acceptable race given the cache TTL closes the window after the first call.

Pitfall 4 — Lazy<T> default mode is what you want

If you ever see new Lazy<...>(factory, LazyThreadSafetyMode.None) in concurrent code, that’s a footgun. PublicationOnly is also wrong here (it lets multiple factory invocations race). The parameterless new Lazy<T>(factory) defaults to ExecutionAndPublication which is exactly what you want.

Pitfall 5 — this is in-process only

If you ever scale out to multiple app instances, the in-flight map is per-process. Two app servers will each run their own “single” fetch. You’d need a distributed coordination layer (Redis lock, Postgres advisory lock) at that point. For single-instance Blazor Server apps, this pattern is sufficient.

Recap in one paragraph

To stop a cache stampede, you need one fetch and many shared results. ConcurrentDictionary<TKey, Lazy<Task<TValue>>> gives you both: the dictionary picks one winner per key, the Lazy guarantees the winner runs the factory exactly once, the Task is the shared result that every waiter awaits. A finally { TryRemove } keeps the dictionary as a transient. The pattern is small, idiomatic, and reusable anywhere you have idempotent per-key async work in a long-lived service.
