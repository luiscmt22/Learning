Chapter 1: Understanding Base Classes

1.1 The Problem: Code Duplication

Look at typical entity classes without inheritance:

             public class Board
             {

                    public int Id { get; set; }
                    public DateTime CreatedAt { get; set; }
                    public DateTime? UpdatedAt { get; set; }
                    // ... other properties
             }

             public class TaskItem
             {

                    public int Id { get; set; }
                    public DateTime CreatedAt { get; set; }
                    public DateTime? UpdatedAt { get; set; }
                    // ... other properties
             }

             public class Tag
             {

                    public int Id { get; set; }
                    // No audit fields here - inconsistent!
             }

Problems with this approach:

      • Code duplication - We repeat Id, CreatedAt, UpdatedAt in every entity
      • Inconsistency - Some entities have audit fields, some don't
      • Maintenance nightmare - Adding CreatedById requires modifying every entity

1.2 The Solution: Inheritance

We create base classes that contain common properties:

             // Level 1: Every entity has an ID
             public abstract class BaseEntity
             {

                    public int Id { get; set; }
             }

             // Level 2: Entities that track who created/modified them
             public abstract class BaseAuditableEntity : BaseEntity
             {

                    public DateTime CreatedAt { get; set; }
                    public int? CreatedById { get; set; }
                    public DateTime? UpdatedAt { get; set; }
                    public int? UpdatedById { get; set; }
             }

Now entities become cleaner:

             public class Board : BaseAuditableEntity
             {

                    public string Name { get; set; }
                    public string? Description { get; set; }
                    public bool IsArchived { get; set; }
                    // Id, CreatedAt, CreatedById, etc. are inherited!
             }


--- PAGE BREAK ---

1.3 Why abstract?

The abstract keyword means you cannot create an instance of the class directly. It only exists to be
inherited by other classes.

             // This won't compile
             var entity = new BaseEntity();

             // This works
             var board = new Board();

Why? A "BaseEntity" by itself is meaningless. It's not a board, not a task, not a user. It's just a template for
other classes.

1.4 Why Two Levels?

Not every entity needs audit fields:
Level 1 - BaseEntity (just Id) - For simple entities like:

      • Role - System-defined, no need to track who created them
      • Permission - Same as roles
      • Join tables like TaskTag - Just relationships, not independent entities
Level 2 - BaseAuditableEntity (Id + audit fields) - For business entities:
      • Board, TaskItem, User - Need to know who created/modified them

1.5 The DRY Principle

DRY = Don't Repeat Yourself

Before:    Id, CreatedAt, UpdatedAt, Name, Description, IsArchived
Board:     Id, CreatedAt, UpdatedAt, Title, Description, Priority
TaskItem:  Id, CreatedAt, UpdatedAt, Name, Color
Tag:       Id, CreatedAt, UpdatedAt, Email, UserName, PasswordHash
User:

After:

BaseAuditableEntity: Id, CreatedAt, CreatedById, UpdatedAt, UpdatedById

sss Board:                   Name, Description, IsArchived

sss TaskItem: Title, Description, Priority

sss Tag:                     Name, Color

sss User:                    Email, UserName, PasswordHash

1.6 Real-World Benefit: Adding Features

Imagine adding soft delete (mark as deleted instead of actually deleting):

Without base classes: Modify 10+ entity files

With base classes:

             public abstract class BaseAuditableEntity : BaseEntity
             {

                    public DateTime CreatedAt { get; set; }
                    public int? CreatedById { get; set; }
                    public DateTime? UpdatedAt { get; set; }
                    public int? UpdatedById { get; set; }

                    // NEW: Soft delete - one change, all entities get the feature

This is the power of inheritance: One change affects all inheriting classes.

Chapter 2: Entity Framework Configurations

2.1 Where Do We Define Database Rules?

EF Core needs to know: Which properties are required? What's the maximum length? How are entities
related? What columns should be indexed? There are three approaches:

Approach 1: Data Annotations (Simple but Limited)

             public class User
             {

                    public int Id { get; set; }

                    [Required]
                    [MaxLength(256)]
                    [EmailAddress]
                    public string Email { get; set; }
             }

Cons: Mixes domain model with database concerns, limited capabilities, clutters entity class.

Approach 2: Fluent API in OnModelCreating (Messy)

             protected override void OnModelCreating(ModelBuilder modelBuilder)
             {

                    modelBuilder.Entity<User>(entity =>
                    {

                            entity.HasKey(e => e.Id);
                            entity.Property(e => e.Email).IsRequired().HasMaxLength(256);
                            // ... 20 more lines per entity
                    });
                    // 10 more entities = 500+ lines!
             }

Cons: OnModelCreating becomes huge, hard to find configurations.

Approach 3: Separate Configuration Classes (Recommended)

             // Data/Configurations/Identity/UserConfiguration.cs
             public class UserConfiguration : IEntityTypeConfiguration<User>
             {

                    public void Configure(EntityTypeBuilder<User> builder)
                    {

                            builder.HasKey(e => e.Id);

                            builder.Property(e => e.Email)
                                   .IsRequired()
                                   .HasMaxLength(256);

                            builder.HasIndex(e => e.Email).IsUnique();

                            builder.HasMany(e => e.UserRoles)
                                   .WithOne(e => e.User)
                                   .HasForeignKey(e => e.UserId)
                                   .OnDelete(DeleteBehavior.Cascade);

                    }
             }

Then in DbContext:

             protected override void OnModelCreating(ModelBuilder modelBuilder)
             {

                    // One line loads ALL configurations from the assembly
                    modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);

}

2.2 Understanding the Fluent API

Primary Keys

             // Simple primary key
             builder.HasKey(e => e.Id);

// Composite primary key (for join tables)
builder.HasKey(e => new { e.UserId, e.RoleId });

Property Configuration

builder.Property(e => e.Email)

   .IsRequired()                         // NOT NULL in database

   .HasMaxLength(256)                    // NVARCHAR(256)

   .HasColumnName("email") // Override column name

   .HasDefaultValue(""); // Default value

Indexes

             // Simple index
             builder.HasIndex(e => e.Email);

// Unique index (no duplicates allowed)
builder.HasIndex(e => e.Email).IsUnique();

// Composite index
builder.HasIndex(e => new { e.EntityType, e.EntityId });

Relationships

// One-to-Many: One User has Many UserRoles

builder.HasMany(e => e.UserRoles)             // User has many UserRoles

   .WithOne(e => e.User)                      // Each UserRole has one User

   .HasForeignKey(e => e.UserId)              // Foreign key column

   .OnDelete(DeleteBehavior.Cascade); // Delete UserRoles when User deleted

2.3 Delete Behaviors

   Behavior             Use Case
   Cascade              UserRoles when User is deleted
   Restrict             Can't delete Role if users have it
   SetNull              AuditLog.UserId when User deleted (keep logs)
   NoAction             Database default behavior

             builder.Property(e => e.Name);

             // GOOD - explicit length
             builder.Property(e => e.Name).HasMaxLength(100);

             // BAD - deleting a role deletes all users with that role
             builder.HasMany(e => e.UserRoles)

       .WithOne(e => e.Role)
       .OnDelete(DeleteBehavior.Cascade);

// GOOD - can't delete role if users have it

       .WithOne(e => e.Role)
       .OnDelete(DeleteBehavior.Restrict);

3.1 The Problem: How Do Services Report Errors?

             {

                    // What if email already exists?
                    // What if password is too weak?
                    // What if database fails?

                    var user = new User { Email = dto.Email };
                    await _context.Users.AddAsync(user);
                    await _context.SaveChangesAsync();
                    return user;
             }

3.2 Bad Approaches

Return Null

             public async Task<User?> CreateUserAsync(CreateUserDto dto)
             {

                    if (await EmailExists(dto.Email))
                            return null; // Why null? Email? Validation? Database?

             }

Problem: Caller doesn't know why it failed.

Throw Exceptions

             public async Task<User> CreateUserAsync(CreateUserDto dto)
             {

                    if (await EmailExists(dto.Email))
                            throw new Exception("Email already exists");

             }

Problems: Exceptions are for exceptional cases, not business logic. They're expensive and force try/catch
everywhere.

3.3 The Solution: ServiceResult Pattern

             public class ServiceResult<T>
             {

                    public T? Data { get; private set; }

                    public static ServiceResult<T> Ok(T data, string? message = null)
                    {

                            return new ServiceResult<T>
                            {

                                   Success = true,
                                   Data = data,
                                   Message = message
                            };
                    }

                    public static ServiceResult<T> Fail(string error)
                    {

                            return new ServiceResult<T>

                            {
                                   Success = false,
                                   Message = error,
                                   Errors = [error]

                            };
                    }

                    public static ServiceResult<T> Fail(List<string> errors)
                    {

                            return new ServiceResult<T>
                            {

                                   Success = false,
                                   Message = errors.FirstOrDefault(),
                                   Errors = errors
                            };
                    }
             }

3.4 Using ServiceResult in Services

             public async Task<ServiceResult<UserDto>> CreateUserAsync(CreateUserDto dto)
             {

                    // Validation
                    if (await EmailExistsAsync(dto.Email))

                            return ServiceResult<UserDto>.Fail("Email already exists");

                    var (isStrong, message) = _passwordService.ValidateStrength(dto.Password);
                    if (!isStrong)

                            return ServiceResult<UserDto>.Fail(message);

                    // Create user
                    var user = new User
                    {

                            Email = dto.Email,
                            UserName = dto.UserName,
                            PasswordHash = _passwordService.Hash(dto.Password)
                    };

                    await _context.Users.AddAsync(user);
                    await _context.SaveChangesAsync();

                    // Success
                    return ServiceResult<UserDto>.Ok(MapToDto(user), "User created successfully");
             }

Chapter 4: The Adapter Pattern & Model Agnostic
Design

4.1 The Problem: Tight Coupling

Imagine you're building an LMS (Learning Management System). You need to track which users are
enrolled in courses:

             public class EnrollmentService
             {

                    public async Task EnrollUserAsync(User user, int courseId)
                    {

                            var enrollment = new Enrollment
                            {

                                   UserId = user.Id,
                                   UserEmail = user.Email, // Directly accessing User properties
                                   UserName = user.UserName,
                                   CourseId = courseId
                            };
                    }
             }

Problems with this approach:

      • LMS is tightly coupled to the User class
      • Want to use LMS with employees from another system? Rewrite everything.
      • If User changes? LMS breaks.
      • Want to extract LMS as standalone project? Can't - it depends on User.

4.2 Real-World Analogy: The Power Plug Converter

When you travel to Europe from the US, your phone charger won't fit the wall outlets. Different shapes,
different voltages. The solution? A power adapter (converter) that translates between two incompatible
interfaces.

ssssssssssssssss  ssssssssssssssss  ssssssssssssssss

s US Charger s ssss s Adapter s ssss s EU Outlet s

s (2 prongs) s    s (converter) s  s (2 round) s

ssssssssssssssss  ssssssssssssssss  ssssssssssssssss

4.3 The Adapter Pattern in Code

Step 1: Define What You Need (The Interface)

Instead of depending on User directly, the LMS defines what it needs from a learner:

             // Services/LMS/Abstractions/ILmsLearner.cs
             public interface ILmsLearner
             {

                    int Id { get; }
                    string Name { get; }
                    string Email { get; }
                    string? AvatarUrl { get; }
             }

This is the "universal plug" - any user system can implement this.

Step 2: Create the Adapter (The Converter)

Create a class that adapts your actual User to the ILmsLearner interface:

// Services/LMS/Adapters/SkillCanvasLearnerAdapter.cs
public class SkillCanvasLearnerAdapter : ILmsLearner
{

       private readonly UserDto _user;

   public SkillCanvasLearnerAdapter(UserDto user)
   {

          _user = user;
   }

   // Adapt User properties to ILmsLearner interface

   public int Id => _user.Id;

   public string Name => _user.UserName;        // UserName -> Name

   public string Email => _user.Email;

   public string? AvatarUrl => null;            // User doesn't have avatar

}

Step 3: Create a Provider (The Factory)

A provider fetches and adapts users on demand:

public class SkillCanvasLearnerProvider : ILmsLearnerProvider
{

       private readonly IUserService _userService;
       private readonly IAuthenticationService _authService;

   public async Task<ILmsLearner?> GetLearnerAsync(int userId)
   {

          var result = await _userService.GetByIdAsync(userId);
          if (!result.Success || result.Data == null)

                 return null;

          return new SkillCanvasLearnerAdapter(result.Data);
   }

   public async Task<ILmsLearner?> GetCurrentLearnerAsync()
   {

          var session = await _authService.GetCurrentSessionAsync();
          if (session?.User == null)

                 return null;

              return new SkillCanvasLearnerAdapter(session.User);
       }
}

4.4 Why "Model Agnostic"?

Model Agnostic means the LMS doesn't care about your specific models. It works with any user system
that provides an adapter.

              Scenario                           Solution
              Today: SkillCanvas with User       SkillCanvasLearnerAdapter
              Tomorrow: HR System with Employee  EmployeeLearnerAdapter
              Future: Standalone with AppUser    StandaloneUserAdapter
Same LMS code, different adapters.

4.5 Benefits

Benefit                Explanation
Decoupling             LMS doesn't depend on specific user implementation
Reusability            Extract LMS as separate project anytime
Testability            Mock ILmsLearnerProvider in tests
Flexibility            Switch user systems without changing LMS
Single Responsibility  Adapter handles only translation

4.6 When to Use the Adapter Pattern

Use it when:

      • You want decoupled modules that can be extracted later
      • You need to integrate with multiple user systems
      • You want testable code with mockable dependencies
      • You're building reusable libraries or modules
Don't use it for:

      • Simple internal services that won't be reused
      • When tight coupling is acceptable (small projects)

Chapter 5: Bulk Operations with Entity Framework
Core

5.1 The Problem: Why Bulk Operations?

When importing large datasets, traditional Entity Framework approaches become painfully slow:

             // Inserting 1000 articles the "normal" way
             foreach (var artigo in artigos)
             {

                    context.CrmArtigos.Add(artigo);
                    await context.SaveChangesAsync(); // 1000 round trips to database!
             }

Each SaveChangesAsync() generates: a network round trip, transaction overhead, identity column
retrieval, and change tracking updates. For 1000 records, that's 1000 round trips!

5.2 Approach Comparison

Approach 1: Individual SaveChanges (Slow)

             // Total time for 100 articles with 4 phases each: ~30 seconds
             foreach (var row in excelRows)
             {

                    var artigo = CreateArtigo(row);
                    context.CrmArtigos.Add(artigo);
                    await context.SaveChangesAsync(); // Round trip #1

                    foreach (var phase in row.Phases)
                    {

                            var faseArtigo = CreateFaseArtigo(phase, artigo.Id);
                            context.CrmFaseArtigos.Add(faseArtigo);
                            await context.SaveChangesAsync(); // Round trip #2, #3, #4...
                    }
             }

Approach 2: AddRange + Single SaveChanges (Better)

             // Add all at once, save once
             var artigos = excelRows.Select(r => CreateArtigo(r)).ToList();
             context.CrmArtigos.AddRange(artigos);
             await context.SaveChangesAsync(); // Single round trip!

Cons: Still generates individual INSERT statements. Can't get IDs until SaveChanges completes.

Approach 3: EFCore.BulkExtensions (Our Approach)

             // NuGet: EFCore.BulkExtensions
             using EFCore.BulkExtensions;

             var bulkConfig = new BulkConfig
             {

                    PreserveInsertOrder = true,
                    SetOutputIdentity = true // KEY: Gets IDs back after insert!
             };

             await context.BulkInsertAsync(artigos, bulkConfig);
             // Now artigos[0].Id, artigos[1].Id, etc. are populated!

5.3 Key Concepts


--- PAGE BREAK ---

SetOutputIdentity = true

This is the magic that retrieves IDs after bulk insert:

var bulkConfig = new BulkConfig
{

       SetOutputIdentity = true // Without this, IDs remain 0!
};

await context.BulkInsertAsync(artigos, bulkConfig);
Console.WriteLine(artigos[0].Id); // 12345 (actual ID from database)

PreserveInsertOrder = true

Ensures entities maintain their order, so you can correlate back to source data:

var bulkConfig = new BulkConfig     // artigos[0] stays at index 0
{

       PreserveInsertOrder = true,
       SetOutputIdentity = true
};

await context.BulkInsertAsync(artigos, bulkConfig);

// Now artigos[i] corresponds to excelRows[i]
for (int i = 0; i < artigos.Count; i++)
{

       var ficha = CreateFicha(excelRows[i], artigos[i].Id);
}

5.4 Pattern for Dependent Objects

When you have parent-child relationships, follow this order:

             // Step 1: Insert parents, get IDs
             var bulkConfig = new BulkConfig
             {

                    PreserveInsertOrder = true,
                    SetOutputIdentity = true
             };
             await context.BulkInsertAsync(artigos, bulkConfig);
             // artigos now have IDs!

             // Step 2: Create children using parent IDs
             var fichas = new List<CrmArtigoFicha>();
             for (int i = 0; i < artigos.Count; i++)
             {

                    fichas.Add(CreateFicha(excelRows[i], artigos[i].Id));
             }
             await context.BulkInsertAsync(fichas);

             // Step 3: For grandchildren, use an index map
             var faseArtigos = new List<CrmFaseArtigo>();
             var indexMap = new Dictionary<(int artigoId, string phase), int>();

             for (int i = 0; i < artigos.Count; i++)
             {

                    foreach (var phase in excelRows[i].Phases)
                    {

                            var faseArtigo = new CrmFaseArtigo { Artigoid = artigos[i].Id };
                            indexMap[(artigos[i].Id, phase.Name)] = faseArtigos.Count;
                            faseArtigos.Add(faseArtigo);
                    }
             }

await context.BulkInsertAsync(faseArtigos, bulkConfig);
// faseArtigos now have IDs, use indexMap to find them!

5.5 Transaction Handling: All-or-Nothing

             await using var transaction = await context.Database.BeginTransactionAsync();

             try
             {

                    await context.BulkInsertAsync(artigos, bulkConfig);
                    await context.BulkInsertAsync(fichas);
                    await context.BulkInsertAsync(faseArtigos, bulkConfig);
                    await context.BulkInsertAsync(componentes);

                    await transaction.CommitAsync();
             }
             catch (Exception)
             {

                    await transaction.RollbackAsync();
                    throw; // All changes undone!
             }

5.7 Common Mistakes

             // WRONG: IDs remain 0
             await context.BulkInsertAsync(artigos);
             Console.WriteLine(artigos[0].Id); // 0!

             // RIGHT: IDs are populated
             await context.BulkInsertAsync(artigos, new BulkConfig { SetOutputIdentity = true });

             // WRONG: Order may change, correlation breaks
             await context.BulkInsertAsync(artigos, new BulkConfig { SetOutputIdentity = true });
             var ficha = CreateFicha(excelRows[0], artigos[0].Id); // May not match!

             // RIGHT: Order preserved
             await context.BulkInsertAsync(artigos, new BulkConfig
             {

                    SetOutputIdentity = true,
                    PreserveInsertOrder = true
             });

             // WRONG: If componentes fails, artigos are already committed!
             await context.BulkInsertAsync(artigos, bulkConfig);
             await context.BulkInsertAsync(componentes); // Error leaves orphan artigos

             // RIGHT: Transaction wraps everything
             await using var transaction = await context.Database.BeginTransactionAsync();
             // ... all inserts ... then CommitAsync()

Chapter 6: Role-Based Permissions

6.1 The Bad Way: Boolean Flags

             public class User
             {

                    public int Id { get; set; }
                    public string Email { get; set; }

                    // Authorization via booleans
                    public bool IsAdmin { get; set; }
                    public bool CanCreateBoards { get; set; }
                    public bool CanDeleteBoards { get; set; }
                    public bool CanManageUsers { get; set; }
                    public bool CanViewReports { get; set; }
                    // ... 20 more boolean flags
             }

Why this is bad:

      • Database bloat - 20 permissions = 20 columns per user
      • No grouping - 100 managers × 20 flags to maintain
      • Hard to change - New permission = column + property + forms + checks
      • No hierarchy - No relationship between Admin and Manager

6.2 The Good Way: Role-Permission Model

             User ss→ UserRole ss→ Role ss→ RolePermission ss→ Permission

             Users have Roles:

Chapter 7: Password Security

7.1 Why We Never Store Plain Passwords

Scenario: Your database gets hacked (it happens to the best companies).

Storage Method  Hacker sees                       Result
Plain text      password123                       Immediate access to all accounts
Hashed          $2a$12$LQv3c1yq...                Useless without cracking

Rule #1: Never, ever store plain text passwords.

7.2 What is Hashing?

Hashing is a one-way function: Input → Output, but you cannot reverse it.

             Password → [Hash Function] → Hash
             "abc123" → [BCrypt] → "$2a$12$R9h/cIPz0gi.URNNX3kh2O..."

             Hash → [???] → Password
             "$2a$12$R9h/cIPz0gi.URNNX3kh2O..." → ??? → IMPOSSIBLE

7.3 Why BCrypt (Not MD5 or SHA)

MD5 and SHA are designed to be fast. A modern GPU can compute 180 billion MD5 hashes per second.
BCrypt is intentionally slow with a configurable work factor.

Work Factor     Time per Hash                     Hashes/Second
10              ~100ms                            10
12              ~300ms                            3
14              ~1 second                         1

8-character password cracking time:
MD5: 6.6 quadrillion ÷ 180 billion = ~10 hours
BCrypt: 6.6 quadrillion ÷ 3 = 70 million years

7.4 What is Salting?

A salt is a random string added to the password before hashing. Same password + different salts =
different hashes.

             Without salt:
             "password123" → [Hash] → "5f4dcc3b5aa..."
             Two users with same password = same hash (bad!)

             With salt:
             "password123" + "x7Kj9L" → [Hash] → "a1b2c3..."
             "password123" + "mN4pQ2" → [Hash] → "d4e5f6..."
             Same password, different hashes (good!)

             BCrypt includes the salt in the hash itself:
             $2a$12$LQv3c1yqT.SIvHn4FZNVCuqQ.aXP1vF...


--- PAGE BREAK ---

             s s s sss Salt + Hash (combined)
             s s sss Work factor (12)
             s sss BCrypt version
             sss Algorithm identifier

7.5 Implementation

             public class PasswordService : IPasswordService
             {

                    private const int WorkFactor = 12;

                    public string Hash(string password)
                    {

                            // BCrypt automatically generates a random salt
                            return BCrypt.Net.BCrypt.HashPassword(password, WorkFactor);
                    }

                    public bool Verify(string password, string hash)
                    {

                            // BCrypt extracts the salt from the stored hash
                            return BCrypt.Net.BCrypt.Verify(password, hash);
                    }
             }

7.6 Account Lockout

             if (user.LockoutEnd > DateTime.UtcNow)
                    return LoginResult.Locked(user.LockoutEnd.Value);

             if (!_passwordService.Verify(password, user.PasswordHash))
             {

                    user.FailedLoginAttempts++;

                    // Lock after 5 failed attempts
                    if (user.FailedLoginAttempts >= 5)

                            user.LockoutEnd = DateTime.UtcNow.AddMinutes(15);

                    return LoginResult.InvalidCredentials(5 - user.FailedLoginAttempts);
             }

             // Success - reset attempts
             user.FailedLoginAttempts = 0;
             user.LockoutEnd = null;

             if (user == null) return "Email not found";
             if (!validPassword) return "Incorrect password";

Chapter 9: Antiforgery & CSRF Protection

9.1 The Attack Explained

CSRF (Cross-Site Request Forgery) tricks a user's browser into making unwanted requests to a site where
the user is authenticated.

             1. Alice logs into her-bank.com
                   → Browser receives auth cookie: "session=abc123"

             2. Alice visits evil-site.com (in another tab)
                   → Evil site contains hidden form:

                   <form action="https://her-bank.com/transfer" method="POST">
                          <input type="hidden" name="to" value="attacker" />
                          <input type="hidden" name="amount" value="10000" />

                   </form>
                   <script>document.forms[0].submit();</script>

             3. Browser automatically includes her-bank.com cookies
                   → Transfer executes with Alice's session!

9.2 How Antiforgery Tokens Solve This

ASP.NET Core uses a double-submit cookie pattern:

YOUR SITE (legitimate request):

ssssssssssssssss             ssssssssssssssss

s Browser s sssssss s Server                 s

s Cookie:  s     s Cookie               s

s Form token: s  s Form                 s

ssssssssssssssss             s Match              s

                  ssssssssssssssss

                  → s Request OK

EVIL SITE (forged request):

ssssssssssssssss             ssssssssssssssss

s Browser s sssssss s Server                 s

s Cookie:  s     s Cookie               s

s Form token: #s  s Form #              s

s (can't read) s  ssssssssssssssss

ssssssssssssssss             → s BLOCKED

Chapter 10: Claims-Based Authorization

    Key Insight: [Authorize], <AuthorizeView>, and IsInRole() work with Claims, not with ASP.NET
    Identity. Identity is just one way to create claims - you can build your own!

10.1 What Are Claims?

A Claim is a statement about a user - a key-value pair that describes something about them.

// Examples of claims:                            // User's name
new Claim(ClaimTypes.Name, "john.doe")           // User's email
new Claim(ClaimTypes.Email, "john@example.com")  // User is in Admin role
new Claim(ClaimTypes.Role, "Admin")              // Custom claim: has permission
new Claim("permission", "users.create")          // Custom claim: department
new Claim("department", "Engineering")

ClaimsPrincipal Structure

             ClaimsPrincipal (represents the user)
                    sss ClaimsIdentity (authentication method, e.g., "SkillCanvasAuth")
                                   sss Claims[] (list of key-value pairs)
                                                 sss ClaimTypes.NameIdentifier = "123"
                                                 sss ClaimTypes.Name = "john.doe"
                                                 sss ClaimTypes.Role = "Admin"
                                                 sss ClaimTypes.Role = "Manager" ← Multiple role claims!
                                                 sss "permission" = "users.create"

Key Point: A user can have multiple claims of the same type - this is how we support multiple roles!

10.2 Claims vs ASP.NET Identity

Many developers think you need ASP.NET Identity for authorization. This is a misconception. The
authorization system only cares about Claims - it doesn't know or care where they came from.

Feature                ASP.NET Identity          Custom Claims System
                                                 Your own User table
User storage           Identity tables           You implement (BCrypt)
                                                 Yes!
Password hashing       Built-in                  Yes!
                                                 Yes!
[Authorize] works?     Yes

<AuthorizeView> works? Yes

IsInRole() works?      Yes

10.3 How Authorization Actually Works

             // When you write:
             [Authorize(Roles = "Admin,Manager")]

             // - Type == ClaimTypes.Role

             // Same as:

             public class CustomAuthStateProvider : AuthenticationStateProvider
             {

                    private readonly IAuthenticationService _authService;
                    private AuthenticationState? _cachedState;

                    public override async Task<AuthenticationState> GetAuthenticationStateAsync()
                    {

                            // Return cached state if available (prevents race conditions)
                            if (_cachedState != null) return _cachedState;

                            try
                            {

                                          var identity = new ClaimsIdentity(claims, "MyAuthType");
                                          var principal = new ClaimsPrincipal(identity);

                                          _cachedState = new AuthenticationState(principal);
                                   }
                                   else
                                   {

                                          _cachedState = new AuthenticationState(new ClaimsPrincipal());
                                   }
                            }
                            catch

                                   _cachedState = new AuthenticationState(new ClaimsPrincipal());
                            }

                            return _cachedState;
                    }

                    public void NotifyAuthStateChanged()
                    {

                            NotifyAuthenticationStateChanged(GetAuthenticationStateAsync());
                    }
             }

Chapter 11: ProtectedLocalStorage

11.1 What is ProtectedLocalStorage?

ProtectedLocalStorage is a Blazor Server service that provides secure, encrypted access to the
browser's localStorage. Unlike regular JavaScript localStorage, it encrypts data before storing and protects
against tampering.

             @inject ProtectedLocalStorage LocalStorage

             // Store a value (encrypted automatically)
             await LocalStorage.SetAsync("user_preference", "dark_mode");

             // Retrieve a value (decrypted automatically)
             var result = await LocalStorage.GetAsync<string>("user_preference");
             if (result.Success)
             {

                    var value = result.Value; // "dark_mode"
             }

11.2 The Prerendering Problem

Blazor Server uses prerendering by default. The page is first rendered on the server (no browser exists
yet), then sent to the client, then Blazor reconnects via SignalR. During server prerendering, there is no
browser—so ProtectedLocalStorage throws an exception!

             // BAD - This will fail during prerendering!
             protected override async Task OnInitializedAsync()
             {

                    var result = await LocalStorage.GetAsync<string>("token"); // EXCEPTION!
             }

             // GOOD - OnAfterRenderAsync runs after browser is available
             protected override async Task OnAfterRenderAsync(bool firstRender)
             {

                    if (firstRender)
                    {

                            var result = await LocalStorage.GetAsync<string>("token"); // Works!
                            if (result.Success)
                            {

                                   _token = result.Value;
                                   StateHasChanged(); // Re-render with loaded data
                            }
                    }
             }

Chapter 13: JavaScript Interop

    Key Insight: JavaScript interop in Blazor Server is NOT available during prerendering. You must
    handle InvalidOperationException gracefully and defer JS calls to OnAfterRenderAsync.

13.1 What is JavaScript Interop?

Blazor runs C# code, but sometimes you need to interact with browser JavaScript APIs (DOM
manipulation, localStorage, third-party JS libraries). JavaScript Interop (JS Interop) is the bridge
between C# and JavaScript.

             // Calling JavaScript from C#
             @inject IJSRuntime JS

             var result = await JS.InvokeAsync<string>("localStorage.getItem", "myKey");

             // Or call a custom function
             await JS.InvokeVoidAsync("myJsFunction", arg1, arg2);

             // JavaScript side
             window.myJsFunction = function(arg1, arg2) {

                    console.log("Called from C#!", arg1, arg2);
             };

13.2 The Blazor Server Rendering Timeline

             Phase 1: PRERENDER (Server-Side, NO JavaScript)
             ssssssssssssssssssssssssssssssssssssssssssssssss
             - Initial HTTP request arrives at server
             - Components render to static HTML
             - NO SignalR connection yet
             - s JS Interop calls WILL FAIL

             Phase 2: HTML SENT TO BROWSER
             ssssssssssssssssssssssssssssssssssssssssssssssss
             - Static HTML displayed to user (fast first paint!)
             - Blazor JavaScript bundle loads
             - SignalR connection establishing...
             - s JS Interop still not ready

             Phase 3: INTERACTIVE MODE (SignalR Connected)
             ssssssssssssssssssssssssssssssssssssssssssssssss
             - SignalR WebSocket connection established
             - OnAfterRenderAsync(firstRender: true) fires
             - s JS Interop NOW AVAILABLE

13.3 Why JS Interop Fails During Prerender

             // This FAILS during prerender!
             protected override async Task OnInitializedAsync()
             {

                    var value = await JS.InvokeAsync<string>("localStorage.getItem", "key");
             }

             // Error:
             // InvalidOperationException: JavaScript interop calls cannot be issued at
             // this time. This is because the component is being statically rendered.

13.4 Safe Patterns for JS Interop


--- PAGE BREAK ---

Pattern 1: OnAfterRenderAsync (Recommended)

             @code {
                    private string? _storedValue;
                    private bool _isLoaded = false;

                    protected override async Task OnAfterRenderAsync(bool firstRender)
                    {

                            if (firstRender)
                            {

                                   // s SAFE - SignalR is connected, JS is available
                                   _storedValue = await JS.InvokeAsync<string>("localStorage.getItem", "key");
                                   _isLoaded = true;
                                   StateHasChanged(); // Re-render with loaded data
                            }
                    }
             }

Pattern 2: Try-Catch with Graceful Fallback

             public async Task<string?> GetSessionTokenAsync()
             {

                    try
                    {

                            var result = await _localStorage.GetAsync<string>("session_token");
                            return result.Success ? result.Value : null;
                    }
                    catch (InvalidOperationException)
                    {
                            // Expected during prerender - JS not available
                            _logger.LogDebug("Session token unavailable (prerender phase)");
                            return null;
                    }
                    catch (Exception ex)
                    {
                            // Actual errors should be logged as ERROR
                            _logger.LogError(ex, "Error retrieving session token");
                            return null;
                    }
             }

13.5 Common Pitfalls and Solutions

             // s WRONG - OnInitializedAsync runs during prerender
             protected override async Task OnInitializedAsync()
             {

                    _value = await JS.InvokeAsync<string>("localStorage.getItem", "key");
             }

             // s CORRECT - OnAfterRenderAsync is safe
             protected override async Task OnAfterRenderAsync(bool firstRender)
             {

                    if (firstRender)
                    {

                            _value = await JS.InvokeAsync<string>("localStorage.getItem", "key");
                            StateHasChanged();
                    }
             }

             // s WRONG - Infinite loop!
             protected override async Task OnAfterRenderAsync(bool firstRender)
             {

                    _value = await LoadDataAsync(); // Always loads
                    StateHasChanged(); // Re-renders → OnAfterRenderAsync → repeat!

             @* s WRONG - Throws if _user is null during prerender *@
             <span>Welcome, @_user.DisplayName!</span>

             @* s CORRECT - Handle null state *@
             @if (_user != null)
             {

                    <span>Welcome, @_user.DisplayName!</span>

13.7 Exception Handling Best Practices

Scenario                 Exception                                     Log Level
Prerender phase          InvalidOperationException                     Debug
Language change          InvalidOperationException                     Debug
Network error            JSException                                   Error
Deserialization failure  JsonException                                 Error

13.8 Key Takeaways

      • JS Interop requires SignalR - Not available during prerender
      • Use OnAfterRenderAsync - The ONLY safe lifecycle method for JS calls
      • Check firstRender - Avoid infinite render loops
      • Handle InvalidOperationException - Expected during prerender, log as Debug
      • Show loading states - UI must handle null/loading gracefully
      • Cache when possible - Prevent concurrent JS calls
