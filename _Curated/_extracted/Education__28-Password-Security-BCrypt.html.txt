Tutorial #28 — Password Security & BCrypt
From plaintext disasters to cryptographically secure hashing in GivingCare
1. Why Not Store Plaintext?
Imagine your database gets leaked (it happens to the biggest companies in the world). If passwords are stored in plaintext, every user account is instantly compromised. The attacker doesn't need to crack anything — they just read the passwords.
Password hashing is a one-way transformation. You can turn a password into a hash, but you can never turn a hash back into a password. When a user logs in, you hash their input and compare the hashes — you never need to know the original password.
PLAINTEXT STORAGE (never do this):
┌───────────────────────────────────┐
│ Username │ Password │
│───────────┼───────────────────────│
│ admin │ MyS3cretPass! │ <-- attacker reads this directly
│ joao │ password123 │
└───────────────────────────────────┘
HASHED STORAGE (correct approach):
┌──────────────────────────────────────────────────────────────────┐
│ Username │ PasswordBcrypt │
│───────────┼──────────────────────────────────────────────────────│
│ admin │ $2a$12$LJ3m4ys... (60 chars, irreversible) │
│ joao │ $2a$12$Kx9pQw... (different salt = different hash) │
└──────────────────────────────────────────────────────────────────┘

Why "Fast = Bad" for Passwords
For file checksums or digital signatures, speed is a feature. But for password hashing, speed is the enemy. A fast algorithm lets attackers try billions of guesses per second. BCrypt is deliberately slow — the work factor controls exactly how slow.
Work Factor Explained
BCrypt's work factor (also called "cost factor") is a power of 2. A work factor of 12 means 2^12 = 4,096 internal iterations. Each increment doubles the computation time:

At work factor 12, a single hash takes ~260ms. A user logging in waits a quarter-second (imperceptible). An attacker trying 1 billion passwords waits 8.2 years .
BCrypt is like a combination lock with adjustable complexity. Work factor 12 means the lock has 4,096 tumblers. Each additional factor DOUBLES the work — making brute force exponentially harder.

Hashing — HashBCrypt
public string HashBCrypt ( string password )
{
// Work factor of 12 is a good balance between security and performance
return BCrypt.Net.BCrypt . HashPassword ( password , 12 );
}
BCrypt.HashPassword(password, 12) reads as: "Take this password, generate a random salt, hash it 4,096 times, and return the result with the salt baked in."
What Does the Output Look Like?
$2a$12$LJ3m4ysR7Gx1qZv5k8Pn6eYz.......................
│ │ │ │
│ │ │ └── The salt (22 chars) + hash (31 chars)
│ │ └───── Work factor: 12 (meaning 2^12 = 4,096 iterations)
│ └──────── BCrypt version identifier
└─────────── Algorithm marker ($2a = BCrypt)
The salt is embedded in the hash string itself . This means you don't need a separate salt column in your database. When you call Verify , BCrypt extracts the salt from the stored hash, re-hashes the input with it, and compares.
Verification — VerifyBCrypt
public bool VerifyBCrypt ( string password , string hash )
{
try
{
return BCrypt.Net.BCrypt . Verify ( password , hash );
}
catch ( Exception ex )
{
_logger . LogError ( ex , "Error verifying BCrypt password" );
return false ;
}
}
BCrypt.Verify doesn't decrypt the password. It re-hashes the input with the same salt (extracted from the stored hash) and compares the results. Passwords are never "decrypted."
The Wrapper — VerifyPassword
public bool VerifyPassword ( string password , string bcryptHash )
{
if ( string . IsNullOrEmpty ( bcryptHash ))
return false ;
return VerifyBCrypt ( password , bcryptHash );
}
This is the public entry point. It adds a null-check guard before delegating to VerifyBCrypt . A user with no PasswordBcrypt value can never authenticate.
4. Password Strength Validation
Hashing protects passwords in storage, but it can't save a weak password like "123456" . GivingCare enforces password strength at creation time.
ValidatePasswordStrength
public bool ValidatePasswordStrength ( string password )
{
if ( string . IsNullOrEmpty ( password ) || password .Length < 8 )
return false ;
bool hasLower = password . Any ( char .IsLower);
bool hasUpper = password . Any ( char .IsUpper);
bool hasDigit = password . Any ( char .IsDigit);
bool hasSpecial = password . Any ( ch => ! char . IsLetterOrDigit ( ch ));
// Require at least 3 of the 4 character types
int complexity = ( hasLower ? 1 : 0 ) + ( hasUpper ? 1 : 0 ) +
( hasDigit ? 1 : 0 ) + ( hasSpecial ? 1 : 0 );
return complexity >= 3 ;
}
The rules are:
Minimum 8 characters — rejects short passwords immediately
3 of 4 character types required: lowercase, uppercase, digit, special character
This means Password1 (lower + upper + digit) passes, but password1 (lower + digit = only 2 types) fails
Helpful Error Messages — GetPasswordStrengthMessage
public string GetPasswordStrengthMessage ( string password )
{
if ( string . IsNullOrEmpty ( password ))
return "Password is required" ;
if ( password .Length < 8 )
return "Password must be at least 8 characters" ;
List < string > missing = new ();
if (! hasLower ) missing . Add ( "lowercase letter" );
if (! hasUpper ) missing . Add ( "uppercase letter" );
if (! hasDigit ) missing . Add ( "number" );
if (! hasSpecial ) missing . Add ( "special character" );
if ( missing .Count > 1 )
return $"Password should include: {string.Join(", ", missing)}" ;
return "Password is strong" ;
}
Instead of a generic "password too weak" error, this tells the user exactly what's missing. Good UX makes good security — users are more likely to create strong passwords when they get clear guidance.

The Core Login Method
public async Task < LoginResult > LoginAsync ( string username , string password )
{
// Step 1: Check for lockout
if ( IsLockedOut ( username ))
{
return new LoginResult
{
Success = false ,
Message = "Account is locked. Please try again in 15 minutes."
};
}
await using var context = _contextFactory . CreateBaseControleContext ();
// Step 2: Lookup user (exclude soft-deleted)
var user = await context .Users
. FirstOrDefaultAsync ( u => u .Username == username
&& ( u .IsDeleted == false || u .IsDeleted == null ));
if ( user == null )
{
await RecordFailedAttempt ( username );
await _auditService . LogFailedLoginAsync ( username );
return new LoginResult { Success = false , Message = "Invalid username or password" };
}
// Step 3: Verify BCrypt hash
bool isValid = _passwordService . VerifyPassword ( password , user .PasswordBcrypt);
if (! isValid )
{
await RecordFailedAttempt ( username );
await _auditService . LogFailedLoginAsync ( username );
return new LoginResult
{
Success = false ,
Message = "Invalid username or password" ,
FailedAttempts = GetFailedAttempts ( username )
};
}
// Step 4: Check if user is active
if ( user .IsActive != true )
{
return new LoginResult { Success = false , Message = "User account is inactive" };
}
// Step 5-8: Success path
ClearFailedAttempts ( username );
await _sessionService . SetUserSessionAsync ( new CompanyUserSession { ... });
await _auditService . LogLoginAsync ( user .Id);
user .LastLogon = DateTime .Now;
await context . SaveChangesAsync ();
// Step 9: Check if password change is required
return new LoginResult
{
Success = true ,
User = user ,
RequiresPasswordChange = user .ChangePassword == true
};
}
Notice the security-conscious design: both "user not found" and "wrong password" return the same message ( "Invalid username or password" ). This prevents username enumeration — an attacker can't tell whether the username or the password was wrong.
6. Account Lockout Mechanism
The lockout system prevents brute-force attacks by temporarily blocking login after too many failures. It uses a static dictionary to track attempts in memory.
The Tracking Structure
// Track failed attempts (in production, use distributed cache)
private static readonly Dictionary < string , LoginAttempts > _failedAttempts = new ();
private class LoginAttempts
{
public int Count { get ; set ; }
public DateTime LastAttempt { get ; set ; }
public DateTime LockedUntil { get ; set ; }
}
The dictionary is static — it persists across requests and across scoped service lifetimes. The key is the username, so each user is tracked independently.
Checking Lockout
private bool IsLockedOut ( string username )
{
if ( _failedAttempts . TryGetValue ( username , out var attempts ))
{
if ( attempts .Count >= 5 && attempts .LockedUntil > DateTime .Now)
{
return true ;
}
}
return false ;
}
Recording Failures
private async Task RecordFailedAttempt ( string username )
{
if (! _failedAttempts . ContainsKey ( username ))
{
_failedAttempts [ username ] = new LoginAttempts ();
}
var attempts = _failedAttempts [ username ];
attempts .Count++;
attempts .LastAttempt = DateTime .Now;
if ( attempts .Count >= 5 )
{
attempts .LockedUntil = DateTime .Now. AddMinutes ( 15 );
}
}
Clearing on Success
private void ClearFailedAttempts ( string username )
{
_failedAttempts . Remove ( username );
}
Attempt 1: wrong password → Count = 1 "Invalid username or password (4 remaining)"
Attempt 2: wrong password → Count = 2 "Invalid username or password (3 remaining)"
Attempt 3: wrong password → Count = 3 "Invalid username or password (2 remaining)"
Attempt 4: wrong password → Count = 4 "Invalid username or password (1 remaining)"
Attempt 5: wrong password → Count = 5 LockedUntil = Now + 15 min
Attempt 6: any password → "Account is locked. Try again in 15 minutes."
...
After 15 minutes: → Lock expires, attempts resume
Correct password: → ClearFailedAttempts() — counter reset to 0
The Login.razor page shows the remaining attempts to the user:
if ( result .FailedAttempts > 0 && result .FailedAttempts < 5 )
{
ErrorMessage += $" ({5 - result.FailedAttempts} tentativas restantes)" ;
}

The Reset Method
public async Task < bool > ResetPasswordAsync ( string email )
{
await using var context = _contextFactory . CreateBaseControleContext ();
var user = await context .Users
. FirstOrDefaultAsync ( u => u .Email == email
&& ( u .IsDeleted == false || u .IsDeleted == null ));
if ( user == null )
return false ; // Don't reveal if email exists
// Generate temporary password (cryptographically secure)
var tempPassword = _passwordService . GeneratePassword (
length: 12 ,
includeLowercase: true ,
includeUppercase: true ,
includeNumeric: true ,
includeSpecial: true );
// Hash and save temporary password
user .PasswordBcrypt = _passwordService . HashBCrypt ( tempPassword );
user .ChangePassword = true ; // Force change on next login
await context . SaveChangesAsync ();
// Send email with temporary password
var emailSent = await _emailService . SendPasswordResetEmailAsync (
email , user .Name, user .Username, tempPassword );
if ( emailSent )
await _auditService . LogAsync ( user .Id, "PASSWORD_RESET_REQUESTED" );
return emailSent ;
}
The temporary password is never stored in plaintext in the database. Only the BCrypt hash is saved. The plaintext exists only in the email sent to the user and is immediately eligible for garbage collection after the method returns.
8. Legacy MD5 Column
The User model still contains the old MD5 password column, but it is marked as obsolete and never used in code.
File: Models/Identity/User.cs
[ Obsolete ( "MD5 password support removed. This column is retained for DB compatibility only." )]
[ Column ( "AgPassword" )]
[ JsonIgnore ]
[ StringLength ( 50 )]
public string ? AgPassword { get ; set ; }
[ Column ( "PasswordBcrypt" )]
[ JsonIgnore ]
[ StringLength ( 100 )]
public string ? PasswordBcrypt { get ; set ; }
Three important attributes on the legacy column:
[Obsolete] — generates a compiler warning if any code tries to use it, with a message explaining why
[JsonIgnore] — never serialized in API responses (defense in depth — even if someone accidentally returns a User object, the hash won't leak)
[StringLength(50)] — MD5 produces a 32-character hex string, so 50 was enough. BCrypt needs StringLength(100) because its output is 60 characters
Why keep the column? The database still has AgPassword data for historical records. Dropping the column would require a migration, and the column costs nothing to keep. The [Obsolete] attribute ensures no developer accidentally uses it.
9. Secure Random Password Generation
When the system generates temporary passwords (for resets, new accounts, etc.), it uses cryptographically secure randomness — not Random() .
public string GeneratePassword ( int length , bool includeLowercase = true ,
bool includeUppercase = true , bool includeNumeric = true ,
bool includeSpecial = true )
{
const string lowercaseChars = "abcdefghijklmnopqrstuvwxyz" ;
const string uppercaseChars = "ABCDEFGHIJKLMNOPQRSTUVWXYZ" ;
const string numericChars = "0123456789" ;
const string specialChars = "!@#$%^&*" ;
string charSet = "" ;
if ( includeLowercase ) charSet += lowercaseChars ;
if ( includeUppercase ) charSet += uppercaseChars ;
if ( includeNumeric ) charSet += numericChars ;
if ( includeSpecial ) charSet += specialChars ;
if ( string . IsNullOrEmpty ( charSet ))
throw new ArgumentException ( "At least one character set must be included." );
return new string ( Enumerable . Repeat ( charSet , length )
. Select ( s => s [ RandomNumberGenerator . GetInt32 ( s .Length)])
. ToArray ());
}

How the LINQ Chain Works
// Conceptual breakdown of the password generation:
// 1. Repeat the character set string 12 times (once per desired character)
Enumerable . Repeat ( "abcABC012!@#" , 12 )
// 2. For each repetition, pick one random character
. Select ( s => s [ RandomNumberGenerator . GetInt32 ( s .Length)])
// 3. Combine into a string
. ToArray () // → char[] → new string()
