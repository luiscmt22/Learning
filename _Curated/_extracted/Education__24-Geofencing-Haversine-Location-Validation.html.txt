Geofencing & Haversine — GPS-Based Location Validation
Geofencing & Haversine
GPS-Based Location Validation — How GivingCare Knows Where You Are
1. What Is Geofencing?
A geofence is an invisible boundary around a physical location, defined by a center point
(latitude + longitude) and a radius (in meters). The system checks whether a person's GPS coordinates fall
inside or outside that boundary.
In GivingCare, geofencing answers one critical question for attendance: "Are you actually at the
office (or job site) when you check in?" Without this, employees could clock in from home and
the system would have no way to verify their physical presence.
The default geofence radius in GivingCare is 100 meters . This is configurable per Location
and per Job.
A geofence is like an invisible dog fence — the boundary exists only in software, but if you cross
it, the system knows. There is no physical wire or wall. The "fence" lives entirely in the database as
a latitude, longitude, and radius. The phone's GPS is the "collar" that tells the system where you are.
* Employee phone GPS (41.1580, -8.6300)
/
/ Distance = 87m (Haversine)
/
O -------- radius: 100m -------- Office center (41.1579, -8.6291)
Result: INSIDE geofence (87m < 100m) --> CHECK-IN ALLOWED
The circle has a center (the office) and a radius (100m). The employee's phone reports GPS coordinates.
We calculate the distance between the two points. If distance <= radius , they are inside.
If distance > radius , they are outside.
2. The Math: Haversine Formula
The core of geofencing is distance calculation. Given two GPS coordinates, how far apart are they in
meters? This is handled by the GeofenceService — a stateless utility that implements
the Haversine formula .
The Actual Code
From Services/Core/Geofence/GeofenceService.cs :
public class GeofenceService : IGeofenceService
{
// Earth's radius in meters
private const double EarthRadiusMeters = 6371000 ;
public double CalculateDistance ( decimal lat1 , decimal lon1 , decimal lat2 , decimal lon2 )
{
// Convert to radians
var lat1Rad = ( double ) lat1 * Math .PI / 180 ;
var lat2Rad = ( double ) lat2 * Math .PI / 180 ;
var deltaLat = (( double ) lat2 - ( double ) lat1 ) * Math .PI / 180 ;
var deltaLon = (( double ) lon2 - ( double ) lon1 ) * Math .PI / 180 ;
// Haversine formula
var a = Math . Sin ( deltaLat / 2 ) * Math . Sin ( deltaLat / 2 ) +
Math . Cos ( lat1Rad ) * Math . Cos ( lat2Rad ) *
Math . Sin ( deltaLon / 2 ) * Math . Sin ( deltaLon / 2 );
var c = 2 * Math . Atan2 ( Math . Sqrt ( a ), Math . Sqrt ( 1 - a ));
return EarthRadiusMeters * c ;
}
}
Breaking Down the Math Step by Step
Step 1: Convert Degrees to Radians
GPS coordinates are in degrees (e.g., 41.1579). Trigonometric functions like
Math.Sin and Math.Cos expect radians . The conversion is
simple: multiply by π/180 .
var lat1Rad = ( double ) lat1 * Math .PI / 180 ;
// 41.1579° becomes 0.7185 radians
Step 2: Calculate the Deltas
deltaLat and deltaLon are the differences between the two points, also
converted to radians. These represent "how far apart are the two points in each axis?"
var deltaLat = (( double ) lat2 - ( double ) lat1 ) * Math .PI / 180 ;
var deltaLon = (( double ) lon2 - ( double ) lon1 ) * Math .PI / 180 ;
// Small differences: ~0.000017 radians for 1 meter
Step 3: The Haversine Formula (variable a )
This is the heart of the algorithm. It calculates a value a that represents the
square of the half-chord length between the two points on the sphere:
var a = Math . Sin ( deltaLat / 2 ) * Math . Sin ( deltaLat / 2 ) +
Math . Cos ( lat1Rad ) * Math . Cos ( lat2Rad ) *
Math . Sin ( deltaLon / 2 ) * Math . Sin ( deltaLon / 2 );
The formula is: a = sin²(Δlat/2) + cos(lat1) × cos(lat2) ×
sin²(Δlon/2)
Think of it this way: the first term ( sin²(Δlat/2) ) handles the north-south
distance. The second term handles the east-west distance, but it is weighted by
cos(lat1) × cos(lat2) because longitude lines converge at the poles.
At the equator, cos(0°) = 1 , so longitude has full weight. At the North Pole,
cos(90°) = 0 , so longitude contributes nothing (because all longitude lines meet
at the poles).
Step 4: Angular Distance (variable c )
var c = 2 * Math . Atan2 ( Math . Sqrt ( a ), Math . Sqrt ( 1 - a ));
c is the angular distance in radians between the two points on the
sphere's surface. The atan2 function is used instead of asin because it is
more numerically stable for small distances (which is exactly our use case — we are measuring
tens to hundreds of meters, not thousands of kilometers).
Step 5: Multiply by Earth's Radius
return EarthRadiusMeters * c ;
// 6,371,000 meters × angular distance = surface distance in meters
The angular distance c (in radians) times the sphere's radius gives the arc
length — the actual distance along the Earth's surface. This is the number we compare
against the geofence radius.
The Haversine formula reads as: "Given two points on a sphere, how far apart are they along the surface?"
It accounts for the curve of the Earth. You cannot just use sqrt((x2-x1)² + (y2-y1)²)
because that would be a straight line through the Earth, not along the surface. And more importantly,
degrees of longitude are not the same physical distance at every latitude.
Why Not Pythagorean Distance?
You might think: "Can't I just calculate sqrt((lat2-lat1)² + (lon2-lon1)²) and
multiply by some constant?" The answer is no , for two reasons:
The Earth is a sphere, not a flat plane. Distances along the surface are curved,
not straight lines.
Longitude degrees are not constant. At the equator (latitude 0°),
1° of longitude = ~111 km. At latitude 41° (Porto, Portugal), 1° of longitude = ~85 km.
At latitude 60° (Helsinki), 1° of longitude = ~55 km. At the poles, 1° of longitude = 0 km.
The Pythagorean formula treats longitude and latitude as equal, which would produce wildly wrong
distances at non-equatorial latitudes.
Never use Pythagorean distance for GPS coordinates. The Earth is a sphere. Use Haversine. At latitude
41° (Porto), 1° of longitude is only ~85km, not 111km like at the equator. Using flat-plane
math would overestimate east-west distances by ~30% at Porto's latitude, potentially blocking employees
who are legitimately inside the geofence.

3. Getting the User's Location — JavaScript Interop
Before we can validate a geofence, we need the employee's GPS coordinates. Since Blazor Server runs on
the server, it cannot directly access the phone's GPS. We use JavaScript Interop to
call the browser's Geolocation API, then pass the result back to C#.
The JavaScript Fallback Chain
From App.razor — the geolocation function uses a three-step fallback:
// Geolocation Function with fallback chain: GPS -> Network -> IP
window . getGeolocation = async () => {
if ( location .protocol !== 'https:' && location .hostname !== 'localhost' ) {
return { success : false , error : "HTTPS necessario para geolocalizacao" };
}
if (! navigator .geolocation) {
return await getIpGeolocation ();
}
// Step 1: Try high accuracy (GPS) - 5 second timeout
const highAccuracy = await tryBrowserGeolocation ( true , 5000 );
if ( highAccuracy .success) return highAccuracy ;
// Step 2: Try low accuracy (cell tower/network) - 2 second timeout
const lowAccuracy = await tryBrowserGeolocation ( false , 2000 );
if ( lowAccuracy .success) return lowAccuracy ;
// Step 3: Fall back to IP geolocation
return await getIpGeolocation ();
};
The Browser Geolocation Helper
const tryBrowserGeolocation = ( highAccuracy , timeout ) => {
return new Promise (( resolve ) => {
navigator .geolocation. getCurrentPosition (
( pos ) => resolve ({
success : true ,
latitude : pos .coords.latitude,
longitude : pos .coords.longitude
}),
( err ) => resolve ({ success : false , error : err .message }),
{ enableHighAccuracy : highAccuracy , timeout : timeout , maximumAge : 60000 }
);
});
};
The IP Geolocation Fallback
const getIpGeolocation = async () => {
try {
const response = await fetch ( 'http://ip-api.com/json/?fields=status,lat,lon,message' );
const data = await response . json ();
if ( data .status === 'success' ) {
return { success : true , latitude : data .lat, longitude : data .lon };
}
} catch ( e ) {
// IP geolocation failed
}
return {
success : false ,
error : 'Nao foi possivel obter localizacao. Ative o GPS.'
};
};

Key design decisions:
Latitude and Longitude are nullable ( double? ).
Not every location has GPS coordinates. An office might exist in the system for organizational
purposes without a geofence.
GeofenceRadius defaults to 100 meters and is non-nullable. If
coordinates exist, there is always a radius.
HasGeofence is a [NotMapped] computed property. It is
not stored in the database — it is calculated on the fly from the nullable coordinates.
The database does not need to store a redundant boolean.

5. The Validation Pipeline
Check-in validation uses a chain of responsibility pattern. Each validator checks
one thing and returns either Ok() or Fail("reason") . They run in order.
The first failure stops the chain.
The Validator Interface
public interface ICheckInValidator
{
/// Execution order (lower = earlier)
int Order { get ; }
/// Validates the check-in context. Returns Ok or Fail with message.
CheckInValidationResult Validate ( CheckInContext context , CheckInValidationOptions options );
}
public record CheckInValidationResult ( bool IsValid , string ? Message )
{
public static CheckInValidationResult Ok () => new ( true , null );
public static CheckInValidationResult Fail ( string message ) => new ( false , message );
}
The Pipeline Order
Order 10 Order 20 Order 30 Order 40
+-----------+ +-----------------+ +-----------------+ +-------------------+
| Active |-->| Schedule Source |-->| Time Window |-->| Geolocation |
| CheckIn | | Validator | | Validator | | Validator |
| Validator | | | | | | |
+-----------+ +-----------------+ +-----------------+ +-------------------+
"Already "No schedule" "Too early" "Outside geofence"
checked in?" "All shifts done?" "Before window?" "Too far away?"
Each validator has a single responsibility (SRP). If validator at Order 10 fails, the ones at 20, 30,
and 40 never run. This means we do not waste time calculating GPS distance if the employee is already
checked in.
The GeolocationValidator (Check-In)
From Services/CheckIn/Validators/GeolocationValidator.cs — the last validator in
the chain (Order 40):
public class GeolocationValidator : ICheckInValidator
{
public int Order => 40 ;
public CheckInValidationResult Validate ( CheckInContext context , CheckInValidationOptions options )
{
// Skip if geolocation not required for this employee
if (! context .RequiresGeolocation)
return CheckInValidationResult . Ok ();
// Location not yet obtained (still acquiring GPS)
if (! options .LocationObtained)
return CheckInValidationResult . Fail ( "A obter localizacao..." );
// No valid geofence target (Location/Job missing coordinates)
if (! context .TargetLatitude.HasValue || ! context .TargetLongitude.HasValue)
return CheckInValidationResult . Fail (
"Localizacao de trabalho sem coordenadas GPS configuradas" );
// Outside geofence
if (! context .IsWithinGeofence)
{
var distanceOutside = context .DistanceToLocation - context .GeofenceRadius;
return CheckInValidationResult . Fail (
$"Fora da area autorizada ( { distanceOutside : F0 } m fora)" );
}
return CheckInValidationResult . Ok ();
}
}
Notice the progression of early returns. The method checks the simplest, cheapest condition first
( RequiresGeolocation is just a boolean) and only reaches the expensive check
( IsWithinGeofence ) if everything else passed. This is polite code
— fail fast, fail cheap.
How the Pipeline Runs
From CheckInValidationService.CanPerformCheckIn() :
public ( bool CanCheckIn, string ? BlockReason) CanPerformCheckIn (
CheckInContext context ,
bool locationObtained )
{
var options = new CheckInValidationOptions (
LocationObtained: locationObtained ,
EarlyCheckInToleranceMinutes: _config .EarlyCheckInToleranceMinutes
);
// Run validators in order (SOLID: OCP - add new validators without modifying this)
foreach ( var validator in _validators )
{
var result = validator . Validate ( context , options );
if (! result .IsValid)
{
return ( false , result .Message);
}
}
return ( true , null );
}
The _validators collection is injected via DI as
IEnumerable<ICheckInValidator> , sorted by Order in the constructor.
Adding a new validator is a matter of creating a class and registering it — no changes to
existing code (Open/Closed Principle).
6. Check-In vs Check-Out — The Critical Difference
The geofence behaves differently for check-in and check-out. This is by design.
Operation
Outside Geofence?
Behavior
Check-In
BLOCKED
"You can't start work if you're not here"
Check-Out
ALLOWED but RECORDED
"You can end your shift anywhere, but we note it"
Check-in blocks you outside the geofence. Check-out records it but
lets you leave. This is intentional — you cannot fake arriving at work, but you should not be
stuck unable to clock out because you left for lunch, drove to a client meeting, or just walked to
the car park. The system records the checkout location for auditing but does not prevent the action.
Check-Out GeolocationValidator
From Services/CheckOut/Validators/GeolocationValidator.cs :
public class GeolocationValidator : ICheckOutValidator
{
private readonly IGeofenceService _geofenceService ;
public int Order => 30 ;
public CheckOutValidationResult Validate (
CheckOutContext context ,
CheckOutValidationOptions options )
{
if (! context .RequiresGeolocation)
{
context .IsValidLocation = true ;
return CheckOutValidationResult . Ok ();
}
if (! options .LocationObtained)
return CheckOutValidationResult . Fail ( "A obter localizacao..." );
if (! context .TargetLatitude.HasValue || ! context .TargetLongitude.HasValue)
{
// Allow checkout but mark as invalid location
context .IsValidLocation = false ;
context .GeofenceMessage = "Localizacao sem coordenadas GPS configuradas" ;
return CheckOutValidationResult . Ok (); // <-- Always allows!
}
// Calculate distance
var distance = _geofenceService . CalculateDistance (
options .Latitude, options .Longitude,
context .TargetLatitude.Value, context .TargetLongitude.Value);
context .Distance = ( decimal ) distance ;
context .IsValidLocation = distance <= context .GeofenceRadius;
if ( context .IsValidLocation)
{
context .GeofenceMessage = $"Valido - { context .GeofenceTargetName} ( { distance : F0 } m)" ;
}
else
{
var distanceOutside = distance - context .GeofenceRadius;
context .GeofenceMessage = $"Fora da area ( { distanceOutside : F0 } m fora)" ;
}
// Allow checkout even if outside geofence
// The IsValidLocation flag records whether they were inside or not
return CheckOutValidationResult . Ok (); // <-- ALWAYS returns Ok
}
}
Observe the key difference from the check-in validator: this validator always returns
Ok() . It never blocks. Instead, it populates context.IsValidLocation
and context.GeofenceMessage — recording the facts for the attendance record without
preventing the action.
The CheckOutContext even has a separate Distance property (as
decimal? ) that gets snapshotted into the attendance record for later auditing.

9. Singleton Registration
The GeofenceService is registered as a Singleton in
Program.cs :
#region Core Utility Services (Shared across modules - no database dependencies)
builder .Services. AddSingleton < IGeofenceService , GeofenceService >();
builder .Services. AddSingleton < IHoursCalculationService , HoursCalculationService >();
builder .Services. AddScoped < IWorkingDaysCalculationService , WorkingDaysCalculationService >();
Why Singleton? Three reasons:
Pure math, no state. The service has no fields that change. EarthRadiusMeters
is a const . There are no instance variables to corrupt.
No database, no DI dependencies. The class has zero constructor parameters. It
does not inject anything. It cannot hold a reference to a scoped DbContext.
Thread-safe by nature. Since there are no mutable fields, any number of threads
can call CalculateDistance simultaneously without interference. The method is
referentially transparent — the same inputs always produce the same outputs.
Contrast this with GeofenceResolutionService , which is Scoped because it
accesses the database. It needs a fresh IDbContextFactoryService per request.
"If a service has no state and no dependencies, make it a Singleton. If it touches the database or
user-specific data, make it Scoped. If it is used once and thrown away (validators, generators), make
it Transient." This simple heuristic covers 95% of DI lifetime decisions.

Common Pitfalls
GPS Accuracy Indoors
GPS accuracy indoors is poor: typically 30-50 meters of error. Inside buildings,
the GPS signal bounces off walls and ceilings (multipath interference), making the reported position
jump around. This is why the default geofence radius is 100 meters — it accounts for the fact
that even a phone sitting on your desk at the office might report a position 30 meters away from the
actual office center.
Why 100 Meters?
GPS accuracy indoors: 30-50m error is normal
Building size: A typical office building is 30-50m across
Parking lot: Employees often check in from the car park, which might be 50-80m
from the building center
100m = comfortable margin that covers all these cases without being so large that
employees could check in from a neighboring building
The radius is configurable per Location and per Job, so a small retail shop might use 50m while a
large construction site might use 500m.
Edge Case: Exact Boundary
If the employee is at exactly 100.0 meters from the center and the radius is 100m, they
pass . The comparison is distance <= radius (less than or
equal to ). Even 1 meter inside the boundary is a pass. At 100.1 meters, it is a fail.
// From GeofenceService.IsWithinRadius()

Caching Gotcha: maximumAge
Notice in the JavaScript code: maximumAge: 60000 (60 seconds). This means the browser
can return a cached GPS position up to 60 seconds old instead of getting a fresh one. This is
acceptable for check-in (you are not moving between buildings in 60 seconds), but be aware that
if you teleport in DevTools, you may need to wait up to 60 seconds for the new position to take
effect.

The Core Formula
a = sin^2(delta_lat / 2) + cos(lat1) * cos(lat2) * sin^2(delta_lon / 2)
c = 2 * atan2(sqrt(a), sqrt(1 - a))
distance = Earth_Radius * c
Where:
Earth_Radius = 6,371,000 meters
All angles in radians (degrees * pi / 180)

Check-in blocks outside the geofence — check-out records but allows
Haversine, not Pythagorean — the Earth is a sphere
