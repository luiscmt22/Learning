Factory Floor Production System — Technical Documentation

Formal technical documentation for a Blazor Server MES (manufacturing execution system) that tracks production orders, records material consumption with variance analysis, and syncs stock movements to the Primavera ERP.

Real factories run on paper for a reason: paper doesn't crash mid-write and leave you with 700 units of finished product and zero recorded raw-material consumption. To replace paper, your software needs transactions that are atomic across four tables, idempotent against accidental double-clicks, and forgiving enough that a worker with one free hand and a glove on the other can still operate them. Here's how FactoryFloor does it.

Executive summary

This is the formal engineering spec for FactoryFloor, a real-time production-tracking module built on Blazor Server with MudBlazor, EF Core, and an IPrimaveraRepository integration. It documents the Factory_New.razor page (per-machine filtering via route param), the MaterialConsumptionModal with 1.5-second debounced material loading, the FactoryFloorService transaction flow that atomically updates order quantities + consumption tracking + generates ENTSTOCK/SAIDASTOCK/DESP documents, and the PIN-based worker authentication model. The material calculation algorithm uses proportional scaling (perUnitQuantity × quantityProduced) with historical averages as suggestions, and the whole write path is wrapped in an EF Core BeginTransactionAsync for atomicity.

💡
MetaphorFactoryFloor is the cockpit of the factory. The worker taps a machine and sees only that machine's jobs (like filtering to your flight on a busy departures board). Pressing Start is easy; pressing Stop is where the real accounting happens — the modal is a checklist asking 'how much did you actually make, how much did you waste, and how much of each raw material did you actually use?' The submit button is a very slow single click — behind the scenes it's a six-step transaction that has to either fully commit or roll back, because a half-recorded production run would poison the ERP downstream.

1Why it exists

Manufacturing floors need a live view of every production order, the ability to pause/stop/resume jobs per machine, and bulletproof recording of what materials were actually consumed versus what was planned. Without this system, material variance (waste, over-consumption, misallocation) is invisible until the end of the month, and the ERP (Primavera) has no idea what happened on the floor until someone hand-keys it in. This module also exists to give workers a fast, PIN-authenticated way to interact with the system on shared factory tablets without typing full credentials.

2What it does

Shows production orders filtered by machine (via /factory_new/{maquinaid} route), lets workers start, pause, and end production runs with PIN auth, captures actual quantity produced plus waste in a modal, loads the expected materials list based on quantity (with a 1.5s debounce so rapid typing doesn't spam the server), computes variance against the plan and displays historical averages for sanity-checking, and on submission atomically updates the order, records the material consumption, generates the three stock documents (ENTSTOCK for finished goods, SAIDASTOCK for raw materials, DESP for waste), and pushes the movement to Primavera ERP.

3How it works

Factory_New.razor is the main page — it has a maquinaid route parameter and uses a FactoryLayout. It calls IFactoryFloorService.GetProductionOrdersAsync, then filters locally (no server roundtrip) when the machine selection changes. Actions go through RequestPinForAction → PIN dialog → ExecuteProductionAction → service call. MaterialConsumptionModal uses CancellationTokenSource to debounce OnQuantityProducedChanged by 1.5 seconds before calling GetMaterialsForProductionAsync. RegisterProductionAsync in FactoryFloorService wraps everything in context.Database.BeginTransactionAsync: update order.QuantidadeFeita, increment gastoFase.QuantidadeConsumida and NumeroProducoes, call GenerateStockMovementsAsync which creates CrmDocumento + CrmDocumentoDetalhe entries for ENT/SAI/DESP, then commits. The service is registered scoped, with an IDbContextFactory<BioBragaContext> for per-operation contexts and an existingContext parameter pattern to share contexts across nested transaction operations.

Material Calculation Algorithm

GetMaterialsForProductionAsync Logic

// Core calculation for proportional material consumption
var totalPlannedForOrder = mat.gf.Quantidade ?? 0;
var orderQuantity = order.Quantidade ?? 1;
var perUnitQuantity = totalPlannedForOrder / orderQuantity;
var proportionalQty = Math.Round(perUnitQuantity * quantityProduced, 6);
// Historical average consideration
decimal? suggestedQty = null;
if (mat.gf.QuantidadeMedia.HasValue && mat.gf.QuantidadeMedia.Value > 0)
{
suggestedQty = Math.Round(mat.gf.QuantidadeMedia.Value * quantityProduced, 6);
}

Transaction Management

RegisterProductionAsync Transaction Flow

using var transaction = await context.Database.BeginTransactionAsync();
try
{
// 1. Update order quantities
order.QuantidadeFeita += quantityProduced;
order.QuantidadeFalta -= quantityProduced;
// 2. Update consumption tracking
gastoFase.QuantidadeConsumida += material.ActualQuantity;
gastoFase.NumeroProducoes++;
// 3. Generate stock movements
await GenerateStockMovementsAsync(...);
// 4. Commit transaction
await transaction.CommitAsync();
}
catch
{
await transaction.RollbackAsync();
throw;
}

Key takeaways

  • Use IDbContextFactory + existingContext parameter pattern to share transactions across service methods
  • Wrap multi-step production writes in BeginTransactionAsync with a try/catch/rollback — never leave partial state
  • Debounce user input on tablets with CancellationTokenSource.Cancel + new CTS to avoid spam-loading
  • Filter collections client-side in Blazor when the full dataset is already loaded — avoids unnecessary roundtrips
  • PIN authentication belongs at the action-request layer, not the page layer — every sensitive action re-asks
  • Generate ERP documents inside the same transaction as the operational updates so they can't drift
