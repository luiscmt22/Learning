How do you build a factory-floor interface that survives a worker slamming the Enter key ten times, a tablet with patchy wifi, a manager demanding historical variance analysis, and an ERP system that needs every material movement properly documented - all while running transactionally so a crash mid-save never leaves stock half-decremented?

Executive summary

A formal Portuguese-language technical reference for the BioBraga FactoryFloor manufacturing execution system (MES), a Blazor Server + MudBlazor + EF Core application that tracks production orders, material consumption, and stock movements in real time. It documents the three-layer architecture (Presentation/Service/Data), the Factory_New.razor page with its PIN-based worker authentication and machine filtering, the MaterialConsumptionModal with its 1.5-second debounced loading and multi-step transaction flow, and the FactoryFloorService with its transactional stock movement generation (ENTSTOCK/SAIDASTOCK/DESP documents). Also covers Primavera ERP integration, DbContextFactory connection pooling, and variance analysis DTOs.

💡
MetaphorThink of this system as a real-time cashier for a factory kitchen. The worker is the chef, the machine is their station, the production order is a recipe card taped to the counter. When the chef finishes a batch, they punch in their PIN (hashed, like a bank card), say 'I made 47 units using 2.3kg of sugar instead of the planned 2.5kg,' and the cashier - FactoryFloorService - simultaneously marks the recipe done, updates the sugar jar level, prints three receipts (one for finished food, one for sugar used, one for the spilled sugar), and faxes a copy to the accountant at Primavera ERP. If anything goes wrong mid-receipt, the transaction rolls back and nothing is half-done.

1Why it exists

Manufacturing plants need a real-time link between the physical shop floor and the ERP system. Workers on the floor must be able to start, pause, and finish production orders, record actual material consumption versus planned consumption, and have every action automatically generate the correct stock movements (entries, exits, waste documents) in Primavera ERP. Without this bridge, inventory drift occurs, compliance suffers, and managers cannot see what's actually being produced versus what's planned. The system exists to give BioBraga real-time visibility into production orders and to automate the accounting flow that feeds back into Primavera.

2What it does

Provides a Blazor Server interface where authenticated workers (via hashed PIN) can select a machine, see the production orders assigned to it, start/pause/stop production, and submit material consumption data. The MaterialConsumptionModal dynamically loads the required materials proportional to the quantity produced, compares actual versus planned quantities with variance analysis, and displays historical consumption averages. On submission, a database transaction updates the order quantities, decrements material consumption tracking, generates three kinds of stock documents (ENTSTOCK for finished goods, SAIDASTOCK for materials consumed, DESP for waste), and forwards the movements to the Primavera ERP via a repository abstraction.

3How it works

The architecture follows a strict Presentation -> Service -> Data flow. Factory_New.razor is the main page, accepting an optional maquinaid route parameter for machine-specific views; it uses CascadingParameter for the current worker and filters orders locally to avoid server roundtrips. MaterialConsumptionModal uses a CancellationTokenSource-based debounce (1.5 seconds) on the QuantityProduced input to avoid thrashing when workers type values. FactoryFloorService is scoped in DI and receives an IDbContextFactory<BioBragaContext>, an IPrimaveraRepository, and an ILogger. The core transaction in RegisterProductionAsync wraps everything in a BeginTransactionAsync: update order quantities, update gastoFase consumption tracking, generate stock movements via GenerateStockEntryAsync/GenerateStockExitAsync, and CommitAsync - with rollback on any exception. Material calculation uses a simple proportional formula (totalPlannedForOrder / orderQuantity * quantityProduced), optionally using QuantidadeMedia historical averages when present. Context reuse is done via a 'shouldDisposeContext' pattern so nested service calls can share one transaction. Security uses Utils.Hash(pin) for PIN validation and filters by worker.Isactive, with all actions logged to CrmOrdemProducaoLog with a Criadopor field for audit.

Gestão de Transações



Fluxo de Transação RegisterProductionAsync



using var transaction = await context.Database.BeginTransactionAsync();

try

{



       // 1. Atualizar quantidades da ordem

       order.QuantidadeFeita += quantityProduced;

       order.QuantidadeFalta -= quantityProduced;



       // 2. Atualizar rastreamento de consumo

       gastoFase.QuantidadeConsumida += material.ActualQuantity;

       gastoFase.NumeroProducoes++;



       // 3. Gerar movimentos de stock

       await GenerateStockMovementsAsync(...);



       // 4. Confirmar transação

       await transaction.CommitAsync();

}

catch

{

       await transaction.RollbackAsync();

       throw;

}

       // Análise de Variância

       public decimal Variance => ActualQuantity - PlannedQuantity;

       public decimal VariancePercentage =>



              PlannedQuantity != 0 ? (Variance / PlannedQuantity) * 100 : 0;

Key takeaways

  • Use IDbContextFactory<T> for connection pooling in long-lived Blazor Server circuits
  • Wrap multi-step business operations in BeginTransactionAsync for atomicity
  • Debounce input-driven async loads with CancellationTokenSource
  • Filter collections client-side when possible to avoid server roundtrips
  • Use the Repository pattern to abstract external ERP integration from business logic
  • Hash PINs before storage, never compare plaintext
  • Pass a 'shouldDisposeContext' flag when sharing a DbContext across nested service calls
