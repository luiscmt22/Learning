Factory Floor Production System — Technical Documentation

A real-time manufacturing execution system (MES) built in Blazor Server + EF Core that tracks production orders, material consumption with variance analysis, stock movements, and Primavera ERP integration.

Imagine your factory runs on paper and clipboards. Someone writes '60 bottles made' on a clipboard at lunch. By the time that reaches accounting on Friday, three hands have copied it, one typo has slipped in, and nobody knows how much plastic was actually used. Now imagine a worker taps Pause on a tablet, confirms '60 bottles, 6kg plastic, 0 waste', and sixty seconds later stock, production, and ERP are all simultaneously correct. That's the difference this system is built to make.

Executive summary

The Factory Floor Production System is a Blazor Server MES for tracking production orders on a factory floor. It uses a Repository + Service layer pattern where Factory_New.razor is the control dashboard and MaterialConsumptionModal.razor is the recipe-tracking popup. FactoryFloorService orchestrates Start/Pause/End production actions, calculates proportional material consumption based on planned quantity versus actual quantity produced, generates ENTSTOCK/SAIDASTOCK/DESP stock movements inside a database transaction, and pushes the result to Primavera ERP. Worker actions require PIN-based authentication, all changes are audit-logged, and material loading uses a 1.5-second debounce to avoid re-querying on every keystroke.

💡
MetaphorThis system is like a self-checkout kiosk for manufacturing. The worker scans their badge (PIN), picks their job (order), hits Start, makes stuff, and at Pause or Stop the system asks 'how many did you make, how many did you waste?' Then it does everything a human accountant used to do in their head: subtracts the raw materials from the warehouse, adds the finished goods to inventory, records the waste, and mails the receipt to the ERP. The worker just punched two buttons; the accounting department got five perfectly matched entries.

1Why it exists

Manufacturing floors historically ran on paper: workers scribbled production numbers on clipboards, stock counts drifted, managers learned about problems days later. This system replaces all that with a tablet-friendly Blazor interface that tracks each production order in real time from Start to Pause to End, automatically calculates what materials should have been consumed for the actual quantity produced, flags variances, and pushes everything to the Primavera ERP in one atomic operation. The goal is zero double entry — one worker confirmation updates production orders, stock levels, waste records, and accounting simultaneously.

2What it does

Factory_New.razor shows today's stats, a machine selector, and two columns of orders (To Start / Started). URL parameter /factory_new/{maquinaid} bookmarks a specific machine view. When a worker clicks Start/Pause/Stop, a PIN dialog validates them against the hashed CrmUtilizador.Pin, then ExecuteProductionAction calls FactoryFloorService's StartProductionAsync / PauseProductionAsync / EndProductionAsync. Pause and Stop trigger MaterialConsumptionModal which asks for QuantityProduced and Waste, then loads materials — after a 1.5s debounce — via GetMaterialsForProductionAsync which computes perUnitQuantity = totalPlannedForOrder / orderQuantity and suggests proportionalQty = perUnitQuantity * quantityProduced, enriched with a HistoricalAverage when prior QuantidadeMedia exists. The worker confirms, and RegisterProductionAsync runs inside a database transaction that updates order.QuantidadeFeita, decrements order.QuantidadeFalta, bumps gastoFase.QuantidadeConsumida, calls GenerateStockMovementsAsync, and commits — or rolls back on any failure.

3How it works

The service layer uses IDbContextFactory<BioBragaContext> so every operation gets a fresh context (except when passing an existingContext to chain operations inside a transaction). The OrdemProducao composite model bundles CrmOrdemProducao, CrmDocumento, CrmDocumentoDetalhe, CrmArtigo, and a List<ComponenteProd> so the UI has everything it needs in one object. MaterialConsumptionDto exposes computed properties Variance and VariancePercentage so the UI can colour-code over-consumption without server logic. Stock movements generate three document types: ENTSTOCK (finished goods entering stock), SAIDASTOCK (raw materials leaving stock), and DESP (waste). After commit, _primaveraRepo.SendMovimentacaoStock(doc, lines) pushes the movement to the external ERP. If Primavera fails, the local transaction still commits — integration failures are logged but don't block production. Cascading parameters propagate CurrentWorker across the component tree. Local filtering (FilterOrdersByMachine) happens client-side so machine selection doesn't roundtrip to the server.

Transaction Management



RegisterProductionAsync Transaction Flow



using var transaction = await context.Database.BeginTransactionAsync();

try

{



       // 1. Update order quantities

       order.QuantidadeFeita += quantityProduced;

       order.QuantidadeFalta -= quantityProduced;



       // 2. Update consumption tracking

       gastoFase.QuantidadeConsumida += material.ActualQuantity;

       gastoFase.NumeroProducoes++;



       // 3. Generate stock movements

       await GenerateStockMovementsAsync(...);



       // 4. Commit transaction

       await transaction.CommitAsync();

}

catch

{

       await transaction.RollbackAsync();

       throw;

}

Key takeaways

  • A composite DTO (OrdemProducao) that bundles related entities avoids lazy loading surprises
  • Use BeginTransactionAsync + try/catch/rollback whenever a single user action mutates multiple tables
  • Debounce expensive lookups (1.5s delay + CancellationTokenSource) to survive fast typing
  • Proportional material consumption scales by actual quantity but still suggests historical averages
  • ExistingContext parameter lets you chain service calls inside an outer transaction
  • Hash PINs with Utils.Hash and validate IsActive on every authentication check
  • ERP integration should not block the local transaction — log failures and retry
