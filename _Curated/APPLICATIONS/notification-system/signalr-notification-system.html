SignalR Notification System: Multi-Target Real-Time Notifications

How the HRModule notification system uses a dedicated SignalR NotificationHub with cross-database target resolution to push real-time notifications to Users, Groups, Departments, Jobs, or Employee Roles across a multi-tenant architecture.

MD Advanced 1,842 words 9 min read Source: Education/14-SignalR-Notification-System.md

Your admin clicks 'Notify IT Department'. In a single-database app this is a WHERE clause away from the answer. In your multi-tenant system, employees live in CompanyA_DB, users live in LoginDatabase, and the link between them is a third table you have to consult. How do you get from 'deptId = 3' to the SignalR group names of three online users without leaking CompanyB data along the way?

Executive summary

A detailed walkthrough of the multi-target SignalR notification subsystem in the HR module, contrasting it with the simpler AttendanceHub from Part 1. Explains why a second hub was needed (different events, different group scheme), how the NotificationTargetResolver handles the multi-database challenge where users live in the central LoginDatabase but employees/departments/jobs live in per-company databases, and how the group naming convention (User_{id}, Dept_{empresaId}_{deptId}, etc.) keeps targeting precise. Covers the full flow from admin UI through service layer, target resolution, database persistence, and SignalR push. Also explains why a REST controller coexists with the injected service (external systems, mobile apps, background jobs), the junction-table design for multi-target notifications, and offline user support via database persistence plus best-effort push.

💡
MetaphorThis is the difference between a public-address loudspeaker and an intercom with a building directory. The AttendanceHub is the loudspeaker - everyone in the office hears 'Joao checked in'. The NotificationHub is the intercom: type 'IT department at CompanyA' and the system looks up who is actually in that group (across two databases), finds their personal buzzers, and delivers the message privately. Offline employees walk in tomorrow and find the message taped to their desk because it was written down first and broadcast second.

1Why it exists

A simple SignalR hub that broadcasts to everyone is useless in a multi-tenant HR system where users belong to multiple companies and administrators need to notify specific audiences - 'everyone in the IT department of CompanyA' or 'all employees with the Manager role in CompanyB'. The challenge is that users are stored in the central LoginDatabase while departments, jobs, and employees live in per-company databases, so a naive 'send to department 3' cannot find the actual user IDs needed for SignalR group targeting. This system solves the cross-database resolution problem and gives administrators a unified UI for targeting any combination of users, groups, departments, jobs, and employee roles.

2What it does

Lets an admin compose a single notification and target it at any mix of: individual users, user groups, departments, jobs, employee roles, entire companies, or 'All'. The system resolves all these targets into a flat list of unique user IDs (via cross-database joins), persists one notification record per user, and pushes the notification in real-time via SignalR to any currently connected clients. Offline users see the notification on their next login because it was persisted first. Notifications can be sent by Blazor UI components directly (via injected INotificationService) or by external systems, mobile apps, and background jobs (via REST endpoints on NotificationController). The SignalR hub auto-joins every connecting user to the groups they belong to based on their roles, departments, companies, etc.

3How it works

The NotificationHub extends Hub and in OnConnectedAsync adds the connection to 'User_{id}', 'All', optionally 'Admins', one group per company ('Company_{id}'), and groups for each user group, department, job, and role the user belongs to. When the admin clicks send in EnvioGlobal.razor, the Blazor component calls NotificationService.SendNotificationToMultipleTargetsAsync with a DTO listing all chosen target IDs. The service loops through each target type and calls INotificationTargetResolver.GetUserIdsForDepartmentAsync (or Job, Role, etc.), which executes a two-step SQL query: first SELECT Id FROM CrmFuncionarios WHERE DepartamentoId = @deptId on the company database, then SELECT UserId FROM UserEmployeeLinkage WHERE EmployeeId IN (...) AND CompanyDatabase = @db on the central database. All resolved user IDs collect into a HashSet<int> to dedupe. For each unique user, the service creates a Notifications row and calls NotificationHubService.SendNotificationToUserAsync(userId, dto) which invokes _hubContext.Clients.Group($"User_{userId}").SendAsync('ReceiveNotification', dto). The client NotificationBadge.razor component has registered _hubConnection.On<NotificationDto>('ReceiveNotification', ...) and updates its badge count plus shows a Snackbar toast for Error/Warning types. The database schema uses a NOTIFICATION_TARGETS junction table with (TargetType, TargetId) columns instead of JSON arrays for proper indexing and queryability.

Architecture Overview

Why Two Hubs?

We have two separate SignalR hubs for different purposes:

AttendanceHub
├── Purpose: Real-time attendance events
├── Events: CheckIn, CheckOut, AttendanceUpdate
└── Groups: CompanyAttendance_{id}, TeamAttendance_{id}_{teamId}

NotificationHub
├── Purpose: Push notifications to users
├── Events: ReceiveNotification, NotificationMarkedRead
└── Groups: User_{id}, All, Admins, Company_{id}, UserGroup_{gid}_{eid}
            Dept_{eid}_{did}, Job_{eid}_{jid}, Role_{eid}_{rid}

SignalR Groups in Notifications

Group Naming Convention

We use a consistent naming pattern for SignalR groups:

Target Type Pattern Example
All users All All
Admins Admins Admins
Company Company_{id} Company_1
User Group UserGroup_{groupId}_{empresaId} UserGroup_5_1
Department Dept_{empresaId}_{deptId} Dept_1_3
Job Job_{empresaId}_{jobId} Job_1_42
Employee Role Role_{empresaId}_{roleId} Role_1_7
Individual User User_{userId} User_123

Auto-Joining Groups

When a user connects to the NotificationHub, they automatically join relevant groups:

// NotificationHub.cs
public override async Task OnConnectedAsync()
{
    var userId = GetUserId();

    // Always join personal group
    await Groups.AddToGroupAsync(Context.ConnectionId, $"User_{userId}");

    // Join "All" group
    await Groups.AddToGroupAsync(Context.ConnectionId, "All");

    // Join admin group if applicable
    if (await _notificationService.IsUserAdminAsync(userId))
    {
        await Groups.AddToGroupAsync(Context.ConnectionId, "Admins");
    }

    // Join company groups
    var companies = await _notificationService.GetUserCompaniesAsync(userId);
    foreach (var company in companies)
    {
        await Groups.AddToGroupAsync(Context.ConnectionId, $"Company_{company.Id}");
    }

    // Join user groups
    // ... and so on for departments, jobs, roles
}

Problem: When someone sends a notification to "IT Department", how do we find the actual users?

The Solution: NotificationTargetResolver

public interface INotificationTargetResolver
{
    // Resolve targets to user IDs (the magic!)
    Task<List<int>> GetUserIdsForDepartmentAsync(int departmentId, string companyDatabase);
    Task<List<int>> GetUserIdsForJobAsync(int jobId, string companyDatabase);
    Task<List<int>> GetUserIdsForEmployeeRoleAsync(int roleId, string companyDatabase);

    // Check if user belongs to target
    Task<bool> IsUserInDepartmentAsync(int userId, int departmentId, string companyDatabase);

    // Get names for UI display
    Task<string?> GetDepartmentNameAsync(int departmentId, string companyDatabase);
}

Complete Implementation Example

Sending to a Department

Here's the full flow when an admin sends a notification to the IT Department:

1. UI (EnvioGlobal.razor)

@inject INotificationService NotificationService
@inject INotificationTargetResolver TargetResolver

<!-- Admin selects Department tab, picks "IT Department" -->

@code {
    private async Task SendNotification()
    {
        var request = new NotificationToMultipleTargetsDto
        {
            EmpresaId = _selectedEmpresaId,
            CompanyDatabase = _companyDatabase,
            Title = _notificationTitle,
            Message = _notificationMessage,
            Type = _notificationType,
            DepartmentIds = new List<int> { 3 }  // IT Department
        };

        await NotificationService.SendNotificationToMultipleTargetsAsync(
            request,
            UserSession.User.Id);
    }
}

2. Service (NotificationService.cs)

public async Task<bool> SendNotificationToMultipleTargetsAsync(
    NotificationToMultipleTargetsDto request,
    int? fromUserId)
{
    // Collect all unique user IDs from all target types
    var allUserIds = new HashSet<int>();

    // Resolve department targets
    if (request.DepartmentIds?.Any() == true)
    {
        foreach (var deptId in request.DepartmentIds)
        {
            var userIds = await _targetResolver.GetUserIdsForDepartmentAsync(
                deptId, request.CompanyDatabase);
            foreach (var id in userIds) allUserIds.Add(id);
        }
    }

    // ... resolve other target types ...

    // Create notification for each user
    foreach (var userId in allUserIds)
    {
        // Save to database
        var notification = new Notification { /* ... */ };
        _context.Notifications.Add(notification);

        // Push via SignalR
        await _hubService.SendNotificationToUserAsync(userId, notificationDto);
    }

    await _context.SaveChangesAsync();
    return true;
}

3. SignalR Push (NotificationHubService.cs)

public async Task SendNotificationToUserAsync(int userId, NotificationDto notification)
{
    await _hubContext.Clients
        .Group($"User_{userId}")
        .SendAsync("ReceiveNotification", notification);
}

4. Client Receives (NotificationBadge.razor)

@code {
    protected override async Task OnInitializedAsync()
    {
        _hubConnection.On<NotificationDto>("ReceiveNotification", async (notification) =>
        {
            // Update badge count
            _unreadCount++;

            // Show toast for important notifications
            if (notification.Type == "Error" || notification.Type == "Warning")
            {
                Snackbar.Add(notification.Title, Severity.Warning);
            }

            StateHasChanged();
        });
    }
}

Database Schema

New Tables and Columns

-- Added to NOTIFICATIONS table
ALTER TABLE NOTIFICATIONS ADD TO_DEPARTMENT_ID INT NULL;
ALTER TABLE NOTIFICATIONS ADD TO_JOB_ID INT NULL;
ALTER TABLE NOTIFICATIONS ADD TO_EMPLOYEE_ROLE_ID INT NULL;
ALTER TABLE NOTIFICATIONS ADD COMPANY_DATABASE NVARCHAR(100) NULL;

-- New junction table for multi-target notifications
CREATE TABLE NOTIFICATION_TARGETS (
    ID INT IDENTITY(1,1) PRIMARY KEY,
    NOTIFICATION_ID INT NOT NULL,
    TARGET_TYPE NVARCHAR(20) NOT NULL,  -- 'Department', 'Job', 'EmployeeRole', 'UserGroup'
    TARGET_ID INT NOT NULL,
    CREATED_AT DATETIME2 DEFAULT GETDATE(),

    INDEX IX_NotificationTargets_NotificationId (NOTIFICATION_ID),
    INDEX IX_NotificationTargets_Lookup (TARGET_TYPE, TARGET_ID)
);

Why Junction Table Instead of JSON Arrays?

JSON Arrays Junction Table
Can't index Fully indexable
Slow JSON parsing Fast SQL joins
No query optimization Query optimizer works
Violates 1NF Proper normalization

Best Practices

1. Always Validate Targets Before Sending

var userIds = await _targetResolver.GetUserIdsForDepartmentAsync(deptId, companyDb);
if (!userIds.Any())
{
    _logger.LogWarning("Department {DeptId} has no linked users", deptId);
    return false;
}

2. Log All Notification Sends

_logger.LogInformation(
    "Notification sent to {Count} users for Department {DeptId}",
    userIds.Count, deptId);

3. Handle Offline Users Gracefully

  • Notifications are saved to database first
  • Users see them on next login
  • SignalR push is best-effort

4. Set Reasonable Expiration Dates

var notification = new CreateNotificationDto
{
    Title = "Promocao Especial",
    ExpiresAt = DateTime.Now.AddDays(7)  // Auto-cleanup after 7 days
};

5. Use Batch Operations for Multiple Targets

// Good: Single call with multiple targets
await NotificationService.SendNotificationToMultipleTargetsAsync(new NotificationToMultipleTargetsDto
{
    DepartmentIds = new List<int> { 1, 2, 3 },
    JobIds = new List<int> { 10, 20 },
    // ...
});

// Avoid: Multiple individual calls
// foreach (var deptId in deptIds)
//     await NotificationService.SendNotificationToDepartmentAsync(deptId, ...);

Troubleshooting

Notification Not Received?

  1. Check SignalR Connection
  • Green dot in NotificationBadge = connected
  • Browser console for SignalR errors
  1. Verify User is in Correct Group
   // In NotificationHub, log group joins
   _logger.LogInformation("User {UserId} joined {GroupName}", userId, groupName);
  1. Check Database
  • Is notification saved in NOTIFICATIONS table?
  • Is target resolution working? (check logs)
  1. Verify Employee-User Linkage
   SELECT * FROM USER_EMPLOYEE_LINKAGE
   WHERE EmployeeId = @empId AND CompanyDatabase = @db

Connection Drops Frequently?

  • Check server memory/CPU
  • Review SignalR connection limits
  • Consider sticky sessions for load balancers

Key takeaways

  • Use separate hubs for separate concerns (AttendanceHub for attendance, NotificationHub for notifications)
  • Group naming conventions must be consistent and include context (e.g. Dept_{empresaId}_{deptId} not just Dept_{deptId})
  • Auto-join users to their relevant groups in Hub.OnConnectedAsync based on their profile
  • Cross-database resolution needs a UserEmployeeLinkage table that maps central users to per-company employees
  • REST controllers and direct service injection can coexist: Blazor components inject the service, external systems hit the API
  • Use junction tables (NotificationTargets with TargetType/TargetId) not JSON arrays for queryable multi-target data
  • Persist notifications first, push via SignalR second - offline users still see them on next login
  • Always deduplicate resolved user IDs with HashSet before sending
  • Log all target resolutions and send batch operations instead of one-per-target
