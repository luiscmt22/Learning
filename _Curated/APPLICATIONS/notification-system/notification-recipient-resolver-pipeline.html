Notification Recipient Resolver Pipeline

An OCP-compliant strategy pipeline that resolves notification recipients by chaining ordered resolvers (Manager, HRAdmin, future ones) without modifying existing code.

MD Intermediate 918 words 5 min read Source: Education/15-Notification-Recipient-Resolver-Pipeline.md

Picture the kind of switch statement that grows by one case every quarter for two years. Every time a new manager type is added, you have to find that file, find the method, add a case, hope you didn't break the manager logic, redeploy. Now imagine never having to edit that file again. That's what an OCP-compliant pipeline buys you.

Executive summary

This document describes a production strategy-pipeline implementation in an HR system for deciding who gets notified when an employee event occurs. Rather than hardcoding 'send to manager AND HR admins', the system defines an INotificationRecipientResolver interface with an Order property and a GetRecipientUserIdsAsync method, registers multiple resolvers via DI, and orchestrates them through NotificationRecipientService which executes them in order, deduplicates via HashSet, and excludes the action initiator. Two concrete resolvers exist (ManagerRecipientResolver order 10, HRAdminRecipientResolver order 20). Adding a TeamLead resolver requires zero changes to existing code — just a new class and one DI registration.

💡
MetaphorThe recipient pipeline is like a relay race where each runner has a number on their back saying when they run, but they all carry the same baton — the context. Runner 10 is the manager, runner 20 is HR, runner 25 is the department head. You can drop a new runner in at position 15 without re-organizing the rest of the team, and the baton (the recipient set) automatically dedupes so nobody gets two notifications even if two runners both think they should notify the same person.

1Why it exists

The HR system needs to send notifications when events occur (attendance check-in, leave request, schedule change). The naive approach would be a switch statement inside each notification call site listing every recipient type, which violates Open/Closed — every new stakeholder type (team leads, department heads, project managers) requires editing the same method. This grows into a god-method that nobody dares touch.

2What it does

Provides a single GetRecipientsAsync(context) call that returns a deduplicated, ordered list of user IDs to notify. The context carries the triggering EmployeeId, the company database, and an optional ExcludeUserId (typically the user who initiated the action so they don't notify themselves). The pipeline supports manager resolution, HR admin resolution, and is extensible to team leads, department heads, etc., simply by writing a new class.

3How it works

INotificationRecipientResolver defines Order and GetRecipientUserIdsAsync. NotificationRecipientService injects IEnumerable<INotificationRecipientResolver> from the DI container, sorts them by Order, calls each one with the context, collects results into a HashSet<int> (which automatically deduplicates), and filters out ExcludeUserId. ManagerRecipientResolver (order 10) navigates UserEmployeeLinkage -> CrmUtilizador.ReportToUser to find the direct supervisor. HRAdminRecipientResolver (order 20) calls INotificationService.GetAdminUserIdsAsync to fetch users with RoleLevel >= 50. New resolvers register via builder.Services.AddTransient<INotificationRecipientResolver, MyResolver>() with no other code changes.

Notification Recipient Resolver Pipeline

Overview

The Notification Recipient Resolver Pipeline is an OCP-compliant (Open/Closed Principle) system for determining who should receive notifications when events occur in the HR system. Instead of hardcoding recipient logic, it uses a strategy pipeline pattern that allows adding new recipient types without modifying existing code.

Key Components

1. Context Record

// Services/Notifications/Resolvers/INotificationRecipientResolver.cs

public record NotificationRecipientContext(
    int EmployeeId,           // Employee whose action triggered notification
    string CompanyDatabase,   // Company context for data resolution
    int? ExcludeUserId = null // User to exclude (usually the action initiator)
);

2. Resolver Interface

public interface INotificationRecipientResolver
{
    /// <summary>
    /// Order in which this resolver executes (lower = earlier)
    /// </summary>
    int Order { get; }

    /// <summary>
    /// Resolves user IDs that should receive notifications
    /// </summary>
    Task<IEnumerable<int>> GetRecipientUserIdsAsync(NotificationRecipientContext context);
}

3. Orchestrator Service

// Services/Notifications/Resolvers/NotificationRecipientService.cs

public class NotificationRecipientService : INotificationRecipientService
{
    private readonly IEnumerable<INotificationRecipientResolver> _resolvers;

    public async Task<IReadOnlyList<int>> GetRecipientsAsync(NotificationRecipientContext context)
    {
        var recipientIds = new HashSet<int>();

        // Execute resolvers in order
        foreach (var resolver in _resolvers.OrderBy(r => r.Order))
        {
            var ids = await resolver.GetRecipientUserIdsAsync(context);

            foreach (var id in ids)
            {
                if (id != context.ExcludeUserId)
                {
                    recipientIds.Add(id);  // HashSet ensures uniqueness
                }
            }
        }

        return recipientIds.ToList();
    }
}

Current Resolvers

ManagerRecipientResolver (Order: 10)

Resolves the employee's direct manager via the ReportToUser or Reportto field.

Resolution path:

  1. Find UserEmployeeLinkage for the employee
  2. Get the linked user's ReportToUser (or fallback to Reportto)
  3. Return that manager's user ID
// Order 10: Manager is resolved first (most direct supervisor)
public int Order => 10;

public async Task<IEnumerable<int>> GetRecipientUserIdsAsync(NotificationRecipientContext context)
{
    // 1. Find user linked to employee
    var linkage = await baseContext.Set<UserEmployeeLinkage>()
        .FirstOrDefaultAsync(l => l.EmployeeId == context.EmployeeId && ...);

    // 2. Get manager from user's ReportToUser field
    var employeeUser = await baseContext.CrmUtilizadors
        .FirstOrDefaultAsync(u => u.Id == linkage.UserId);

    var managerId = employeeUser?.ReportToUser ?? employeeUser?.Reportto;

    // 3. Return manager ID if found and not excluded
    if (managerId.HasValue && managerId.Value != context.ExcludeUserId)
        recipients.Add(managerId.Value);

    return recipients;
}

HRAdminRecipientResolver (Order: 20)

Resolves all HR administrators (users with system role level >= 50).

// Order 20: HR Admins are resolved after manager
public int Order => 20;

public async Task<IEnumerable<int>> GetRecipientUserIdsAsync(NotificationRecipientContext context)
{
    // Uses INotificationService.GetAdminUserIdsAsync()
    // Returns users with UserSystemRole.RoleLevel >= 50
    var adminIds = await _notificationService.GetAdminUserIdsAsync();

    return adminIds.Where(id => id != context.ExcludeUserId);
}

DI Registration

// Program.cs

// Notification recipient resolvers (SOLID: OCP-compliant pipeline)
builder.Services.AddTransient<INotificationRecipientResolver, ManagerRecipientResolver>();
builder.Services.AddTransient<INotificationRecipientResolver, HRAdminRecipientResolver>();
builder.Services.AddScoped<INotificationRecipientService, NotificationRecipientService>();

Usage Example

In NotificationSchedulerService (Background Service)

// Get recipients using the shared resolver pipeline
var context = new NotificationRecipientContext(employee.Id, company.Database);
var recipients = await recipientService.GetRecipientsAsync(context);

if (!recipients.Any()) continue;

// Send notification to all resolved recipients
foreach (var recipientId in recipients)
{
    await notificationService.SendNotificationToUserAsync(recipientId, notification);
}

In AttendanceNotificationService

public async Task NotifyValidatorsAsync(Attendance attendance, string companyDatabase, int? fromUserId)
{
    var context = new NotificationRecipientContext(
        attendance.EmployeeId,
        companyDatabase,
        fromUserId  // Exclude the person who triggered the action
    );

    var recipients = await _recipientService.GetRecipientsAsync(context);

    var notification = new CreateNotificationDto
    {
        Title = "Nova Presenca para Validar",
        Message = $"{attendance.EmployeeName} registou entrada as {attendance.CheckInTime:HH:mm}.",
        Type = "Task",
        Url = "/Myinfo?tab=inbox"
    };

    foreach (var recipientId in recipients)
    {
        await _notificationService.SendNotificationToUserAsync(recipientId, notification, fromUserId);
    }
}

Key takeaways

  • Inject IEnumerable<TInterface> in ASP.NET DI to receive ALL registered implementations of an interface
  • Use an Order property on each strategy so callers can control execution sequence without coupling
  • HashSet<int> for recipient IDs is the simplest deduplication primitive
  • Pass an ExcludeUserId in the context so action initiators don't notify themselves
  • Adding a new recipient type should be a one-class, one-DI-line change — anything more violates OCP
  • Use record types for context DTOs to get value-equality and immutability for free
