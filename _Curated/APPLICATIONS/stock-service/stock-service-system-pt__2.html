Sistema de Serviço de Stock — O Guia "Para Totós"

A Portuguese 'for dummies' walkthrough of a stock/inventory service that uses a two-layer design — a cached decorator wrapping a real StockService — with time-sensitive cache expiration rules tailored to how old the stock data is.

Your inventory tab takes 3 seconds to load, and your users click it a hundred times a day. Multiply that out — it's a lot of wasted warehouse-counting. What if the second click were instant, and the tenth click still felt instant, without any chance of lying to users when stock actually moves?

Executive summary

This is the Portuguese beginner-friendly explainer for the project's stock-tracking system. It presents the service as a two-layer cake: an outer CachedStockService decorator that checks IMemoryCache first, and an inner StockService that actually talks to the database. The clever bit is time-graded expiration: historical stock (>7 days old) caches for 1 hour because it never changes, while recent stock caches for only 5 minutes because it's still moving, and filtered queries don't cache at all because they're one-off. The doc also covers the Razor UI pattern of pre-loading _stockSummaryTask in OnInitializedAsync so clicking the Stock tab feels instant.

💡
MetaphorThis is the post-it-note trick for inventory. Every time someone asks 'how many do we have of SKU-42?', you normally have to walk into the warehouse and count. Instead, the first person triggers a count and you slap a post-it on the monitor. For the next five minutes, anyone who asks just reads the note — zero walking. Old questions like 'how many did we have last March?' get a thicker post-it that lasts an hour because the past can't change. Weird oddly-specific questions ('how many blue ones came in on the second Tuesday of April?') don't get a note at all — nobody's going to ask that again. The result: 99% of questions cost milliseconds instead of seconds.

1Why it exists

Without this service, every single stock check would mean recomputing sums over the whole movements table — slow, database-hammering, and frustrating for users waiting on reports. The goal is to make stock lookups feel instant even when thousands of users and thousands of items are involved, while keeping historical reporting accurate. It also exists to decouple the UI (which just wants 'how much do I have?') from the database query that answers it.

2What it does

Given an article ID and optionally a date, the service returns the current stock level, the full movement history (each entrada/saída with document reference), and aggregate totals. It supports a 'time machine' query — tell me what stock I had on January 15th — and it answers every query in sub-millisecond time when the answer is cached. Filtered date-range queries bypass the cache because they're too specific to reuse, while 'since-forever' totals and point-in-time snapshots are eagerly cached.

3How it works

Two services are registered: StockService does the real SQL work (SUM entradas, SUM saidas, SUM stock FROM movimentos WHERE data <= X), and CachedStockService is a decorator that wraps it, checking IMemoryCache by a composite key like stock_{artigoId}_{date:yyyyMMdd} before falling through. Cache lifetime is branched on date: older than 7 days gets 1 hour; newer gets 5 minutes; filtered queries get no cache at all. In the Razor ArtigoDetalhe.razor, the Stock tab task is kicked off inside OnInitializedAsync so that by the time the user clicks the tab, the await resolves instantly. Dates are formatted using a Portuguese culture with custom abbreviated day names.

O Que é Caching?



Analogia do mundo real: É como ter post-its na sua secretária!



    • Sem caching: Sempre que alguém pergunta "Qual é o número do João?", você abre a

Como Funciona o Seu Cache Inteligente



public async Task<ArtigoStock?> GetArticleStockByDateAsync(int artigoId,

DateTime date)

{



       // Cria um "nome" único para esta pergunta

       var cacheKey = $"stock_{artigoId}_{date:yyyyMMdd}";



       // Verifica os nossos "post-its" primeiro

       if (_cache.TryGetValue<ArtigoStock>(cacheKey, out var cachedStock))

       {



              // Encontrou! Devolve a resposta guardada (SUPER RÁPIDO!)

              return cachedStock;

       }



       // Não está em cache, precisa calcular

       var stock = await _innerService.GetArticleStockByDateAsync(artigoId,

date);



       // Guarda para a próxima vez com expiração inteligente

       if (date < DateTime.Today.AddDays(-7))



              _cache.Set(cacheKey, stock, TimeSpan.FromHours(1)); // Dados

antigos = cache mais longo



       else

              _cache.Set(cacheKey, stock, TimeSpan.FromMinutes(5)); // Dados



recentes = cache mais curto



       return stock;}

O seu sistema é inteligente sobre QUANDO esquecer dados em cache:



1. Dados Históricos (>7 dias atrás)

         o Cache por 1 HORA

         o Porquê? Stock antigo não muda!

         o Como guardar a lista telefónica do ano passado - não vai mudar



2. Dados Recentes (<7 dias atrás)

         o Cache por 5 MINUTOS

         o Porquê? Stock recente ainda pode estar a mudar

         o Como o horário de entregas de hoje - pode ter atualizações



3. Queries Filtradas

         o NÃO guardadas em cache

         o Porquê? Muito específicas, improvável serem perguntadas novamente

         o Como perguntar "Mostra-me só entregas de terça de itens azuis"

// Registar ambos os serviços

services.AddScoped<StockService>();

services.AddScoped<IStockService>(provider =>

{



       var innerService = provider.GetRequiredService<StockService>();

       var cache = provider.GetRequiredService<IMemoryCache>();

       var logger =

provider.GetRequiredService<ILogger<CachedStockService>>();

       return new CachedStockService(innerService, cache, logger);

});

    Porque Este Design é Brilhante



1. Separação de Responsabilidades



    • StockService: Faz o trabalho real

    • CachedStockService: Gere memória/caching

    • UI (Razor): Apenas exibe dados



2. Padrão Decorator



O serviço com cache "decora" o serviço real:



Pedido → ServiçoCache → (se necessário) → ServiçoStock → BaseDados

                    ↓ (se em cache)



                Devolve imediatamente



3. Pré-carregamento Inteligente



Começa a carregar antes do utilizador precisar = resposta percebida como instantânea!



4. Expiração Graduada de Cache



    • Dados antigos = estáveis = cache mais longo

    • Dados novos = mutáveis = cache mais curto

    • Dados filtrados = únicos = não guardar em cache

Key takeaways

  • Different data ages deserve different cache lifetimes — historical data is stable, recent data is volatile
  • The decorator pattern lets you add caching without touching the underlying service
  • Kicking off the data load in OnInitializedAsync before a tab is clicked makes the UX feel instantaneous
  • Filtered/one-off queries should skip the cache — caching them wastes memory for no hit-rate gain
  • Point-in-time stock is (SUM entradas) − (SUM saídas) up to the given date — a 'time machine' query
