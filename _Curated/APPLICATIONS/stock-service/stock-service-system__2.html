Stock Service System — Technical Documentation

A formal technical spec for a high-performance Stock Service that layers the Decorator Pattern (CachedStockService over StockService) with SQL Server functions, graduated cache expiration, and task pre-loading for perceived-instant UI response.

Here's a riddle: your stock query takes 2 seconds on the server. Your UI feels instant. How? The answer isn't a faster database — it's that the UI asked the database two seconds before the user clicked the button.

Executive summary

The Stock Service provides point-in-time inventory queries backed by a SQL Server table-valued function (fn_ArtigoStockByDate) and a multi-tier caching strategy. It uses the Decorator Pattern to wrap a CachedStockService around the core StockService, applies graduated expiration (1 hour for historical data >7 days old, 5 minutes for recent), and uses fire-and-forget task pre-loading from the Blazor page's OnInitializedAsync so that when a user clicks the stock tab the data is already loaded. It includes connection pooling via IDbContextFactory, LINQ queries with multiple joins for movement history, structured logging, and health checks reporting cache hit rate and memory pressure.

💡
MetaphorThe stock service is like a busy hotel concierge. When a guest asks 'what's available in room 304 tonight?', the concierge first checks the notepad on their desk (in-memory cache). If the answer is scribbled there and less than five minutes old, they rattle it off in a heartbeat. If not, they call housekeeping (the SQL function), get the answer, write it down for next time, and then tell the guest. Oh, and while the guest is still walking up to the desk, the concierge has already made the call anyway (pre-loading) — so 'how long's the wait?' is 'none' almost every time.

1Why it exists

In a typical inventory app, asking 'what is the stock level of article 123 on January 15th?' triggers an expensive aggregation — sum all entries minus all exits up to that date across a document-detail join chain. Doing this on every page load (and every date filter change) melts the database. The Stock Service exists to turn a 2-second query into a 1-ms memory fetch most of the time, while still being able to answer historical queries with point-in-time accuracy. Caching alone would risk stale data; pre-loading alone would still hit the DB on every tab switch. The combination gets users sub-millisecond responses and accepts only the first visit per article per day as the cache-miss cost.

2What it does

The IStockService interface exposes GetArticleStockByDateAsync, GetStockMovementsAsync, GetStockTotalsAsync, and CheckFluxoAsync. StockService (the core implementation) bypasses EF Core for the critical path and calls SELECT * FROM dbo.fn_ArtigoStockByDate(@ArtigoId, @Date) directly via SqlCommand for speed. CachedStockService wraps it and applies graduated expiration: if the date is older than 7 days the data is immutable so cache for 1 hour; otherwise cache for 5 minutes. The Blazor page ArtigoDetalhe.razor starts _stockSummaryTask = StockService.GetCurrentStockAsync(artigo.Id) in OnInitializedAsync — fire and forget. When the user clicks the Stock tab, await _stockSummaryTask usually returns instantly because the task has already completed in the background.

3How it works

A request flows UI -> CachedStockService -> IMemoryCache check with key stock_{artigoId}_{yyyyMMdd}. Cache hit returns in ~1ms. Cache miss descends to StockService which opens a DbConnection from the context factory, builds a SqlCommand with strongly-typed SqlParameter values (preventing injection), executes fn_ArtigoStockByDate, reads the result into an ArtigoStock DTO (ArtigoId, Entrada, Saida, Stock), and returns. CachedStockService then stores the result with the computed expiration before returning to the UI. For movement history, GetStockMovementsAsync uses a LINQ query with joins across CrmDocumentoDetalhes, CrmDocumentos, CrmTipoDocumentos, CrmSerieDocumentos, filters by Movstocks==true and optional date range, orders by document date descending, and returns a list. Filtered movement queries are NOT cached because the keyspace would explode. IMemoryCache is configured with SizeLimit=1000 and CompactionPercentage=0.25 to protect against unbounded memory growth. A StockServiceHealthCheck reports cache hit rate by dividing TotalHits / TotalMisses. Registration in Program.cs uses the factory overload to compose the decorator: register StockService concrete, then register IStockService with a factory that news up CachedStockService(innerService, cache, logger).

System Overview



Purpose



The Stock Service System provides high-performance, real-time inventory tracking with

intelligent caching mechanisms to minimize database load while maintaining data accuracy.



Key Features



    • Real-time stock level queries with point-in-time accuracy

    • Historical stock movement tracking

    • Multi-tier caching with intelligent expiration

    • Async task pre-loading for perceived instant response

    • SQL Server function integration for complex calculations

    • Memory-efficient caching with graduated expiration



Architecture Philosophy



The system implements a Decorator Pattern with separation of concerns:



    • Core Service Layer: Business logic and database operations

    • Caching Layer: Memory management and cache invalidation

    • UI Layer: Presentation and user interaction

public async Task<ArtigoStock?> GetArticleStockByDateAsync(int artigoId,

DateTime date)

{



       // Critical: Add one day for end-of-day inclusion

       var dateWithTime = date.Date.AddDays(1);



       await using var dbContext = await

_contextFactory.CreateDbContextAsync();



       await using var connection = dbContext.Database.GetDbConnection();



       await connection.OpenAsync();



       // Direct SQL function call for performance

       await using var command = connection.CreateCommand();

       command.CommandText = "SELECT * FROM

dbo.fn_ArtigoStockByDate(@ArtigoId, @Date)";

       command.CommandType = CommandType.Text;



       // Strongly-typed parameters prevent SQL injection

       command.Parameters.Add(new SqlParameter("@ArtigoId", SqlDbType.Int) {

Value = artigoId });

       command.Parameters.Add(new SqlParameter("@Date", SqlDbType.DateTime) {

Value = dateWithTime });



       await using var reader = await command.ExecuteReaderAsync();



       if (await reader.ReadAsync())

       {

              return new ArtigoStock

              {

                     ArtigoId = reader.GetInt32(reader.GetOrdinal("ARTIGO_ID")),

                     Entrada = reader.GetDecimal(reader.GetOrdinal("ENTRADA")),

                     Saida = reader.GetDecimal(reader.GetOrdinal("SAIDA")),

                     Stock = reader.GetDecimal(reader.GetOrdinal("STOCK"))

GetStockMovementsAsync



public async Task<List<StockMov>> GetStockMovementsAsync(

       int artigoId,

       DateTime? startDate = null,

       DateTime? endDate = null)



{

       using var dbContext = await _contextFactory.CreateDbContextAsync();



       // Complex LINQ join for movement tracking

       var query = dbContext.CrmDocumentoDetalhes



              .Join(dbContext.CrmDocumentos,

                     detalhe => detalhe.Documentoid,

                     doc => doc.Id,

                     (detalhe, doc) => new { detalhe, doc })



              .Join(dbContext.CrmTipoDocumentos,

                     x => x.doc.Tipodocumentoid,

                     tipo => tipo.Id,

                     (x, tipo) => new { x.detalhe, x.doc, tipo })



              .Join(dbContext.CrmSerieDocumentos,

                     x => x.doc.Serieid,

                     serie => serie.Id,

                     (x, serie) => new { x.detalhe, x.doc, x.tipo, serie })



              .Where(x => x.detalhe.ArtigoId == artigoId && x.tipo.Movstocks ==

true);



       // Dynamic date filtering

       if (startDate.HasValue)



              query = query.Where(x => x.doc.Data >= startDate.Value.Date);



       if (endDate.HasValue)

              query = query.Where(x => x.doc.Data <=



endDate.Value.Date.AddDays(1).AddSeconds(-1));



       return await query

              .Select(x => new StockMov

              {

                     ArtigoId = x.detalhe.ArtigoId,

                     doc = x.doc,

                     docdetalhe = x.detalhe,

                     doctipo = x.tipo,

                     docserie = x.serie

              })

              .OrderByDescending(s => s.doc.Data)

              .ToListAsync();



}

Graduated Expiration Strategy



public async Task<ArtigoStock?> GetArticleStockByDateAsync(int artigoId,

DateTime date)

{



       var cacheKey = $"stock_{artigoId}_{date:yyyyMMdd}";



       // L1 Cache: Memory Check

       if (_cache.TryGetValue<ArtigoStock>(cacheKey, out var cachedStock))

       {



              _logger.LogDebug("Stock cache hit for article {ArtigoId} at date

{Date}",



                     artigoId, date);

              return cachedStock;

       }



       // L2: Database Query

       var stock = await _innerService.GetArticleStockByDateAsync(artigoId,

date);



if (stock != null)



{



   // Intelligent expiration based on data age



   var cacheExpiration = date.Date < DateTime.Today.AddDays(-7)



   ? TimeSpan.FromHours(1)         // Historical: 1 hour



   : TimeSpan.FromMinutes(5); // Recent: 5 minutes



       _cache.Set(cacheKey, stock, cacheExpiration);

}



       return stock;

}

(



       @ArtigoId INT,

       @Date DATETIME

)

RETURNS TABLE

RETURN

(

       SELECT



              @ArtigoId as ARTIGO_ID,

Best Practices



Do's



    • Always use IDbContextFactory for database operations

    • Implement graduated cache expiration based on data stability

    • Pre-load expensive operations when possible

    • Use structured logging for debugging

    • Monitor cache hit rates



Don'ts



    • Don't cache filtered queries (too specific)

    • Don't cache mutable data for long periods

    • Don't forget to handle cache misses gracefully

    • Don't use synchronous database operations

    • Don't ignore memory pressure warnings



Future Enhancements



Proposed Improvements



    1. Redis Integration: Distributed caching for multi-server deployments

    2. GraphQL Support: More efficient data fetching for complex queries

    3. Event-Driven Invalidation: Real-time cache updates via SignalR

    4. Predictive Pre-Loading: ML-based prediction of user behavior

    5. Compression: Compress large cached objects to save memory

Key takeaways

  • Decorator Pattern lets you bolt caching onto a service without touching its code
  • Graduated cache expiration: 1 hour for historical, 5 minutes for recent — data stability drives cache duration
  • Bypass EF Core for hot-path queries by calling SQL functions directly with SqlParameter
  • Fire-and-forget pre-loading in OnInitializedAsync makes 'the data is already there' the common case
  • Don't cache filtered queries — the cache key space explodes
  • Always use IDbContextFactory in services; it handles pooling for you
  • Health checks should report cache hit rate, not just 'service is up'
