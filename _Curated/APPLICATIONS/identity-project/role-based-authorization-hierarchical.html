Role-Based Authorization - From Boolean Flags to Hierarchical Roles

Migration guide from inline boolean role flags (IsSuperAdmin, IsAdmin, IsManager) to a database-driven SystemRole table with numeric Levels that enable hierarchical 'admin or above' checks.

MD Beginner 524 words 3 min read Source: Education/02-Role-Based-Authorization.md

How do you check 'is this user admin or above' when your User class has separate IsAdmin and IsManager bool flags? The honest answer is: with a tangle of OR conditions that breaks every time someone adds a new role. There's a better way, and it's just one numeric column.

Executive summary

This document explains why GivingCare moved away from boolean role flags on the User entity (IsSuperAdmin, IsAdmin, IsManager) and toward a SystemRole table with a numeric Level column (100/80/60/40). The numeric levels enable elegant hierarchical checks like RoleLevel >= 80 meaning 'admin or above'. AuthorizationService.GetUserRoleAsync returns the highest active role for a user, AuthenticatedComponentBase exposes IsSuperAdmin/IsAdminOrAbove/IsManagerOrAbove convenience properties, and CanAssignRoleAsync enforces that admins can only assign roles below their own. Includes a migration cheat sheet for translating old user.IsAdmin checks into the new pattern.

💡
MetaphorBoolean role flags are like a coatroom where each coat has a sticker that says 'gold member' or 'silver member' or 'bronze member' - you have to check every sticker to know who's most senior. The hierarchical Level approach is like giving every coat a number from 0 to 100 - now 'gold or above' is just 'number >= 80' and you don't need to enumerate every tier individually.

1Why it exists

The old pattern stored IsSuperAdmin, IsAdmin, IsManager as bools directly on the User entity. This made it impossible to express 'admin or above', forced schema changes for every new role, gave no audit trail of who assigned which role, and could leave a user inconsistently flagged as both admin and manager. The team needed something that scaled and was auditable.

2What it does

Defines a SystemRole table with Id, Code, and Level columns (SuperAdmin=100, Admin=80, Manager=60, User=40), plus a UserSystemRole join table that records who has which role. AuthorizationService.GetUserRoleAsync queries the join, picks the highest Level for the user, and maps it to a UserRole enum. AuthenticatedComponentBase loads the role in OnInitializedAsync and exposes IsSuperAdmin/IsAdminOrAbove/IsManagerOrAbove properties so Razor pages can do @if (IsAdminOrAbove) { ... }. CanAssignRoleAsync enforces that you can only assign roles strictly below your own.

3How it works

GetUserRoleAsync joins UserSystemRoles to SystemRole, filters by IsActive, orders by Level descending, takes the first, and returns the corresponding UserRole enum value via a switch on Level. AuthenticatedComponentBase stores the result in CurrentUserRole and RoleLevel. Razor pages inherit the base and use IsAdminOrAbove instead of querying the database. CanAssignRoleAsync uses a switch on the assigner's role: SuperAdmin can assign anything, Admin can assign Manager or below, Manager can only assign Regular users.

Role-Based Authorization Explained

The Old Way (Boolean Flags)

Previously, roles were stored as boolean flags directly on the User:

// OLD - Don't do this anymore
public class CrmUtilizador
{
    public bool IsSuperAdmin { get; set; }
    public bool Isadmin { get; set; }
    public bool Ismanager { get; set; }
}

// Check was simple but inflexible
if (user.Isadmin) { ... }

Problems with Boolean Flags

  1. No hierarchy: Can't easily check "admin or above"
  2. Hard to extend: Adding new roles requires schema changes
  3. No audit trail: Can't track who assigned roles
  4. Multiple roles: User could be both admin and manager (inconsistent)

The New Way (Database Roles)

Role Table

SystemRole
├── Id: 1, Code: 'SUPER_ADMIN', Level: 100
├── Id: 2, Code: 'ADMIN', Level: 80
├── Id: 3, Code: 'MANAGER', Level: 60
└── Id: 4, Code: 'USER', Level: 40

User-Role Assignment

UserSystemRole
├── UserId: 123, RoleId: 2 (Admin)
├── UserId: 456, RoleId: 3 (Manager)
└── UserId: 789, RoleId: 4 (User)

Benefits

  1. Hierarchical checks: Level >= 80 means "Admin or above"
  2. Extensible: Add new roles without code changes
  3. Audit trail: Track when/who assigned roles
  4. Single role: Each user has one highest role

How It Works in Code

1. Service Layer

public class AuthorizationService : IAuthorizationService
{
    public async Task<UserRole> GetUserRoleAsync(int userId)
    {
        var assignment = await _context.UserSystemRoles
            .Include(usr => usr.Role)
            .Where(usr => usr.UserId == userId && usr.IsActive)
            .OrderByDescending(usr => usr.Role.Level)
            .FirstOrDefaultAsync();

        if (assignment?.Role == null) return UserRole.Regular;

        return assignment.Role.Level switch
        {
            >= 100 => UserRole.SuperAdmin,
            >= 80 => UserRole.Admin,
            >= 60 => UserRole.Manager,
            _ => UserRole.Regular
        };
    }
}

2. Base Component

public class AuthenticatedComponentBase : ComponentBase
{
    [Inject] protected IAuthorizationService AuthorizationService { get; set; }

    protected UserRole CurrentUserRole { get; private set; }
    protected int RoleLevel { get; private set; }

    // Convenience properties
    protected bool IsSuperAdmin => RoleLevel >= 100;
    protected bool IsAdminOrAbove => RoleLevel >= 80;
    protected bool IsManagerOrAbove => RoleLevel >= 60;

    protected override async Task OnInitializedAsync()
    {
        CurrentUserRole = await AuthorizationService.GetUserRoleAsync(UserId);
        RoleLevel = (int)CurrentUserRole;
    }
}

3. Page Usage

@inherits AuthenticatedComponentBase

@if (IsSuperAdmin)
{
    <MudButton Color="Color.Error">Delete System</MudButton>
}

@if (IsAdminOrAbove)
{
    <MudButton>Manage Users</MudButton>
}

@if (IsManagerOrAbove)
{
    <MudButton>View Team Reports</MudButton>
}

<!-- All authenticated users can see this -->
<MudButton>My Profile</MudButton>

Role Assignment Rules

Super Admin can create:  Super Admin, Admin, Manager, User
Admin can create:        Manager, User
Manager can create:      User
User can create:         Nothing
// In AuthorizationService
public async Task<bool> CanAssignRoleAsync(int assignerId, UserRole targetRole)
{
    var assignerRole = await GetUserRoleAsync(assignerId);

    return assignerRole switch
    {
        UserRole.SuperAdmin => true, // Can assign any
        UserRole.Admin => targetRole <= UserRole.Manager,
        UserRole.Manager => targetRole == UserRole.Regular,
        _ => false
    };
}

Migration Checklist

When updating code from boolean flags to role checks:

Old Pattern New Pattern
user.IsSuperAdmin IsSuperAdmin (base class)
user.Isadmin == true IsAdminOrAbove (base class)
user.Ismanager IsManagerOrAbove (base class)
Direct DB query for admin Query UserSystemRoles with Level >= 80

Key takeaways

  • Boolean role flags on User make 'role or above' checks ugly and force schema changes for every new role
  • A SystemRole table with a numeric Level column enables clean hierarchical checks like Level >= 80
  • AuthenticatedComponentBase loads the role once in OnInitializedAsync and exposes IsAdminOrAbove convenience properties
  • CanAssignRoleAsync should enforce that you can only assign roles strictly below your own level
  • OrderByDescending(Level).FirstOrDefault gives you the highest active role for a user
  • Database-driven roles enable an audit trail of who assigned which role to whom
