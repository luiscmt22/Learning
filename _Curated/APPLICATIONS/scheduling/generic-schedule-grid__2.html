Generic Schedule Grid - For Dummies

Refactoring story of a 2000-line Razor schedule grid into a single GenericScheduleGrid<TSchedule> backed by four IScheduleGridDataProvider implementations - one component, four views, no copy-paste.

MD Intermediate 1,316 words 7 min read Source: Education/ForDummies/09-GenericScheduleGrid-ForDummies.md

How do you avoid maintaining 8000 lines of copy-pasted Razor when business asks for the same grid 'but inverted'? You stop writing components for entities and start writing components for shapes. This is the story of how four schedule views became one generic grid plus four 30-line wrappers.

Executive summary

This document describes how the team turned what would have been four near-identical 2000-line Razor schedule components (Job to Employees, Job to Equipment, Employee to Jobs, Equipment to Jobs) into a single generic GenericScheduleGrid<TSchedule> component. The grid delegates data fetching and saving to an injected IScheduleGridDataProvider, and each of the four views supplies its own provider. Rows implement IScheduleGridRow so the grid can render Employees, Equipment, or Jobs uniformly without knowing what they are. Schedules implement IScheduleEntry so the grid can compute hours and detect overlaps generically. Adding a fifth view (Team -> Employees) means writing one provider and one wrapper - no changes to the grid itself.

💡
MetaphorGenericScheduleGrid is like a universal picture frame that doesn't care what painting you put in it - oil, watercolor, photograph, child's crayon drawing - it just needs the painting to have a width, a height, and a way to hang. The data providers are the curators who know which paintings live in which gallery and how to take them off the wall, while the wrapper components are the gallery labels that say 'this frame currently shows the Renaissance collection.'

1Why it exists

The team had a beautiful schedule grid showing Employees on Jobs but needed three more views: Equipment on Jobs, Jobs on Employee, and Jobs on Equipment. The naive copy-paste approach would have produced 8000+ lines to maintain, with bug fixes and feature requests needing four touches each. They needed one component that worked for all four perspectives.

2What it does

GenericScheduleGrid<TSchedule> renders a row-and-column schedule editor where the rows can be any IScheduleGridRow, the cells contain any IScheduleEntry, and all data fetching is delegated to an injected IScheduleGridDataProvider<TSchedule>. Four data providers (JobEmployeeScheduleDataProvider, JobEquipmentScheduleDataProvider, EmployeeJobScheduleDataProvider, EquipmentJobScheduleDataProvider) each know how to ask the database for the rows and schedules of one specific perspective. Thin wrapper components (JobEmployeeScheduleTab, JobEquipmentScheduleTab, EmployeeScheduleTab, EquipmentScheduleTab) just configure the generic grid with the right provider and ContextId.

3How it works

The IScheduleGridDataProvider<TSchedule> contract requires GetRowsAsync, GetSchedulesAsync, CreateNewSchedule, and CRUD methods. JobEmployeeScheduleDataProvider's GetRowsAsync queries JobEmployee where JobId == jobId; EmployeeJobScheduleDataProvider's GetRowsAsync queries the same join table but filtered by EmployeeId. IScheduleGridRow exposes RowId, RowLabel, RowIcon, NavigationUrl so the grid can render any entity uniformly. IScheduleEntry exposes ScheduleDate, CheckInTime, CheckOutTime, IsCrossMidnightShift, OverlapsWith() so the grid can compute hours and warn about conflicts without caring whether it's an employee or equipment schedule. Adding a new view is four steps: write the provider, register it in DI, write a wrapper that injects it, drop it on the page.

Generic Schedule Grid - For Dummies

The Real-World Problem

We had a beautiful schedule grid that showed Employees on Jobs:

         | Mon 16 | Tue 17 | Wed 18 | Thu 19 |
---------+--------+--------+--------+--------+
Employee1| 08-17  |        | 08-17  |        |
Employee2|        | 08-17  | 08-17  | 08-17  |

But then we needed:

  • Equipment on Jobs (same view, but equipment instead of employees)
  • Jobs on Employee (inverted: see all jobs where Employee X is assigned)
  • Jobs on Equipment (inverted: see all jobs where Equipment Y is assigned)

The naive approach: Copy-paste the 2000+ line JobsScheduleView.razor four times.

The problem:

  • 8000+ lines to maintain
  • Bug fix? Fix it in 4 places
  • Feature request? Add it in 4 places
  • Nightmare!

The smart approach: One generic component that works for ALL four views.

How It Works

Step 1: The Data Provider Contract

Every data provider "signs a contract" promising to implement these methods:

public interface IScheduleGridDataProvider<TSchedule>
{
    // "Tell me who goes in the rows"
    Task<List<IScheduleGridRow>> GetRowsAsync(int contextId, string companyDatabase);

    // "Tell me the schedules for the date range"
    Task<List<TSchedule>> GetSchedulesAsync(int contextId, DateTime start, DateTime end, ...);

    // "Create a new schedule when user clicks a cell"
    TSchedule CreateNewSchedule(int contextId, int rowId, string rowLabel, DateTime date);

    // "Save this schedule"
    Task<ServiceResult> CreateScheduleAsync(TSchedule schedule, ...);
    Task<ServiceResult> UpdateScheduleAsync(TSchedule schedule, ...);
    Task<ServiceResult> DeleteScheduleAsync(int scheduleId, ...);
}

Step 2: Each View Has Its Own Provider

JobEmployeeScheduleDataProvider (Job → Employees):

// GetRowsAsync returns: Employees assigned to this Job
var employees = context.Set<JobEmployee>()
    .Where(je => je.JobId == jobId && je.IsActive)
    .Select(je => je.Employee)
    .ToList();

// GetSchedulesAsync queries: JobSchedule table
var schedules = context.Set<JobSchedule>()
    .Where(s => s.JobId == jobId && s.ScheduleDate >= start && s.ScheduleDate <= end)
    .ToList();

EmployeeJobScheduleDataProvider (Employee → Jobs):

// GetRowsAsync returns: Jobs where this Employee is assigned
var jobs = context.Set<JobEmployee>()
    .Where(je => je.EmployeeId == employeeId && je.IsActive)
    .Select(je => je.Job)
    .ToList();

// GetSchedulesAsync queries: Same JobSchedule table, different filter
var schedules = context.Set<JobSchedule>()
    .Where(s => s.EmployeeId == employeeId && s.ScheduleDate >= start && ...)
    .ToList();

Step 3: The Generic Grid Uses the Provider

<GenericScheduleGrid TSchedule="JobSchedule"
                    ContextId="@JobId"
                    DataProvider="@_dataProvider"
                    CompanyDatabase="@CompanyDb"
                    UserId="@UserId" />

The grid doesn't know or care about:

  • What type of entity the rows represent
  • Where the schedules are stored
  • The specific database queries

It just asks the provider: "Give me rows" and "Give me schedules."

The Row Abstraction

Every row (Employee, Equipment, or Job) looks the same to the grid:

public interface IScheduleGridRow
{
    int RowId { get; }              // Employee 123, Equipment 456, Job 789
    string RowLabel { get; }         // "John Doe", "Excavator-001", "Project Alpha"
    string RowIcon { get; }          // "person", "build", "work"
    string? RowSecondaryLabel { get; } // Optional subtitle
    string NavigationUrl { get; }    // "/employees/123", "/equipments/456"
}

The grid renders:

[icon] RowLabel        | Mon | Tue | Wed | Thu |
       RowSecondaryLabel

Wrapper Components (The Easy Part)

We create thin "wrapper" components that configure the generic grid:

JobEmployeeScheduleTab.razor:

@inject JobEmployeeScheduleDataProvider DataProvider

<GenericScheduleGrid TSchedule="JobSchedule"
                    ContextId="@JobId"
                    DataProvider="@DataProvider"
                    RowHeaderLabel="Colaborador" />

@code {
    [Parameter] public int JobId { get; set; }
    // ... other parameters
}

EmployeeScheduleTab.razor:

@inject EmployeeJobScheduleDataProvider DataProvider

<GenericScheduleGrid TSchedule="JobSchedule"
                    ContextId="@EmployeeId"
                    DataProvider="@DataProvider"
                    RowHeaderLabel="Obra" />

@code {
    [Parameter] public int EmployeeId { get; set; }
    // ... other parameters
}

The magic: Same grid component, different providers, different views!

Adding a New View (Example: Teams → Employees)

Want to show which employees are in a team, with their schedules?

Step 1: Create the provider

// Services/Core/Scheduling/DataProviders/TeamEmployeeScheduleDataProvider.cs
public class TeamEmployeeScheduleDataProvider : IScheduleGridDataProvider<TeamSchedule>
{
    public string EntityType => "Team";

    public async Task<List<IScheduleGridRow>> GetRowsAsync(int teamId, ...)
    {
        // Query TeamMembers to get employees in this team
    }

    public async Task<List<TeamSchedule>> GetSchedulesAsync(int teamId, ...)
    {
        // Query team schedules
    }

    // ... other methods
}

Step 2: Register in Program.cs

builder.Services.AddScoped<TeamEmployeeScheduleDataProvider>();

Step 3: Create wrapper component

@inject TeamEmployeeScheduleDataProvider DataProvider

<GenericScheduleGrid TSchedule="TeamSchedule"
                    ContextId="@TeamId"
                    DataProvider="@DataProvider"
                    RowHeaderLabel="Membro" />

Step 4: Add to your page

Done! No changes to GenericScheduleGrid.razor needed.

Why This Design Rocks

Before (Without Abstraction)

  • 4 separate schedule components
  • 8000+ lines of duplicated code
  • Bug fix = edit 4 files
  • New feature = implement 4 times

After (With Generic Grid)

  • 1 schedule component + 4 thin providers
  • ~1500 lines total
  • Bug fix = edit 1 file
  • New feature = implement once

Adding New Entity Types

Before: Copy-paste entire component, rename everything, pray you didn't miss anything

After:

  1. Create new DataProvider (~200 lines)
  2. Create wrapper component (~30 lines)
  3. Register in DI
  4. Use it!

The Schedule Entry Interface

Both JobSchedule and JobEquipmentSchedule implement:

public interface IScheduleEntry
{
    int Id { get; }
    int JobId { get; }
    int EntityId { get; }           // EmployeeId OR EquipmentId
    DateTime ScheduleDate { get; }
    DateTime? EndDate { get; }
    TimeSpan? CheckInTime { get; }
    TimeSpan? CheckOutTime { get; }

    // Computed properties
    bool IsCrossMidnightShift { get; }
    decimal CalculatedTotalHours { get; }
    bool OverlapsWith(IScheduleEntry other);
}

This means the generic grid can:

  • Display any schedule type in cells
  • Calculate hours
  • Detect overlaps
  • Handle cross-midnight shifts

All without knowing if it's an employee or equipment schedule!

Quick Reference

Want to show Employees on a Job? → Use JobEmployeeScheduleTab with JobId

Want to show Equipment on a Job? → Use JobEquipmentScheduleTab with JobId

Want to show Jobs for an Employee? → Use EmployeeScheduleTab with EmployeeId

Want to show Jobs for Equipment? → Use EquipmentScheduleTab with EquipmentId

Remember

  1. The grid is generic - It works with any schedule type
  2. Providers do the work - They know WHERE the data lives
  3. Wrappers are thin - Just configuration, no logic
  4. One codebase - Fix once, works everywhere
  5. Extensible - New views = new provider, not new grid

Key takeaways

  • When you find yourself about to copy-paste a component, look for a generic type parameter and a strategy interface instead
  • Wrapper components should be thin - just inject a provider and configure the generic component
  • Interfaces like IScheduleGridRow let totally different entities (Employees, Equipment, Jobs) be rendered by the same UI code
  • ContextId is the 'fixed axis' (the entity the user is viewing), RowId is what appears in each row
  • Adding a new view should mean writing a provider, not modifying the generic component
  • Razor supports generic type parameters via TSchedule, making this pattern work in markup
