Blazor Server Architecture and Security Guide

A comprehensive guide covering architecture patterns (base classes, EF configurations, ServiceResult, Adapter, bulk operations), security fundamentals (roles, BCrypt, sessions, CSRF, claims), and Blazor-specific gotchas (ProtectedLocalStorage, localization, JS interop).

PDF Intermediate 6,090 words 30 min read Source: Education/Basics/Blazor_Architecture_and_Security_Guide.pdf

You can build a Blazor app that 'works' in about an afternoon. Building one that survives its third feature request, its first security audit, and its first prerender crash at 2am — that takes the twelve decisions in this guide.

Executive summary

This 13-chapter guide walks through the full stack of patterns you need for an enterprise Blazor Server application, from DRY inheritance hierarchies and EF Core configuration classes to the ServiceResult pattern for error handling and the Adapter pattern for model-agnostic modules. Part II covers security without ASP.NET Identity using custom claims, BCrypt, session tokens, and antiforgery. Part III tackles the prerendering trap: why ProtectedLocalStorage and JS interop crash in OnInitializedAsync and must defer to OnAfterRenderAsync.

Chapter 1: Understanding Base Classes



1.1 The Problem: Code Duplication



Look at typical entity classes without inheritance:



             public class Board

             {



                    public int Id { get; set; }

                    public DateTime CreatedAt { get; set; }

                    public DateTime? UpdatedAt { get; set; }

                    // ... other properties

             }



             public class TaskItem

             {



                    public int Id { get; set; }

                    public DateTime CreatedAt { get; set; }

                    public DateTime? UpdatedAt { get; set; }

                    // ... other properties

             }



             public class Tag

             {



                    public int Id { get; set; }

                    // No audit fields here - inconsistent!

             }



Problems with this approach:



      • Code duplication - We repeat Id, CreatedAt, UpdatedAt in every entity

      • Inconsistency - Some entities have audit fields, some don't

      • Maintenance nightmare - Adding CreatedById requires modifying every entity



1.2 The Solution: Inheritance



We create base classes that contain common properties:



             // Level 1: Every entity has an ID

             public abstract class BaseEntity

             {



                    public int Id { get; set; }

             }



             // Level 2: Entities that track who created/modified them

             public abstract class BaseAuditableEntity : BaseEntity

             {



                    public DateTime CreatedAt { get; set; }

                    public int? CreatedById { get; set; }

                    public DateTime? UpdatedAt { get; set; }

                    public int? UpdatedById { get; set; }

             }



Now entities become cleaner:



             public class Board : BaseAuditableEntity

             {



                    public string Name { get; set; }

                    public string? Description { get; set; }

                    public bool IsArchived { get; set; }

                    // Id, CreatedAt, CreatedById, etc. are inherited!

             }
Page 5
1.3 Why abstract?



The abstract keyword means you cannot create an instance of the class directly. It only exists to be

inherited by other classes.



             // This won't compile

             var entity = new BaseEntity();



             // This works

             var board = new Board();



Why? A "BaseEntity" by itself is meaningless. It's not a board, not a task, not a user. It's just a template for

other classes.



1.4 Why Two Levels?



Not every entity needs audit fields:

Level 1 - BaseEntity (just Id) - For simple entities like:



      • Role - System-defined, no need to track who created them

      • Permission - Same as roles

      • Join tables like TaskTag - Just relationships, not independent entities

Level 2 - BaseAuditableEntity (Id + audit fields) - For business entities:

      • Board, TaskItem, User - Need to know who created/modified them



1.5 The DRY Principle



DRY = Don't Repeat Yourself



Before:    Id, CreatedAt, UpdatedAt, Name, Description, IsArchived

Board:     Id, CreatedAt, UpdatedAt, Title, Description, Priority

TaskItem:  Id, CreatedAt, UpdatedAt, Name, Color

Tag:       Id, CreatedAt, UpdatedAt, Email, UserName, PasswordHash

User:



After:



BaseAuditableEntity: Id, CreatedAt, CreatedById, UpdatedAt, UpdatedById



sss Board:                   Name, Description, IsArchived



sss TaskItem: Title, Description, Priority



sss Tag:                     Name, Color



sss User:                    Email, UserName, PasswordHash



1.6 Real-World Benefit: Adding Features



Imagine adding soft delete (mark as deleted instead of actually deleting):



Without base classes: Modify 10+ entity files



With base classes:

2.1 Where Do We Define Database Rules?



EF Core needs to know: Which properties are required? What's the maximum length? How are entities

related? What columns should be indexed? There are three approaches:



Approach 1: Data Annotations (Simple but Limited)



             public class User

             {



                    public int Id { get; set; }



                    [Required]

                    [MaxLength(256)]

                    [EmailAddress]

                    public string Email { get; set; }

             }



Cons: Mixes domain model with database concerns, limited capabilities, clutters entity class.



Approach 2: Fluent API in OnModelCreating (Messy)



             protected override void OnModelCreating(ModelBuilder modelBuilder)

             {



                    modelBuilder.Entity<User>(entity =>

                    {



                            entity.HasKey(e => e.Id);

                            entity.Property(e => e.Email).IsRequired().HasMaxLength(256);

                            // ... 20 more lines per entity

                    // 10 more entities = 500+ lines!

             }



Cons: OnModelCreating becomes huge, hard to find configurations.



Approach 3: Separate Configuration Classes (Recommended)

Return Null



             public async Task<User?> CreateUserAsync(CreateUserDto dto)

             {



                    if (await EmailExists(dto.Email))

                            return null; // Why null? Email? Validation? Database?

Problem: Caller doesn't know why it failed.



Throw Exceptions

3.3 The Solution: ServiceResult Pattern



             public class ServiceResult<T>

             {



                    public bool Success { get; private set; }

                    public T? Data { get; private set; }

                    public string? Message { get; private set; }

                    public List<string> Errors { get; private set; } = [];



                    public static ServiceResult<T> Ok(T data, string? message = null)

                    {



                            return new ServiceResult<T>

                            {



                                   Success = true,

                                   Data = data,

                                   Message = message

                            };

                    }



                    public static ServiceResult<T> Fail(string error)

                    {



                            return new ServiceResult<T>
Page 11
                            {

                                   Success = false,

                                   Message = error,

                                   Errors = [error]



                            };

                    }



                    public static ServiceResult<T> Fail(List<string> errors)

                    {



                            return new ServiceResult<T>

                            {



                                   Success = false,

                                   Message = errors.FirstOrDefault(),

                                   Errors = errors

                            };

                    }

             }



3.4 Using ServiceResult in Services



             public async Task<ServiceResult<UserDto>> CreateUserAsync(CreateUserDto dto)

             {



                    // Validation

                    if (await EmailExistsAsync(dto.Email))



                            return ServiceResult<UserDto>.Fail("Email already exists");



                    var (isStrong, message) = _passwordService.ValidateStrength(dto.Password);

                    if (!isStrong)



                            return ServiceResult<UserDto>.Fail(message);



                    // Create user

                    var user = new User

                    {



                            Email = dto.Email,

                            UserName = dto.UserName,

                            PasswordHash = _passwordService.Hash(dto.Password)

                    };



                    await _context.Users.AddAsync(user);

                    await _context.SaveChangesAsync();



                    // Success

                    return ServiceResult<UserDto>.Ok(MapToDto(user), "User created successfully");

             }

Chapter 4: The Adapter Pattern & Model Agnostic

Design



4.1 The Problem: Tight Coupling



Imagine you're building an LMS (Learning Management System). You need to track which users are

enrolled in courses:



             public class EnrollmentService

             {



                    public async Task EnrollUserAsync(User user, int courseId)

                    {



                            var enrollment = new Enrollment

                            {



                                   UserId = user.Id,

                                   UserEmail = user.Email, // Directly accessing User properties

                                   UserName = user.UserName,

                                   CourseId = courseId

                            };

                    }

             }



Problems with this approach:



      • LMS is tightly coupled to the User class

      • Want to use LMS with employees from another system? Rewrite everything.

      • If User changes? LMS breaks.

      • Want to extract LMS as standalone project? Can't - it depends on User.



4.2 Real-World Analogy: The Power Plug Converter



When you travel to Europe from the US, your phone charger won't fit the wall outlets. Different shapes,

different voltages. The solution? A power adapter (converter) that translates between two incompatible

interfaces.

4.3 The Adapter Pattern in Code



Step 1: Define What You Need (The Interface)



Instead of depending on User directly, the LMS defines what it needs from a learner:



             // Services/LMS/Abstractions/ILmsLearner.cs

             public interface ILmsLearner

             {



                    int Id { get; }

                    string Name { get; }

                    string Email { get; }

                    string? AvatarUrl { get; }

             }



This is the "universal plug" - any user system can implement this.



Step 2: Create the Adapter (The Converter)

Create a class that adapts your actual User to the ILmsLearner interface:



// Services/LMS/Adapters/SkillCanvasLearnerAdapter.cs

public class SkillCanvasLearnerAdapter : ILmsLearner

{



       private readonly UserDto _user;



   public SkillCanvasLearnerAdapter(UserDto user)

   {



          _user = user;

   }



   // Adapt User properties to ILmsLearner interface



   public int Id => _user.Id;



   public string Name => _user.UserName;        // UserName -> Name



   public string Email => _user.Email;



   public string? AvatarUrl => null;            // User doesn't have avatar



}



Step 3: Create a Provider (The Factory)



A provider fetches and adapts users on demand:



public class SkillCanvasLearnerProvider : ILmsLearnerProvider

{



       private readonly IUserService _userService;

       private readonly IAuthenticationService _authService;



   public async Task<ILmsLearner?> GetLearnerAsync(int userId)

   {



          var result = await _userService.GetByIdAsync(userId);

          if (!result.Success || result.Data == null)



                 return null;



          return new SkillCanvasLearnerAdapter(result.Data);

   }



   public async Task<ILmsLearner?> GetCurrentLearnerAsync()

   {



          var session = await _authService.GetCurrentSessionAsync();

          if (session?.User == null)



                 return null;



              return new SkillCanvasLearnerAdapter(session.User);

       }

}

4.4 Why "Model Agnostic"?



Model Agnostic means the LMS doesn't care about your specific models. It works with any user system

that provides an adapter.



              Scenario                           Solution

              Today: SkillCanvas with User       SkillCanvasLearnerAdapter

              Tomorrow: HR System with Employee  EmployeeLearnerAdapter

              Future: Standalone with AppUser    StandaloneUserAdapter

Same LMS code, different adapters.



4.5 Benefits



Benefit                Explanation

Decoupling             LMS doesn't depend on specific user implementation

Reusability            Extract LMS as separate project anytime

Testability            Mock ILmsLearnerProvider in tests

Flexibility            Switch user systems without changing LMS

Single Responsibility  Adapter handles only translation



4.6 When to Use the Adapter Pattern



Use it when:



      • You want decoupled modules that can be extracted later

      • You need to integrate with multiple user systems

      • You want testable code with mockable dependencies

      • You're building reusable libraries or modules

Don't use it for:



      • Simple internal services that won't be reused

      • When tight coupling is acceptable (small projects)

Chapter 5: Bulk Operations with Entity Framework

Core



5.1 The Problem: Why Bulk Operations?



When importing large datasets, traditional Entity Framework approaches become painfully slow:



             // Inserting 1000 articles the "normal" way

             foreach (var artigo in artigos)

             {



                    context.CrmArtigos.Add(artigo);

                    await context.SaveChangesAsync(); // 1000 round trips to database!

             }



Each SaveChangesAsync() generates: a network round trip, transaction overhead, identity column

retrieval, and change tracking updates. For 1000 records, that's 1000 round trips!



5.2 Approach Comparison



Approach 1: Individual SaveChanges (Slow)



             // Total time for 100 articles with 4 phases each: ~30 seconds

             foreach (var row in excelRows)

             {



                    var artigo = CreateArtigo(row);

                    context.CrmArtigos.Add(artigo);

                    await context.SaveChangesAsync(); // Round trip #1



                    foreach (var phase in row.Phases)

                    {



                            var faseArtigo = CreateFaseArtigo(phase, artigo.Id);

                            context.CrmFaseArtigos.Add(faseArtigo);

                            await context.SaveChangesAsync(); // Round trip #2, #3, #4...

                    }

             }



Approach 2: AddRange + Single SaveChanges (Better)



             // Add all at once, save once

             var artigos = excelRows.Select(r => CreateArtigo(r)).ToList();

             context.CrmArtigos.AddRange(artigos);

             await context.SaveChangesAsync(); // Single round trip!



Cons: Still generates individual INSERT statements. Can't get IDs until SaveChanges completes.



Approach 3: EFCore.BulkExtensions (Our Approach)



             // NuGet: EFCore.BulkExtensions

             using EFCore.BulkExtensions;



             var bulkConfig = new BulkConfig

             {



                    PreserveInsertOrder = true,

                    SetOutputIdentity = true // KEY: Gets IDs back after insert!

             };



             await context.BulkInsertAsync(artigos, bulkConfig);

             // Now artigos[0].Id, artigos[1].Id, etc. are populated!

5.4 Pattern for Dependent Objects



When you have parent-child relationships, follow this order:



             // Step 1: Insert parents, get IDs

             var bulkConfig = new BulkConfig

             {



                    PreserveInsertOrder = true,

                    SetOutputIdentity = true

             };

             await context.BulkInsertAsync(artigos, bulkConfig);

             // artigos now have IDs!



             // Step 2: Create children using parent IDs

             var fichas = new List<CrmArtigoFicha>();

             for (int i = 0; i < artigos.Count; i++)

             {



                    fichas.Add(CreateFicha(excelRows[i], artigos[i].Id));

             }

             await context.BulkInsertAsync(fichas);



             // Step 3: For grandchildren, use an index map

             var faseArtigos = new List<CrmFaseArtigo>();

             var indexMap = new Dictionary<(int artigoId, string phase), int>();



             for (int i = 0; i < artigos.Count; i++)

             {



                    foreach (var phase in excelRows[i].Phases)

                    {



                            var faseArtigo = new CrmFaseArtigo { Artigoid = artigos[i].Id };

                            indexMap[(artigos[i].Id, phase.Name)] = faseArtigos.Count;

                            faseArtigos.Add(faseArtigo);

                    }

             }

5.7 Common Mistakes



             // WRONG: IDs remain 0

             await context.BulkInsertAsync(artigos);

             Console.WriteLine(artigos[0].Id); // 0!



             // RIGHT: IDs are populated

             await context.BulkInsertAsync(artigos, new BulkConfig { SetOutputIdentity = true });



             // WRONG: Order may change, correlation breaks

             await context.BulkInsertAsync(artigos, new BulkConfig { SetOutputIdentity = true });

             var ficha = CreateFicha(excelRows[0], artigos[0].Id); // May not match!



             // RIGHT: Order preserved

             await context.BulkInsertAsync(artigos, new BulkConfig

             {



                    SetOutputIdentity = true,

                    PreserveInsertOrder = true

             });



             // WRONG: If componentes fails, artigos are already committed!

             await context.BulkInsertAsync(artigos, bulkConfig);

             await context.BulkInsertAsync(componentes); // Error leaves orphan artigos



             // RIGHT: Transaction wraps everything

             await using var transaction = await context.Database.BeginTransactionAsync();

             // ... all inserts ... then CommitAsync()

Chapter 6: Role-Based Permissions



6.1 The Bad Way: Boolean Flags



             public class User

             {



                    public int Id { get; set; }

                    public string Email { get; set; }



                    // Authorization via booleans

                    public bool IsAdmin { get; set; }

                    public bool CanCreateBoards { get; set; }

                    public bool CanDeleteBoards { get; set; }

                    public bool CanManageUsers { get; set; }

                    public bool CanViewReports { get; set; }

                    // ... 20 more boolean flags

             }



Why this is bad:



      • Database bloat - 20 permissions = 20 columns per user

      • No grouping - 100 managers × 20 flags to maintain

      • Hard to change - New permission = column + property + forms + checks

      • No hierarchy - No relationship between Admin and Manager



6.2 The Good Way: Role-Permission Model



             User ss→ UserRole ss→ Role ss→ RolePermission ss→ Permission



             Users have Roles:

             Luis → [User, Manager]

             Ana → [User]

             João → [User, Admin]



             Roles have Permissions:

             User → [Boards.View, Tasks.Create, Tasks.Edit]

Chapter 7: Password Security



7.1 Why We Never Store Plain Passwords



Scenario: Your database gets hacked (it happens to the best companies).



Storage Method  Hacker sees                       Result

Plain text      password123                       Immediate access to all accounts

Hashed          $2a$12$LQv3c1yq...                Useless without cracking



Rule #1: Never, ever store plain text passwords.



7.2 What is Hashing?



Hashing is a one-way function: Input → Output, but you cannot reverse it.



             Password → [Hash Function] → Hash

             "abc123" → [BCrypt] → "$2a$12$R9h/cIPz0gi.URNNX3kh2O..."



             Hash → [???] → Password

             "$2a$12$R9h/cIPz0gi.URNNX3kh2O..." → ??? → IMPOSSIBLE



7.3 Why BCrypt (Not MD5 or SHA)



MD5 and SHA are designed to be fast. A modern GPU can compute 180 billion MD5 hashes per second.

BCrypt is intentionally slow with a configurable work factor.



Work Factor     Time per Hash                     Hashes/Second

10              ~100ms                            10

12              ~300ms                            3

14              ~1 second                         1



8-character password cracking time:

MD5: 6.6 quadrillion ÷ 180 billion = ~10 hours

BCrypt: 6.6 quadrillion ÷ 3 = 70 million years



7.4 What is Salting?



A salt is a random string added to the password before hashing. Same password + different salts =

different hashes.



             Without salt:

             "password123" → [Hash] → "5f4dcc3b5aa..."

             Two users with same password = same hash (bad!)



             With salt:

             "password123" + "x7Kj9L" → [Hash] → "a1b2c3..."

             "password123" + "mN4pQ2" → [Hash] → "d4e5f6..."

             Same password, different hashes (good!)



             BCrypt includes the salt in the hash itself:

             $2a$12$LQv3c1yqT.SIvHn4FZNVCuqQ.aXP1vF...

This guide compiles essential patterns and security practices for building robust Blazor Server

applications. Apply these consistently across your projects for maintainable, secure code.

Key takeaways

  • Two-level base class hierarchy (BaseEntity, BaseAuditableEntity) removes audit-field duplication and lets you add features like soft-delete in one place
  • IEntityTypeConfiguration per entity beats Data Annotations and OnModelCreating mega-methods; ApplyConfigurationsFromAssembly wires them up automatically
  • ServiceResult<T> with Ok/Fail factory methods turns service errors into first-class return values, killing both the null-returning and throw-everywhere anti-patterns
  • The Adapter pattern lets a module like an LMS depend on ILmsLearner instead of your concrete User class, making it reusable and extractable
  • BulkExtensions with SetOutputIdentity=true is 60x faster than per-row SaveChanges and returns the new IDs into your original list
  • ASP.NET Identity is optional: [Authorize] and <AuthorizeView> only inspect Claims, so a custom AuthenticationStateProvider that builds ClaimsPrincipal from your own User table works identically
  • BCrypt's intentional slowness (work factor 12 ~300ms per hash) turns a 10-hour MD5 crack into a 70-million-year BCrypt crack
  • ProtectedLocalStorage and JSRuntime throw InvalidOperationException during prerender; move those calls to OnAfterRenderAsync(firstRender) and call StateHasChanged() after
