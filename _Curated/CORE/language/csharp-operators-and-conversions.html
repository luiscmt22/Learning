Operators in C# - Conversion Operators & Symbol Overloading
User-defined operators are compile-time sugar over static methods: conversion operators teach the compiler how your type becomes another type, symbol overloads teach existing symbols (+, ==, <) a new meaning for your type.
You wrote public static implicit operator Person(PersonBuilder pb) in your FacetedBuilder, came back weeks later, and couldn't read your own line. This guide makes that line — and every operator declaration — as readable as a property.
Executive summary
C# lets you define two kinds of custom operators. Conversion operators (implicit/explicit) define how one type transforms into another — implicit fires silently at typed targets (assignments, arguments, returns) and must be safe and lossless; explicit requires a visible cast and is for conversions that may lose data or throw. Symbol overloads redefine +, -, ==, < etc. for your type, with strict pairing rules (== with !=, < with >). Both compile to ordinary static methods (op_Implicit, op_Addition) — there is no runtime magic, which is why var, is, and as never trigger conversions. The design bar for both: only use them when the meaning is obvious to a stranger.
💡
Metaphor
A conversion operator is a customs agreement between two countries: implicit is an open border (citizens cross without showing papers — safe, routine, no losses), explicit is a checkpoint (you must present the cast, because crossing might cost you something). Symbol overloads are teaching an old word a new dialect: everyone knows what + means, so your type had better use it the way everyone expects.

Operators in C#

Conversion operators, symbol overloading, and the design bar for both

1. The Line You Couldn't Read

This came from your own FacetedBuilder (DesignPatterns/Patterns/Creational/Builder/FacetedBuilder/PersonBuilder.cs):

public static implicit operator Person(PersonBuilder pb)
{
    return pb.person;
}

It looks like a method, but the parts are in unfamiliar places: no method name, a type where the name should be, and two keywords (implicit operator) you rarely see. Once you know the grammar, it reads in one pass:

implicit operator Person(PersonBuilder pb) = “Whenever a Person is expected but a PersonBuilder is given, call this silently to convert it.” The parameter is the from type; the “name” position holds the to type. There is no separate return type — the target type is the return type.

That's one of the two species of user-defined operators. Let's map the whole territory.

2. Two Species, One Keyword

Both use operator and both must be public static, but they do different jobs:

Conversion operatorSymbol overload
What it customisesHow your type becomes another typeWhat an existing symbol (+, ==, <…) means for your type

// Symbol overload: return type + symbol where a name would go
public static Money operator +(Money left, Money right) { ... }

// Conversion: the target type IS the name
public static implicit operator Person(PersonBuilder pb) { ... }
People say “operator overloading” for both, and informally that's fine. Strictly: your PersonBuilder line is a user-defined conversion operator, not an overload of any symbol. If an interviewer asks, make the distinction — it signals you actually know the feature.

3. Conversion Operators: When Do They Fire?

This is the part that trips everyone. An implicit conversion fires only when the compiler sees a typed target that doesn't match the expression's type:

PersonBuilder builder = new();

Person a = builder;          // ✅ fires — typed variable is a target
Save(builder);               // ✅ fires — parameter `Person p` is a target
return builder;              // ✅ fires — return type `Person` is a target

var b = builder;             // ❌ never fires — b is a PersonBuilder!
var never triggers a conversion. It adopts the expression's existing type — there's no “expected type” for the compiler to convert toward. This is why your FacetedBuilderDemo, which uses var, has to call .Build() explicitly: the implicit operator sits there unused.

is and as don't call your operator either

var x = builder as Person;   // ❌ compile error CS0039
bool y = builder is Person;  // ❌ compile error
Person z = (Person)builder;  // ✅ works — cast resolves at compile time

is and as perform runtime type checks on an object that already exists. A conversion operator runs your code and produces a (possibly different) object. Different mechanisms, different moments: casts are wired up at compile time; is/as inspect at runtime and can't see your operators at all.

4. Implicit vs Explicit — The Honesty Contract

The keyword you pick is a promise to every future caller:

KeywordThe promiseCaller writesBuilt-in twin
implicitAlways succeeds, loses nothing, cheapPerson p = builder;int → long
explicitMay lose data or throw — opt in visiblyint x = (int)percentage;long → int (truncates)
 
// Rounding loses decimals; negatives throw. Must NOT happen silently:
public static explicit operator int(Percentage p)
{
    if (p.Value < 0) throw new InvalidOperationException("Negative percentage.");
    return (int)Math.Round(p.Value);
}

The rules the compiler enforces

  • One operator per type pair. You can't declare both implicit and explicit for the same pair — and you don't need to: implicit already permits the cast syntax too ((Person)builder works fine with only an implicit operator).
  • You must own one side. At least one of the two types must be the enclosing type (CS0556). No gluing a string → int conversion into some helper class.
  • No conversions to/from base classes or interfaces. The runtime already owns those relationships (inheritance, boxing); user conversions can't shadow the type system.
Implicit is an open border between two friendly countries — citizens cross without showing papers because nothing bad can happen. Explicit is a border checkpoint — you must present the cast, because the crossing might cost you something (decimals, an exception). And DateTime↔string has no border at all: parsing can fail, so .NET makes you take the official route — Parse/TryParse — where failure is part of the signature.

5. Symbol Overloading

The other species: giving an existing symbol a meaning for your type. The classic worthy example is a value type where the math is obvious:

public readonly record struct Money(decimal Amount, string Currency)
{
    public static Money operator +(Money left, Money right)
    {
        if (left.Currency != right.Currency)
            throw new InvalidOperationException("Currency mismatch.");
        return left with { Amount = left.Amount + right.Amount };
    }

    // money * 1.5m  AND  1.5m * money need SEPARATE overloads —
    // the compiler matches operand types positionally, never swaps them
    public static Money operator *(Money m, decimal factor) => m with { Amount = m.Amount * factor };
    public static Money operator *(decimal factor, Money m) => m * factor;  // delegate!
}

What you get free, what you can't touch

  • Free: compound assignment. wallet += price is always rewritten as wallet = wallet + price, reusing your +. You cannot (and need not) overload += separately.
  • Forbidden: =, ., ?:, new, typeof, and &&/|| directly (those come indirectly via overloading &/| plus true/false). C# is deliberately stricter than C++ here.
  • Never mutate an operand. Operators model value math: take inputs, return a new result. Even ++ should return a new value — the compiler handles prefix/postfix placement for you.

6. Equality — Pairs and the Recursion Trap

Some operators are legally married: define one and the compiler demands its partner. == pairs with !=, < with >, <= with >=.

The canonical == for a class, with the trap annotated:

public static bool operator ==(Isbn? left, Isbn? right)
{
    if (ReferenceEquals(left, right)) return true;   // same object, or both null
    if (left is null || right is null) return false; // ⚠ `is null`, NOT `== null`
    return left.Value == right.Value;
}
public static bool operator !=(Isbn? left, Isbn? right) => !(left == right);
Writing left == null inside your own == overload calls the overload itself — infinite recursion, StackOverflowException. is null is immune because pattern matching bypasses user-defined operators entirely. This bug is a rite of passage; now you've had it here instead of in production.

Also override Equals and GetHashCode so dictionaries agree with your == — three views of one truth. Or skip the whole ceremony: records synthesize value-based ==, !=, Equals, and GetHashCode for you. What records never give you is ordering — < on a record is a compile error until you write it, ideally as four one-liners delegating to a single CompareTo.

7. Under the Hood: No Magic

Every operator compiles to an ordinary static method with a reserved name:

foreach (var m in typeof(Money).GetMethods().Where(m => m.IsSpecialName))
    Console.WriteLine(m.Name);

// op_Addition, op_Multiply, op_Equality, op_Inequality ...
// and on PersonBuilder: op_Implicit

“Operator magic” is compile-time name resolution over these methods — nothing happens at runtime you couldn't write yourself. That single fact explains every caveat in this guide: var doesn't convert (no target type to resolve against), is/as don't convert (they're runtime checks, and op_Implicit is invisible to them), and casts do convert (the compiler rewrites them into a call).

8. The Design Bar: Obvious to a Stranger

The feature is easy; the judgment is the skill. Test cases:

CandidateVerdictWhy
date1 - date2 → TimeSpan✅ Operator.NET does exactly this; any stranger reads it correctly
order + orderLine❌ Method (AddLine)+ implies pure value math; this is a stateful domain action
implicit CustomerId → string❌ Don'tThe typed ID exists precisely to NOT silently become a string
implicit decimal → Money❌ Don'tWhich currency does Money m = 50m; have? A conversion that guesses is a bug factory
implicit PersonBuilder → Person🤝 DefensibleSafe, lossless, cheap. But when .Build() also exists, the named method wins in practice — it works with var and announces itself
Operators belong on types that behave like values with meanings a stranger already knows: math, units, money, versions, coordinates. Everything else gets a named method. A + that touches the database is a crime scene.

9. Key Takeaways

  • Two species: conversion operators (type → type) and symbol overloads (new meaning for +, ==…). Same keyword, different grammar: conversions use the target type as the name; overloads have a return type plus a symbol.
  • Conversions fire at typed targets only — assignment to a typed variable, argument passing, return statements. Never with var, never via is/as.
  • Implicit = safe, lossless, cheap. Explicit = may lose or throw. If it can fail, consider a named Parse/TryParse-style method instead of either.
  • Pairing rules: ==/!=, </>, <=/>= come in mandatory pairs. Inside ==, use is null — never == null.
  • No runtime magic: operators are static methods (op_Implicit, op_Addition) resolved at compile time.
  • The design bar: obvious to a stranger, or it gets a name.
