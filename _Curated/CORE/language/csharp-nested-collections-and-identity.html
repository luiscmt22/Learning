Nested Collections & Object Identity
A generic type argument describes a slot, not an object: nesting dictionaries allocates nothing until you write, storing a reference makes two names for one object, and Add / indexer / TryAdd are three different answers to “what does a duplicate key mean?”
You typed Dictionary<int, Dictionary<int, Dictionary<int, string>>> into SearchController to test a hypothesis, and three things bit you in a row: you couldn't say how many dictionaries existed, two variables silently pointed at the same object, and Add threw on a key you'd forgotten was there. None of those are knowledge gaps — they're identity gaps.
Executive summary
Nested collections concentrate three separate C# ideas into one place. First, allocation: type arguments are compile-time descriptions, so only the new keyword creates objects — a three-level dictionary declaration allocates exactly one. Second, identity: storing a dictionary into another dictionary copies the reference, so mutations through any name are visible through all of them; this is a bug when accidental and the load-bearing mechanism of get-or-create when deliberate. Third, write semantics: the indexer upserts and never throws, Add asserts the key is new and throws ArgumentException if not, TryAdd adds only when absent and returns a bool. Reading a missing key throws KeyNotFoundException, so nested access needs TryGetValue at every level but the last — and out var is the correct form because it inherits the [MaybeNullWhen(false)] annotation that an explicit declaration contradicts.
💡
Metaphor
A reference is a street address, not a house. Writing the address into three notebooks doesn't build three houses — and renovating via any one notebook renovates the single house all three point to. Only new builds a house. Every bug in this guide is someone who thought they had three houses.

Nested Collections & Object Identity

Allocation, aliasing, the three writes, and the get-or-create idiom

1. The Line That Bit You

This went into Driveway/src/SearchService/Controllers/SearchController.cs as a hypothesis test:

Dictionary<int, Dictionary<int, Dictionary<int, string>>> yearMakeModelMap
    = new Dictionary<int, Dictionary<int, Dictionary<int, string>>>();

The natural question was “did I just create three dictionaries?” The answer is one — and the reason why is the foundation of everything else here.

Dictionary<int, Dictionary<int, string>> = “a dictionary whose keys are ints and whose values will be dictionaries.” The nested type argument is a description of a slot, checked by the compiler. It is not an instruction to build anything. Nothing exists inside until you put it there.

Three separate ideas collapse into this one declaration: how many objects exist, who else can reach them, and what happens when you write a key that's already taken. This guide takes them in that order.

2. Type Arguments Are Not Allocations

The rule is mechanical: count the new keywords, not the angle brackets.

// 1 object. Count == 0. No inner dictionaries exist.
var a = new Dictionary<int, Dictionary<int, string>>();

// 3 objects: the outer, plus one inner per entry.
var b = new Dictionary<int, Dictionary<int, string>>
{
    { 1, new() { { 1, "x" } } },
    { 2, new() { { 2, "y" } } }
};

A collection initializer isn't special syntax — it's sugar for repeated .Add(...) calls, so every new inside it allocates too. The original three-level literal in SearchController allocated seven dictionaries (one outer, two mid-level, four leaves), and the full experiment eleven — on every HTTP request, since it sat inside the action method.

“Declaring” a nested dictionary is often mistaken for building its shape, the way a fixed-size 2D array does. It doesn't. new int[3,3] really does reserve nine slots; new Dictionary<int, Dictionary<int, int>>() reserves nothing. Every level below the first has to be created explicitly, which is why section 7 exists.

3. Aliasing: One Object, Many Names

Dictionaries are reference types, so storing one copies the reference, not the object:

var makes = new Dictionary<int, string> { { 1, "Toyota" } };
var byYear = new Dictionary<int, Dictionary<int, string>>();

byYear.Add(1990, makes);
byYear.Add(2000, makes);

byYear[1990].Add(2, "Honda");

Console.WriteLine(byYear[2000].Count);   // 2  — the "other" year changed
Console.WriteLine(makes.Count);           // 2  — the local changed too
makes ─────────┐ ▼ byYear[1990] ─▶ ┌──────────────────────┐ │ { 1:"Toyota", │ ONE object byYear[2000] ─▶ │ 2:"Honda" } │ THREE names └──────────────────────┘

Two dictionary entries, one dictionary object, three ways to reach it. Now the part that separates people who understand references from people who've merely read about them:

makes = new Dictionary<int, string>();   // reassign the VARIABLE
Console.WriteLine(byYear[1990].Count);      // still 2 — untouched
Reassigning a variable repoints a label; mutating an object changes the thing. makes = new(...) makes the local point somewhere else and does nothing to the dictionary byYear is still holding. makes.Add(...) changes the shared object and everyone sees it.

Shallow vs deep copy

The same rule explains why the copy constructor doesn't isolate you:

var shallow = new Dictionary<int, Dictionary<int, string>>(original);
shallow[1990].Add(99, "New");
original[1990].ContainsKey(99);   // true! the inner maps are shared

It copies the outer structure and every reference inside it. To isolate, rebuild each level:

var deep = new Dictionary<int, Dictionary<int, string>>();
foreach (var (year, inner) in original)
    deep[year] = new Dictionary<int, string>(inner);   // shallow here is FINE

You stop deep-copying at the first immutable layer. The values are string, which nobody can mutate out from under you, so sharing them is safe. Were they List<T>, you'd have to keep going.

4. The Three Writes

Three ways to put a key in a dictionary. They differ only when the key is already present, and choosing between them is a design decision about what a duplicate means in your domain.

WriteKey absentKey presentThe intent it expresses
d[k] = vAddsOverwrites silently“Upsert — later data wins.”
d.Add(k, v)AddsThrows ArgumentException“A duplicate is a bug in my logic — fail loudly.”
d.TryAdd(k, v)Adds, returns trueNo-op, returns false“First write wins — tell me which happened.”
Add does not mean “don't overwrite” — it means “crash if this would overwrite.” It's a runtime assertion, not a protection. If your goal is “leave the existing value alone”, the answer is TryAdd. This is the exact mistake that made SearchController throw: swapping an indexer assignment for Add on a key that already existed turned a wrong value into an unhandled exception.

Pick by what a collision means, not by which feels safest:

SituationUse
Cache or lookup where later data supersedes[k] = v
Config load where a duplicate key means malformed inputAdd — let it blow up
Merging layered sources where the first source winsTryAdd
Keys originating from user inputNever Add — you're handing users a DoS

The initializer trap

The two initializer syntaxes inherit these semantics, which surprises people:

var a = new Dictionary<int, string> { { 1, "A" }, { 1, "B" } };  // THROWS at runtime
var b = new Dictionary<int, string> { [1] = "A", [1] = "B" };      // fine, b[1] == "B"

Collection-initializer braces compile to Add; indexer syntax compiles to indexer assignment. Both forms compile cleanly — the compiler doesn't constant-fold keys to detect duplicates — so form a fails at runtime. LINQ's ToDictionary() has the same Add semantics and throws on duplicate keys rather than picking a winner.

Reads have their own rule

The indexer is asymmetric: writing a missing key adds it, reading a missing key throws KeyNotFoundException. In map[2010][3] = x, the first bracket is a read and the second is a write — so that line throws if 2010 is absent but happily creates key 3.

5. out var: Scope and Definite Assignment

Because reads throw, safe nested access runs through TryGetValue. Two rules govern the variable it produces.

Scope. An out var declaration is scoped to the enclosing block — exactly as if declared on the line above. Not to the if body, and not beyond the block:

if (map.TryGetValue(1, out var found))
    Console.WriteLine(found);   // ✅
Console.WriteLine(found);       // ✅ still in scope after the if

if (true)
{
    if (map.TryGetValue(2, out var inner)) { }
}
Console.WriteLine(inner);       // ❌ CS0103 — its block has closed

Definite assignment. The out contract requires the method to assign the parameter on every exit path (miss one when writing your own and you get CS0177). That's what makes the variable usable immediately after the call with no initialization — and on a false return it holds default, which for a reference type is null.

6. Why out var Beats an Explicit Declaration

TryGetValue poses a problem the type system can't express. Is the out parameter null after the call? It depends on the return value — and a parameter gets one type, not two. The gap is filled with an attribute:

public bool TryGetValue(TKey key, [MaybeNullWhen(false)] out TValue value)
[MaybeNullWhen(false)] = “value may be null when this method returns false.” It isn't a type — it's metadata the compiler reads to give the variable different nullability in different branches: guaranteed non-null in the true branch, possibly null in the false branch.

Now the payoff. var adopts the type together with its nullability, so it stays honest for free. Writing the type yourself makes a promise that can contradict the method's:

// ✅ no warning — var inherits the null-aware type
if (!map.TryGetValue(2010, out var makesA))
    makesA = map[2010] = new();

// ⚠ warning CS8600 — you declared "never null"; the method may write null
Dictionary<int, string> makesB;
if (!map.TryGetValue(2020, out makesB))
    makesB = map[2020] = new();

The fix for the second form is one character — declare it Dictionary<int, string>? — but you have to remember it, and retype the whole generic type. CS8600 is only a warning and the code runs identically; what you lose is the compiler's null tracking from that point on, so genuine null bugs downstream stop being reported.

Prefer out var. Not because it's shorter — because it inherits the annotation, so the nullable analysis is right by default instead of right only if you remember a ?.

7. The Get-or-Create Idiom

Everything above assembles into the one pattern you'll write for the rest of your career: reach a nested level, creating it if it doesn't exist, without ever throwing.

// get-or-create at each level, then write the leaf
if (!byYear.TryGetValue(year, out var makes))
    makes = byYear[year] = new Dictionary<int, Dictionary<int, string>>();

if (!makes.TryGetValue(makeId, out var models))
    models = makes[makeId] = new Dictionary<int, string>();

models[modelId] = modelName;

Read it as: if there's no makes-map for this year, create one and file it under the year; the same for the make; then write the leaf. After each if, the variable is guaranteed non-null on both paths — that guarantee is what lets the next block dereference it safely.

Why the chained assignment isn't two objects

Assignment in C# is an expression that evaluates to the value assigned, and it is right-associative:

makes = ( byYear[year] = new Dictionary<...>() );
//        └─ stores the new dict, then evaluates to that same reference ─┘

One allocation, two references to it. Writes through makes land inside byYear[year] because it is the same object. Section 3's aliasing — accidental there — is the load-bearing mechanism here. Note also that the writes use the indexer, never Add: you only reach that line when the key is known absent, and the indexer cannot throw.

Three implementations, three costs

FormLookups (hit / miss)Verdict
ContainsKey then indexer2 / 3Avoid — hashes the key repeatedly, and is racy on shared state
TryGetValue + indexer1 / 2The default. Readable, one obvious meaning
CollectionsMarshal.GetValueRefOrAddDefault1 / 1Measured hot paths only
 
// .NET 6+: a ref straight into the dictionary's bucket — no second lookup
ref var slot = ref CollectionsMarshal.GetValueRefOrAddDefault(map, key, out bool existed);
slot ??= new();
That ref points into the dictionary's internal array, and any insert that triggers a resize invalidates it. You must not touch map while slot is alive. One extra hash lookup is nothing next to code your team can read without a comment — use TryGetValue unless a profiler sent you here.

8. Should You Nest At All?

Having made nesting work, the honest question is whether it was the right shape. Three designs for the same year/make/model lookup:

DesignGood atBad at
Dictionary<int, Dictionary<int, Dictionary<int, string>>>“All makes in 1990” is one indexer callGet-or-create ladders, aliasing, partially-built levels, unreadable in the debugger
Dictionary<(int Year, int Make, int Model), string>Exact lookups; one flat map, no ladder, no aliasing“All makes in 1990” needs a full scan
List<Vehicle> of recordsQuerying by many shapes — name, range, sortedPoint lookups are O(n)
The deciding question is not performance — it's “do I ever need a whole level on its own?” If “every make in 1990” is a real operation, nesting earns its complexity. If you only ever do exact three-part lookups, the composite key is dramatically simpler and you should take it.

The tuple key works for free because ValueTuple implements structural Equals and GetHashCode over its fields — the same contract covered in csharp-equality-guide and csharp-named-tuples. A record key behaves identically.

9. Key Takeaways

  • Count new, not angle brackets. A three-level declaration allocates one dictionary; type arguments describe slots, they don't build them.
  • Storing a collection copies the reference. One object, many names — mutations are visible through all of them. Reassigning a variable repoints a label and changes nothing.
  • Three writes, three intents: indexer = upsert, Add = assert-and-throw, TryAdd = first-write-wins. Add is not a guard against overwriting; it's a crash when you would have.
  • The indexer is asymmetric: writing a missing key adds it, reading one throws KeyNotFoundException.
  • Prefer out var: it's scoped to the enclosing block, definitely assigned on all paths, and inherits [MaybeNullWhen(false)] so nullable analysis is correct without a manual ?.
  • Get-or-create is deliberate aliasing: child = parent[k] = new() allocates once and shares the reference on purpose.
  • Nest only if you need a level on its own. Otherwise a composite tuple key is the same lookup with none of the ceremony.
