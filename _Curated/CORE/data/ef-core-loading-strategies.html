EF Core Relationships, Lazy Loading and Virtual Properties

A quick reference showing when to use lazy, eager, and explicit loading in EF Core, when the virtual keyword is actually needed, and why lazy loading is usually the wrong choice.

DOCX Beginner 678 words 3 min read Source: 📘 Loadings_Includes_virtuals.docx

Your page that lists 100 companies takes 4 seconds to load. You check the SQL log: 101 queries. One to fetch the companies, then 100 more - one per company - to fetch each country. That's lazy loading biting you. The fix is usually one line, and this doc tells you which line.

Executive summary

A concise EF Core cheat sheet covering navigation properties versus foreign keys, the three loading strategies (lazy/eager/explicit), the specific role of the virtual keyword (only required when lazy loading is enabled), the correct use of [NotMapped] for computed properties, and performance tips like using .Include() and .Select() to avoid N+1 queries. Includes a quick decision guide table for choosing the right approach per scenario.

💡
MetaphorThink of EF Core's loading strategies as three different ways to order at a restaurant. Eager loading is a prix-fixe menu: you ask for the steak and it arrives with the vegetables, potatoes, and sauce all on one plate, one trip from the kitchen. Lazy loading is tapas: you get the steak, then when you reach for a potato the waiter runs back to the kitchen, then for a carrot another trip - by the end of your meal the waiter has done fifty laps (that's N+1). Explicit loading is when you flag the waiter down yourself and say 'now bring me the dessert' - controlled but manual. The virtual keyword is the little bell on your table that lets the waiter run off to the kitchen when you touch a side dish; without it, you can't do lazy loading at all.

📘 Entity Framework Core — Relationships, Lazy Loading & Virtual Properties

🧩 1. Navigation Properties & Foreign Keys

In EF Core, each relationship usually uses both an FK property and a navigation property:


public class Empresa

{

public string EmpresaId { get; set; }

public string Nome { get; set; }

// Foreign key

public int CountryId { get; set; }

// Navigation property

public Country Country { get; set; }

}
Property Purpose Stored in DB?
----------- ---------- ---------------
CountryId Foreign key, links entities ✅ Yes
Country Navigation for related data ❌ No

⚙️ 2. Loading Related Data

Loading type Description Example SQL queries Recommended for
--------------- -------------- ---------- -------------- -----------------
Lazy Loading Loads data when property is first accessed empresa.Country.Name Many (N+1) Small datasets, simple UIs
Eager Loading Loads related data up front via join .Include(e => e.Country) Single Lists, tables, APIs
Explicit Loading Manually load related data later context.Entry(e).Reference(x => x.Country).Load() Separate Controlled cases

🧠 3. The virtual Keyword

Context Is virtual needed? Why
---------- ---------------------- -----
Lazy loading ✅ Yes EF substitutes proxy overrides for navigation props
Eager loading (Include) ❌ No Data loaded via join
Explicit loading (Load) ❌ No Manual load
Projection (Select) ❌ No Custom object mapping
💡 Tip: Many production apps turn lazy loading off for predictable performance and simpler debugging.

🧱 4. Recommended Relationship Setup


public class Country

{

public int CountryId { get; set; }

public string Name { get; set; }

public ICollection<Empresa> Empresas { get; set; }

}

public class Empresa

{

public string EmpresaId { get; set; }

public string Nome { get; set; }

public int CountryId { get; set; }

public Country Country { get; set; }

}

Optional explicit Fluent API configuration:


modelBuilder.Entity<Empresa>()

.HasOne(e => e.Country)

.WithMany(c => c.Empresas)

.HasForeignKey(e => e.CountryId);

🚀 5. Query Examples

✅ Eager Loading (Recommended for lists)


var empresas = dbContext.Empresas

.Include(e => e.Country)

.Select(e => new

{

e.EmpresaId,

e.Nome,

CountryName = e.Country.Name

})

.ToList();

🧠 Result: A single optimized JOIN query fetching only needed data.

🧰 6. [NotMapped] Attribute

Use [NotMapped] only for properties that don’t exist in the database, e.g.:


[NotMapped]

public string DisplayName => $"{Nome} ({Country?.Name})";

Do not use [NotMapped] on valid navigation properties like Country.

⚡ 7. Performance Tips

Tip Why
----- -----
Avoid lazy loading in large loops Prevents N+1 query issues
Use .Include() Loads related data in one query
Use .Select() Fetch only columns you need
Keep virtual only if lazy loading is used Otherwise unnecessary
Turn off lazy loading globally in production Makes query flow explicit

🧭 8. Quick Decision Guide

Scenario Lazy Loading Eager Loading virtual Needed [NotMapped]
----------- --------------- --------------- ------------------ ---------------
Small admin pages ✅ Optional ✅ Good ✅ Yes ❌ No
Large tables / APIs ❌ No ✅ Yes ❌ No ❌ No
Computed property N/A N/A ❌ No ✅ Yes
DTO / projection ❌ No ✅ Yes ❌ No ✅ (if outside EF)

✅ 9. Key Takeaways

  • ✔️ Keep both CountryId (FK) and Country (navigation).
  • ⚙️ Use .Include() or .Select() instead of lazy loading.
  • 🚫 Don’t mark navigation properties [NotMapped].
  • 🧠 Only use virtual when you enable lazy loading.
  • 💪 Prefer eager loading for predictable, performant queries.
  • 🧾 EF automatically manages relationships via conventions or OnModelCreating.

End of Notes — EF Core Relationship & Loading Reference

Key takeaways

  • Keep both the FK property (CountryId) and the navigation property (Country) on your entity
  • Use .Include() or .Select() instead of lazy loading for predictable performance
  • The virtual keyword is only needed when lazy loading is enabled - otherwise it's noise
  • Never put [NotMapped] on a real navigation property - it's for computed in-memory values only
  • Most production apps turn off lazy loading globally for predictability
  • Use .Select() to project only the columns you need and reduce wire traffic
  • .Include() generates a single JOIN; lazy loading generates N+1 queries
