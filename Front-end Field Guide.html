Words Vocabulary, before anything else

Every table below uses these words. Each gets one plain sentence and, where it helps, an example from Jolefilo.

HTML

Element
One piece of the page: an opening tag, its content, a closing tag. <p>Olá</p> is an element; <p> alone is its tag.
Attribute
A setting written inside the opening tag as name="value": <a href="/Clientes">.
Boolean attribute
An attribute that is on when present and off when absent, whatever its value: disabled, checked.
Semantic
A tag chosen for its meaning (nav, main, button) instead of its look. A div has no meaning.
Void element
A tag with no content and no closing tag: img, input, br.
Markup
The HTML text itself, as opposed to the styles or the code.
DOM
The tree the browser builds from the markup. CSS and JavaScript act on the tree, not on the text.

CSS basics

Rule
A selector plus a block of declarations: .jf-card { padding: 14px; }.
Selector
The part that says which elements the rule hits: .jf-card, a:hover.
Declaration
One property: value; pair inside the block.
Property
The thing being set: padding, color, display.
Class
A label you put on elements (class="jf-card") so a selector can find them. Many elements may share one; one element may have many.
Id
A label that must be unique on the page (id="login").
Pseudo-class
A selector suffix for a state or a position: :hover, :focus-visible, :first-child.
Shorthand
One property that sets several at once: margin sets four sides, font sets size, weight, line height and family.
Cascade
The procedure that decides which rule wins when several set the same property on the same element.
Specificity
The weight of a selector in that decision: an id beats any number of classes, a class beats any number of tags.
Inheritance
Some values (colour, font) flow from an element to everything inside it unless something inside sets its own.

Colour words

Token / custom property
A value stored once under a name (--jf-primary: #1f6b3b) and reused with var(--jf-primary), so a change in one place changes every use.
Tint
A pale version of a colour, used as a background: the mint behind a "Faturada" chip.
Tone / strong
The deep version of the same colour, used for text or icons on that tint.
Palette
The whole set of colours a design allows itself.
Contrast ratio
How different the text colour is from the background, as a ratio; 4.5:1 is the minimum for body text.

Layout words

Box
Every element is a rectangle made of four layers: content, padding, border, margin.
Padding / margin
Space inside the border (padding) and outside it (margin).
Block / inline
A block starts on a new line and takes the full width (a paragraph). An inline sits inside a line of text (a link).
Flow
The default arrangement: blocks top to bottom, inline left to right. Flex and grid replace it for one element's children.
Container / item
The element you give display: flex or grid to, and its direct children.
Main axis / cross axis
In flex, the direction items are laid in (horizontal for a row) and the one at right angles to it.
Track
One column or one row of a grid.
Gap
Space between items, set once on the container instead of margins on each item.
Overflow
Content larger than its box. The overflow property says whether it spills, is clipped, or scrolls.
Viewport
The visible area of the browser window; on a phone, the screen.
Breakpoint
A width at which the layout changes, written as a media query.
Media query
@media (min-width: 600px) { … }: rules that apply only while the condition holds.
Stacking context
A group of elements whose front-to-back order is settled among themselves before the whole group is placed against the rest of the page.
Safe area
The parts of a phone screen under the notch or the home bar, where nothing should be drawn.
DPR
Device pixel ratio: a phone 412 CSS pixels wide may draw 1080 real pixels.

Type words

Face / family
The font itself (Plus Jakarta Sans). A stack lists fallbacks in case it is missing.
Weight
How bold: 400 normal, 600 semibold, 700 bold.
Scale
The short list of sizes a design allows itself.
Line height / leading
The distance from one line of text to the next.
Letter-spacing / tracking
Extra space between letters; uppercase labels get a little.
Measure
How many characters fit on one line; about 65 reads best.
Ellipsis
The "…" that replaces cut-off text.

Tailwind words

Utility
A class that sets exactly one declaration: p-4 is padding: 1rem.
Variant
A prefix that adds a condition to a utility: hover:, md:, dark:.
Scale
Tailwind's fixed set of allowed values; the spacing scale steps by 4px, so 4 is 16px.
Theme / config
Where the scales and the colour palette are defined for the project.
Arbitrary value
Square brackets to use any value outside the scale: w-[760px].
Scanner
The build step that reads your files for class names and generates only those; a name built at runtime is never generated.
@apply
A stylesheet directive that bundles utilities under a normal class name.

Accessibility words

Screen reader
Software that reads the screen aloud: TalkBack on Android, VoiceOver on iPhone.
Accessibility tree
The browser's list of what is on the page as roles, names and states; what the reader actually reads.
Role / name / state
What an element is (button), what it is called (Faturas), how it currently is (pressed).
Landmark
A region a reader can jump to: main, navigation, header.
Live region
An area whose changes are read aloud without moving focus.
Focus
The one element that receives the keyboard right now; Tab moves it.
Hit area / touch target
The tappable size of a control, which may be larger than what is drawn.

Blazor words

Component
A .razor file: markup plus code, rendered to HTML.
Circuit
The live connection between a Blazor Server page and the server; when it drops, the page stops responding.
Diff
The server works out what changed in the markup and sends only that to the browser.
Splat
Attributes a component does not declare are passed through to its root element.
CSS isolation
A .razor.css whose rules only hit that one component.
Ripple
MudBlazor's spreading-circle effect on tap.
Hot reload
Applying a code change to a running app without restarting it; changes to a component's structure need a restart.

HTML Document skeleton

<!doctype html>
<html lang="pt-PT">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Jolefilo · Clientes</title>
  <link rel="stylesheet" href="css/site.css">
  <script src="app.js" defer></script>
</head>
<body>
  <header>…</header>
  <main>…</main>
  <footer>…</footer>
</body>
</html>
langTells screen readers and spell-checkers the language. Jolefilo's UI is PT-PT.
viewportWithout it a phone renders the page at 980px and zooms out. Mandatory for mobile.
deferLoads the script without blocking and runs it after the HTML is parsed.
<head>Metadata only, nothing visible. Blazor Server writes most of it in App.razor.

Void elements never close: <meta>, <link>, <img>, <input>, <br>, <hr>. Everything else does.

Boolean attributes (disabled, checked, readonly, required, hidden, open) are on when present, off when absent. disabled="false" is still disabled. ARIA state attributes are not boolean: they need the words "true" or "false".

CSS Specificity and cascade

When two rules set the same property on the same element, the most specific wins; on a tie, the later one in the file wins.

style="…"Inline, beats all selectors #id1-0-0 .class [attr] :hover0-1-0 each div ::before0-0-1 each * :where()0-0-0 !importantWins over everything above; the last resort 
/* 0-2-0 beats MudBlazor's 0-1-0 and 0-2-0 by order */
.jf-client-doc-card.mud-button-root { padding: 15px; }

/* 0-3-0 plus a state */
.jf-client-doc-card.active.mud-button-root:hover { background: #f3f9f5; }

Inherited by children: color, font-*, line-height, letter-spacing, text-align, cursor. Not inherited: margin, padding, border, background, width, display. Force with inherit; reset with initial or unset.

CSS Recipes TW

/* centre anything */
.centre { display: grid; place-items: center; }
/* grid place-items-center */

/* row: text on the left, amount pushed right, never wraps */
.row { display: flex; align-items: center; gap: 12px; }
.row .text { flex: 1; min-width: 0; }
.row .amount { white-space: nowrap; flex-shrink: 0; }
/* flex items-center gap-3 / flex-1 min-w-0 / whitespace-nowrap shrink-0 */

/* truncate one line */
.one-line { white-space: nowrap; overflow: hidden; text-overflow: ellipsis; }
/* truncate */

/* card */
.card { background: #fff; border: 1px solid #ebefec; border-radius: 18px;
        box-shadow: 0 1px 3px rgba(20,45,30,.05); }
/* bg-white border border-gray-200 rounded-2xl shadow-sm */

/* pill chip */
.chip { display: inline-flex; align-items: center; gap: 6px; padding: 4px 11px;
        border-radius: 999px; font-size: 12px; font-weight: 700; }
/* inline-flex items-center gap-1.5 px-3 py-1 rounded-full text-xs font-bold */
/* two columns that stack on phones */
.form { display: grid; grid-template-columns: repeat(2, minmax(0, 1fr)); gap: 12px; }
@media (max-width: 360px) { .form { grid-template-columns: minmax(0, 1fr); } }
/* grid grid-cols-1 sm:grid-cols-2 gap-3 */

/* sticky header */
.header { position: sticky; top: 0; z-index: 10; background: #fff; }
/* sticky top-0 z-10 bg-white */

/* visually hidden, still read by screen readers */
.sr-only { position: absolute; width: 1px; height: 1px; padding: 0; margin: -1px;
           overflow: hidden; clip: rect(0 0 0 0); white-space: nowrap; border: 0; }
/* sr-only */

/* wide table that scrolls inside its box, not the page */
.table-scroll { overflow-x: auto; }
.table-scroll table { min-width: 760px; }
/* overflow-x-auto / min-w-[760px] */

/* a scrolling body inside a fixed-height column (drawer) */
.body { flex: 1; min-height: 0; overflow-y: auto; overscroll-behavior: contain; }
.body > * { flex-shrink: 0; }
/* flex-1 min-h-0 overflow-y-auto overscroll-contain */

/* image that fills its box */
.cover { width: 100%; height: 100%; object-fit: cover; }
/* w-full h-full object-cover */

Three traps. Classes built at runtime ("text-" + colour) are not generated: the scanner needs the full literal in the source. Utilities all have the same specificity, so a later utility in Tailwind's output wins, not the later one in your class="". Use @apply in a stylesheet for a repeated pattern, or a component; mixing both for the same thing creates two sources of truth.

How a page is built

Three trees, built in order. Most layout surprises come from forgetting which tree a rule touches.

The browser reads the HTML into the DOM, a tree of elements. It reads the stylesheets into the CSSOM, every rule with its selector. It then walks the DOM, finds the rules that match each element, computes the final value of every property (the cascade), and builds the render tree of boxes. Layout gives each box a position and size, paint draws them, and compositing stacks the layers. Change a class and the browser repeats from the cascade step for the affected elements; animate width and it repeats layout every frame, which is why only transform and opacity animate smoothly.

A fourth tree matters for people who do not see the screen: the accessibility tree, derived from the DOM. A <button> becomes a node with the role button and the name of its text. A <div> with a click handler becomes nothing a screen reader can act on. This is the whole argument for semantic HTML: the tag you choose decides what three of the four trees contain, before any CSS.

Blazor Server builds the DOM differently from a static site. The component renders on the server, a diff travels over the SignalR circuit, and a small script patches the browser's DOM. Browser extensions that rewrite the DOM before the circuit attaches are why Jolefilo runs without prerendering. For CSS and ARIA nothing changes: the result in the browser is ordinary HTML, and DevTools shows it.

The cascade and inheritance

Which rule wins, and which values flow down to children on their own.

Three questions, in order

  1. Importance and origin. Author styles beat the browser's defaults. !important flips the order and should be a last resort, which is why MudBlazor's palette text classes using it are so hard to override.
  2. Specificity. Count ids, then classes (attributes and pseudo-classes count as classes), then types. #a beats any number of classes; .a.b beats .a; div.a beats .a. Inline style beats every selector.
  3. Order. Equal specificity: the rule that appears later wins. Tailwind's whole model rests on this: utilities are emitted in a fixed order, so p-4 p-2 gives whichever the generated file lists last, not the last in your attribute.

The practical rule for a MudBlazor app: when your class loses, add one of the component's own classes to your selector. .jf-cash-close.mud-button-root has two classes and is written after MudBlazor's stylesheet, so it wins on both counts. Add the state when the component styles its states: .jf-x.mud-button-root:hover.

Inheritance

Some properties pass to children when the child does not set them: colour, every font-*, line-height, letter-spacing, text-align, visibility, cursor. Set font-family once on body and every element uses it. Box properties never inherit: margin, padding, border, background, width, display, position.

Two consequences you will meet. A <button> and an <input> do not inherit the font by default; the browser gives them their own, so resets add font: inherit to form controls. And the Clientes row turned green when it became a link because color inherits: the link's colour flowed into the name span that set none of its own. Color="Color.Inherit" stopped the link from forcing one.

button, input, select, textarea { font: inherit; color: inherit; }
.jf-client-row.mud-link { color: var(--jf-text); } /* flows into the name */

The box model

Every element is a rectangle with four layers. Sizing goes wrong when you forget which layers a width includes.

margin → border → padding → content

content: width × height

With the default box-sizing: content-box, width: 200px plus 16px padding each side plus a 1px border renders 234px wide. With border-box, the 200px includes padding and border, which is what everyone expects. Set it once for everything and forget it:

*, *::before, *::after { box-sizing: border-box; }

Margins collapse, padding does not

Two block siblings with margin-bottom: 20px and margin-top: 30px sit 30px apart, not 50. A first child's top margin leaks through its parent unless the parent has padding, a border, or is a flex or grid container. This is why the project rule says to space siblings with gap on a flex or grid parent: gaps never collapse, never double, and never leak.

Sizing vocabulary

  • width: auto on a block means "fill the parent"; on a flex item it means "as wide as my content".
  • min-width and max-width clamp any width, including auto. A fluid card is width: 100%; max-width: 760px.
  • Percent heights only work when the parent has a definite height; prefer min-height or flex.
  • margin: 0 auto centres a block only when it has a width smaller than its parent.

Flow: block and inline

Before flex and grid there is normal flow, and every element starts there.

A block element starts on a new line and takes the full width of its parent: div, p, section, headings, lists. An inline element sits in the line of text and is as wide as its content: span, a, strong, code. Width, height and vertical margins are ignored on inline elements, which is the usual reason a padded span looks wrong. inline-block keeps the element in the line but lets it have a box; inline-flex does the same for a flex container, which is what a chip is.

An image is inline by default, so it sits on the text baseline and leaves a few pixels of space below it for descenders. display: block or vertical-align: middle removes that gap. display: contents makes an element disappear from layout while its children stay, useful when a wrapper breaks a grid; it has accessibility bugs on some elements, so avoid it on buttons and lists.

Flex and grid change how the children of one element are laid out, and only those children. The children themselves become flex or grid items, their own display notwithstanding, and their descendants go back to normal flow. Layout is decided one level at a time.

Grow, shrink, basis

flex: grow shrink basis. basis is the starting size (auto = the content), grow says how much of the leftover space the item takes, shrink how much it gives up when space is short. flex: 1 means 1 1 0%: start from nothing and share equally. flex: none freezes an item at its content size.

The min-width trap. A flex item refuses to shrink below its content's minimum width, because its default is min-width: auto. A long client name then pushes the amount and the chevron off the screen. min-width: 0 on the text column lets it shrink and ellipsise. Every row in Jolefilo has it; every overflow bug you will meet in Tailwind is a missing min-w-0.

Wrapping: flex-wrap: wrap lets items drop to new lines; align-content then spaces the lines. A column flex (flex-direction: column) swaps the axes: justify-content is vertical, align-items horizontal. The drawer is a column flex with a sticky footer: header, a body with flex: 1; min-height: 0; overflow-y: auto, footer.

Positioning and stacking

Taking an element out of flow, and deciding what paints over what.

static is the default: the element sits where flow puts it and top/left do nothing. relative keeps its place in flow but can be nudged, and, more usefully, becomes the containing block for absolutely positioned children. absolute leaves the flow entirely and is placed against the nearest positioned ancestor; inset: 0 stretches it over that ancestor. fixed is placed against the viewport and ignores scrolling: headers, toasts, the drawer backdrop. sticky is the hybrid: it scrolls with its parent until it reaches the threshold you set, then holds there until the parent scrolls away.

z-index and stacking contexts

z-index only orders siblings inside the same stacking context, and only on positioned elements (or flex and grid items). A new context is created by position with a z-index, opacity below 1, transform, filter, will-change, position: fixed or sticky, and isolation: isolate. Inside a context, a child's z-index: 9999 cannot escape over a sibling of the context's parent. The usual symptom: a dropdown stuck under a card with a shadow and a transform.

MudBlazor places popovers and dialogs in a provider at the end of body precisely to escape every stacking context in the page. The popover that stuck out past the right edge in Jolefilo was not a z-index problem but a viewport one: anything positioned beyond the right edge makes mobile Chrome widen the layout viewport. html { overflow-x: clip } is the safety net; anchoring the popover is the fix.

.jf-drawer { position: fixed; inset: 0 0 0 auto; width: min(100%, 480px); z-index: 1300; }
.jf-header { position: sticky; top: env(safe-area-inset-top, 0px); z-index: 10; }

Responsive design

Design for the narrowest screen first; every breakpoint then adds room, never removes it.

The viewport meta tag makes the phone report its real width instead of pretending to be a 980px desktop. From there the base CSS is the phone layout and each @media (min-width: …) widens it. Writing it the other way round, desktop first with max-width queries, means every phone rule has to undo a desktop rule, and the undo is forgotten more often than the rule.

Three habits remove most responsive bugs. Use relative sizes (%, rem, fr, minmax) and cap them with max-width. Let rows wrap or stack: flex-wrap, or a grid that goes to one column below a width. Give anything with text inside a flex or grid cell min-width: 0, so a long word wraps or ellipsises inside its cell instead of pushing the page wider.

Fluid type: font-size: clamp(18px, 5vw, 24px) grows with the viewport between a floor and a ceiling, so one rule replaces three breakpoints. Prefer it for display sizes; body text stays fixed.

Phone specifics

  • Touch targets at least 42px; the visual can be smaller if the hit area is not.
  • 100vh is taller than the visible area while the browser bar shows; 100dvh tracks it.
  • Safe areas on phones with a notch: padding-top: env(safe-area-inset-top) on fixed bars.
  • Hover does not exist on touch; Android keeps :hover on after a tap, so a hover tint looks like a stuck state. Style :active and :focus-visible instead.
  • Wide content (tables, code) scrolls inside its own overflow-x: auto box. The page body never scrolls sideways; the Console snippet in the DevTools card finds the offender.
  • Test in a mobile emulation with a mobile user agent and touch, at 360, 375 and 412 wide. A narrow desktop window does not reproduce the viewport-expansion behaviour.

Container queries

A media query asks about the viewport; a container query asks about the parent: container-type: inline-size on the card list, then @container (min-width: 400px) { … } inside. The same card component then adapts whether it sits in a sidebar or a full page.

Typography on screen

Most of what makes a screen look designed is type: a scale, a measure, and a line height.

A font stack lists faces in order of preference and ends with a generic family. Web fonts are loaded with a <link> to Google Fonts and display=swap, so text shows in the fallback at once and swaps when the font arrives. Jolefilo pairs a display face for titles and amounts with a text face for everything else; the display face is only used at 15px and above, where its character reads.

A scale is a short list of sizes you never leave: Jolefilo's runs 11, 11.5, 12, 12.5, 13, 13.5, 14.5, 15, 17, 22, 26, 27. The consistency matters more than the exact numbers. Pair each size with a weight and a line height: headings tight (1.2) and heavier, body open (1.5), labels small, uppercase and letter-spaced (.04em) so the caps do not clump.

The measure is the line length. Running text reads best around 65 characters; max-width: 65ch gives it. Cards and rows hold short strings, where the opposite rule applies: never let an amount or a date wrap.

Colour and theming

Name colours once as tokens, then build every rule from the names.

A custom property is a variable in CSS: declare --jf-primary: #1f6b3b on :root and read it anywhere with var(--jf-primary). Custom properties inherit, so redefining one on a section recolours everything inside. They are the only sane way to keep a palette consistent across hundreds of rules, and the only way to theme: redefine the same names in a dark block and nothing else changes.

:root { --bg: #eef2ef; --fg: #16241d; --primary: #1f6b3b; }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { --bg: #111816; --fg: #e7ede9; --primary: #63c3a6; color-scheme: dark; }
}
:root[data-theme="dark"] { --bg: #111816; --fg: #e7ede9; --primary: #63c3a6; color-scheme: dark; }
body { background: var(--bg); color: var(--fg); }

The pattern above is the one this page uses: a full light palette on :root, the dark values under the OS preference unless the user chose light, and again under an explicit dark choice. Component rules never contain a literal colour, so they are correct in both themes by construction.

Semantic colour

Keep two families apart. Brand colours (Jolefilo's primary green, the amber accent) identify the product. Semantic colours carry meaning: success, info, warning, error, each with a strong tone for text and a tint for backgrounds. The data model's states map onto them: Faturada and Pago are success, Guia emitida is info, Pendente is the accent, Diferença and Anular are error. A chip's colour is then a fact, not decoration, and the same fact reads the same on every screen.

Contrast

Text needs a contrast ratio of 4.5:1 against its background, large text 3:1. Light grey hints on white often fail; use them only for secondary text and never for the one sentence the user must read. DevTools shows the ratio when you click the colour swatch in the Styles pane.

Three ways to write one colour

#1f6b3b, rgb(31 107 59) and hsl(146 55% 27%) are the same green. HSL is the easiest to adjust by hand: keep the hue, lower the saturation for a muted variant, raise the lightness for a tint. The modern syntax uses spaces and a slash for alpha: rgb(31 107 59 / .5).

A field is a label, a control and a message, tied together so both eyes and readers connect them.

Focus

Every control must show where keyboard focus is. Browsers draw a ring on :focus-visible; if a reset removes outlines, add your own ring with outline and outline-offset, which does not move layout. Focus order follows the DOM, so a visually reordered flex item (order) is tabbed in source order, which confuses everyone. Reorder the markup instead.

ARIA and accessibility

What assistive technology reads, the three kinds of attributes, and the rules, each with the place in Jolefilo where it showed up.

The accessibility tree

A screen reader does not read pixels or HTML. The browser builds a second tree next to the DOM in which every node has a role (what it is), a name (what to call it) and, where it applies, a state. TalkBack walks it and speaks "Faturas, button, pressed". Native HTML fills the tree for free; ARIA corrects or completes it when HTML alone cannot say what the screen shows.

Roles, states, properties

Roles say what an element is and change nothing else: a div with role="button" is still a div with no keyboard behaviour. States change at runtime and take the words "true" and "false". Properties describe: a name, a description, a live region, a relation.

The rules, with our own code

  • Native first. The client row began as a div with role="button", tabindex and a key handler. As an <a href> it got the role, Enter, focus and long-press for free. The filter cards became real buttons for the same reason.
  • Every control needs a specific name. Icon buttons carry aria-label="Imprimir FT 2026/318", so six print buttons are not six "button"s. The trap: aria-label replaces the content. The row's "Abrir ficha de…" label silently hid the amounts from the reader until it was removed.
  • States are strings and track the visual. The green border came from a class and was right; aria-pressed came from a bool and was wrong. Drive both from the same if.
  • Announce changes away from focus. The list title changes when a card is tapped while focus stays on the card: aria-live="polite" speaks it. role="status" is a built-in polite region; role="alert" interrupts and is for errors.
  • Group what belongs together: role="group" aria-label="Filtrar documentos" around the cards, real headings for sections so a reader can jump.
  • Hide decoration with aria-hidden="true", never anything focusable.
  • Keep focus visible and somewhere. A ring on :focus-visible; when the focused element disappears ("Ver todos"), move focus to a sensible neighbour.

The Blazor bool trap, once more. Blazor renders a C# bool as an HTML boolean attribute: present and empty when true, absent when false. ARIA states need "true"/"false" as text, and an empty value reads as "no state". Write aria-pressed="@(Active ? "true" : "false")". Same for aria-expanded, aria-checked, aria-disabled, aria-selected.

Seeing it

DevTools → Elements → Accessibility pane shows role, name and states for the selected node. Playwright queries the same tree: getByRole('button', { name: 'Faturas', pressed: true }) only matches when all three are right, so a locator written that way is a test and an accessibility check at once. TalkBack on a real phone is the final word.

Tailwind for CSS people

A utility is one declaration with a short name. Everything else is the cascade you already know.

p-4 is padding: 1rem. flex is display: flex. text-sm is font-size: .875rem; line-height: 1.25rem. Tailwind scans your source files for class names, generates exactly those rules, and ships them in one stylesheet. The design lives in the theme: the spacing scale (one step is 4px), the colour palette with eleven shades per hue, the type scale, radii and shadows. In v3 you configure it in tailwind.config.js; in v4 in CSS with @theme.

Variants are prefixes that wrap a utility in a condition: hover:bg-gray-100, md:grid-cols-3 (a min-width: 768px media query), dark:text-white, focus-visible:ring-2. They stack: md:hover:underline. group and peer let a child or a sibling react to the parent or previous element's state.

Arbitrary values in square brackets escape the scale when a design needs an exact number: w-[760px], text-[13.5px], grid-cols-[repeat(auto-fill,minmax(150px,1fr))]. Jolefilo's mock would use these often, because its sizes are not on a 4px grid.

What changes in your head

  • You stop naming things. The class attribute describes the box; a repeated box becomes a component (a Razor component, a React component) rather than a CSS class.
  • Specificity disappears from daily life: every utility is one class. Two utilities for the same property on one element: the one later in Tailwind's generated order wins, and the order is fixed by property, not by your attribute. Reach for ! only when fighting a library.
  • Responsive is mobile first by default, exactly like the handwritten min-width pattern.
  • The scanner needs full literal class names in the source. "bg-" + tone produces a class Tailwind never generates. Map to full strings: tone == "error" ? "bg-red-100" : "bg-green-100".

Composing repeated patterns

Three options, pick one per pattern: a component that carries the classes (best for anything with behaviour); @apply in a stylesheet to bundle utilities under a class (.jf-chip { @apply inline-flex items-center gap-1.5 rounded-full px-3 py-1 text-xs font-bold; }); or plain CSS when the pattern needs selectors Tailwind cannot express. Do not do two of them for the same pattern.

Why Jolefilo does not use it

MudBlazor ships its own stylesheet and class names, and the mock's sizes are specific. A token file in :root plus jf-* classes keeps the overrides in one file with the specificity under control. Tailwind next to MudBlazor is possible but you would spend the time on conflicts. Driveway, without a component library, is the right place to learn it.

Styling Blazor and MudBlazor

Where the CSS goes, how to win against the library, and the rendering details that bite.

Where CSS lives

Two choices. A global stylesheet (wwwroot/css/site.css) with tokens on :root and prefixed classes (jf-*), which is what Jolefilo does: one file, one place to search, no scoping surprises. Or CSS isolation: a Component.razor.css next to the component, whose rules are rewritten at build time to match only that component's elements (an attribute like b-x1y2 is added to both). Isolation cannot reach into child components unless you write ::deep .mud-button-root, and it cannot style MudBlazor's popovers, which render elsewhere. For a design-system app the global file wins.

Winning against MudBlazor

Every MudBlazor component accepts Class and merges it with its own classes on the root element. Your rule then competes with MudBlazor's, which is loaded first and usually has one or two classes of specificity. The reliable pattern: your class and one of theirs on the same element, .jf-cash-close.mud-button-root, plus the state when they style it, :hover, :focus-visible, .mud-disabled. For text colour MudBlazor's palette classes carry !important; set Color="Color.Inherit" and colour the wrapper instead of fighting them. Inline Style works but hides the rule from the stylesheet; use it only for values computed at runtime.

Rendering details

  • Bool attributes: true renders the bare attribute, false removes it. Right for disabled, wrong for ARIA.
  • Unmatched attributes on a MudBlazor component are splatted onto its root element: role, aria-*, data-* land where you expect.
  • @key tells the diff which rendered row belongs to which item; without it a filtered list patches rows by position and inputs keep stale values. Keys must be unique among siblings or rendering throws, and in Blazor Server that kills the circuit.
  • @onclick:preventDefault and :stopPropagation are attribute modifiers; they apply to every event of that kind on the element, so do not put @onkeydown:preventDefault on something the user must Tab through.
  • Ripple and hover: MudButton paints hover, focus and ripple backgrounds. On Android the hover tint sticks after a tap; override the state selectors with enough specificity and set Ripple="false" where a card should keep its own colours.
  • No prerendering in Jolefilo means the DOM is built only by the circuit, so JS interop is always available and lifecycle methods run once; it also means the first paint waits for the connection.

A debugging routine

When a screen looks wrong, work through this in order; most problems fall out by step four.

  • Select the element in DevTools and read Computed: is the property what you think, and which rule set it? A struck-through rule lost the cascade; find the winner above it.
  • Check the box in the Computed diagram: margin, border, padding, content. A collapsed margin or a content-box width explains most "it's 20px off" cases.
  • Check the container: is the parent flex or grid, and does the child have min-width: 0? Turn on the Layout overlay to see the tracks.
  • Check overflow: run the Console snippet to find what reaches past the right edge; check scrollHeight > clientHeight where something should scroll.
  • Check the state: force :hov states, toggle classes with .cls, and read the Accessibility pane for role, name and state.
  • Check the width: repeat at 360, 375 and 412 in the device toolbar with a mobile user agent, and in both themes.
  • Fix in the stylesheet, not in the Styles pane; then reload and confirm the rule you added is the one that wins.

Keep this page open next to the project rules. The cheatsheet answers "how do I write it"; this part answers "why did it do that". When neither does, the DevTools card has the three lines of Console that answer most of the rest.
